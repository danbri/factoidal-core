# Parse stack performance pass, 2026-11-05

Scope: `formal/lean4/L4Factoidal/` HTML, DOM, XML, Syntax (Turtle, N-Triples,
lexing, IRI), RDF term and graph lists, and the basic SPARQL path. The long-term
target is an ESP32-P4 class device: 32-bit, 400 MHz, 768 KB L2, 32 MB PSRAM. So
this note gives memory peak, allocation count and stack depth with the time.

## Result

Paired instruction counts, realistic inputs of 1 MB, net of process start:

| stage | instr/B before | after | change |
|---|---:|---:|---:|
| HTML tree (`parseHtml`) | 2460 | 1128 | -54 % |
| HTML DOM arena | 2460 | 1138 | -54 % |
| HTML tokenizer alone | 875 | 693 | -21 % |
| XML (`parseXML`) | 424 | 400 | -6 % |
| XML namespace view | 986 | 747 | -24 % |
| Turtle | 793 | 769 | -3 % |
| N-Triples | 478 | 345 | -28 % |

Peak memory of the HTML stages fell from about 64 to about 29 bytes per input
byte. Allocations of the HTML tree stage fell from 8.2 to 3.1 per byte.

Nine rows of the stress table that cost quadratic time are now linear (see "Stress
shapes"). The worst case: a 400 KB XML start tag with about 30,000 attributes through
the namespace view fell from 362,621 to 1,573 instructions per byte.

Turtle hardly changed (-3 percent) and XML by -6 percent: their profiles are flat, and
the large items left in Turtle are not small fixes.

Output stayed byte-identical on every corpus (see "Output check").

Not fixed, in order of importance for the target:

1. `parseTurtle` and `parseNTriples` hold the document as `List Char`: 41 to 49 bytes
   of peak memory per input byte. This is the largest memory defect in the stack.
   For N-Triples the `String` cursor reader `foldLinesS` already avoids it (167
   instr/B, 0.1 bytes of net RSS per byte). Turtle has no such reader.
2. Nested `[ ]` and `( )` in Turtle cost quadratic time and stack per level.
3. XML element nesting and `HTML.buildTree` use stack in proportion to the depth.
4. HTML `<div>` nesting costs quadratic time: "has an element in button scope"
   walks the stack of open elements.

## Method

Tool: `formal/lean4/Harness/ParseBench.lean` (`l4parse-bench`),
`formal/lean4/Harness/ParseBenchQuery.lean` (`l4parse-bench-query`) and
`tools/parse-bench.py`.

```
cd formal/lean4 && LEAN_NUM_THREADS=2 lake build l4parse-bench l4parse-bench-query
python3 tools/parse-bench.py --bin BIN --dir SCRATCH table    # realistic inputs
python3 tools/parse-bench.py --bin BIN --dir SCRATCH stress   # one feature at scale
python3 tools/parse-bench.py --bin BIN --dir SCRATCH stack    # smallest stack
python3 tools/parse-bench.py --bin BIN --query-bin QBIN --dir SCRATCH query
```

The inputs are generated by the tool, so they are the same on each run and the
repository holds no large file. Each is a block repeated with a counter: an
article page for HTML, an Atom-style feed with two namespaces for XML, resources
with nested blank nodes and collections for Turtle, and lines with IRIs, labels
and blank nodes for N-Triples.

Measures:

- **Instructions** and **peak RSS**: `/usr/bin/time -l` on macOS arm64. Figures
  are net of the `null` stage on the same file, which is process start, file read
  and the UTF-8 check. The smallest of 2 runs for the table; 1 run for stress.
  Instructions varied by 0.2 to 0.5 percent between runs (4 runs of `ttl`, 3 of
  `html-tree`, 1 MB). Wall time was not used:
  the load average of the machine was 10 to 37.
- **Allocations**: the change of `IO.getNumHeartbeats` around the stage. It counts
  small-object allocations of the thread. It does not count large arrays and
  strings, and it does not count bytes.
- **Linearity**: the exponent `e` in `cost = n^e` over the last doubling (1 MB to
  2 MB for the table, 200 KB to 400 KB for stress). An exponent of 1.00 is linear.
- **Stack**: the smallest `LEAN_STACK_SIZE_KB` with which the run ends well, by
  bisection to 1/16. `lean_run_main` runs `main` on a new thread of that size;
  `ulimit -s` has no effect. The floor on this machine is 15 KB, so "15" means 15 KB
  or less. Inputs of 25, 50 and 100 KB.
- **Recursion in compiled code**: `tools/lean-tail-recursion-audit.py` and
  `tools/lean-csimp-reach.py`, run over the C of the 121 modules that this pass
  built. CI runs them over the whole library.
- **Profiles**: `sample` on a process spawned suspended, so that the start of the
  run is in the sample. 1 ms sampling, 4 runs of a 2 MB input, 400 to 1,100 samples
  for each stage. **Profile percentages are noisy** (the machine was loaded and a
  stage runs 0.1 to 0.3 s): treat a difference under 2 points as nothing.

`nt-text` is the existing `String` cursor reader
(`StrictFeedText.foldLinesS`, counting triples, keeping no graph), after the pass
only: 167 instr/B, 0.33 allocations per byte, 0.1 bytes of net RSS per byte at 1 MB,
exponent 1.01, stack at the floor. It is not comparable with `nt`, which builds the
graph, but it shows that N-Triples can run with no `List Char`.

The net RSS at 1 KB is mostly the first pages of the allocator, so RSS/B at 1 KB
says nothing about a large input. Instructions per byte at 1 KB are higher than at
1 MB because a fixed cost per document is in them.

Process start is outside these figures. `l4parse-bench` takes 45.2 M instructions
to start, a Lean program that prints one line takes 24.4 M, and
`l4parse-bench-query`, which has no HTML modules, takes 32.4 M. So the closure with
HTML costs about 13 M more at start. The likely cause is the table of named
character references in `HTML/Entities.lean`, built at module start. This pass did
not change that file and did not measure the cause.

Basic SPARQL, `SELECT` over a parsed N-Triples list, net of the parse, 1 MB input
(1 run): a join of two patterns on `?s` costs 50 instructions and 0.13 allocations
per input byte, with an exponent of 1.03. A one-subject pattern costs 3
instructions per byte. Query evaluation is small beside the parse. This path did
not change.

## Stack

Smallest stack in KB at inputs of 25, 50 and 100 KB:

| shape | stage | before | after |
|---|---|---|---|
| `xml-attrs` | `xml`, `xml-ns` | 23, 167, 471 | 15, 15, 15 |
| `xml-nsdecls` | `xml-ns` | 15, 71, 263 | 15, 15, 15 |
| `html-deep` | `html-tree` | 279, 711, 1607 | 279, 711, 1607 |
| `html-deep` | `html-dom` | not measured | passes at 16 at 100 KB |
| `xml-deep` | `xml`, `xml-ns` | 1287, 2695, 5639 | 1287, 2695, 5639 |
| `ttl-deep` | `ttl` | not measured | 1799, 3719, 7431 |
| `ttl-coll-deep` | `ttl` | not measured | 1735, 3591, 7175 |

After the pass, all realistic inputs and all wide or long-token shapes run at the
15 KB floor at 25, 50 and 100 KB. The two `xml-*` rows were recursion per attribute:
`parseAttributes`, `List.zip` in `changedAttrs`, and `applyDeclarations`. The recursion
that remains is per nesting level, not per token, per character or per sibling:

- HTML, about 180 bytes per level: `HTML.buildTree`. `DOM.parseHtmlDocument` does not
  call it: 9,090 levels pass with a 16 KB stack through `html-dom`, and fail with 64 KB
  through `html-tree`. On record as pending in
  https://github.com/danbri/factoidal/issues/1110 (recursion audit).
- XML, about 400 bytes per level: `parseElementW`, `parseChildrenW`, `checkElement`,
  `namespaceView`.
- Turtle, about 450 bytes per level of `[ ]`, about 220 per level of `( )`: the
  `readObject` cycle.

At those frame sizes a 16 KB task stack holds about 40 levels of XML or Turtle. These
functions need an explicit stack, or a nesting limit, before the target reads an
untrusted document. These are arm64 frames; a wasm or RISC-V frame differs.

## Ranked hotspots

Before the pass, by effect on the target. Numbers are from the runs above.

1. **Copy of a child list on each insert** (`HTML.insertAt`). 87 percent of the main
   thread on `html-wide`, in `lean_copy_expand_array` and `lean_del_core_other`. Fixed:
   14,413 to 1,159 instr/B at 400 KB, exponent 1.80 to 0.97.
2. **`List Char` as the input of Turtle and N-Triples.** `String.toList` alone is 17
   and 30 percent of inclusive samples after the pass, and the list is 24 bytes per
   character. Not fixed: the parsers and their theorems are written over lists.
3. **One token per text character** in the tree builder: 15 allocations and 3,841
   instructions per byte on `html-text`. Fixed with `textRun`: 0 allocations (205 in
   the whole document) and 204 instructions per byte.
4. **`attrsUniqueExpanded`** through `List.eraseDups`, 86 percent of `xml-ns` on
   `xml-attrs`. Fixed: hash from 16 keys.
5. **`hasAttr` in `parseAttributes`**, and the same search in `Tok.finishAttr`.
   Quadratic in the attributes of a tag, and `parseAttributes` used a frame per
   attribute. Fixed.
6. **`normalizeNewlines`** through two lists: 11 percent of `html-tree` and the
   largest part of its peak memory. Fixed: one pass into an array, proved equal.
7. **`isValidNCName`** through `String.toList`: 27 percent of `xml-ns`. Fixed.
8. **`IriStep` and `StrLitStep`** allocated per character: 41 percent inclusive in
   `readIriRefBodyGo` on N-Triples. Fixed: 34 percent after, and one allocation less
   per byte.
9. **Tokenizer record copied per token** in `runAll`, and error lists copied by
   `perr` in `adoption`. Fixed.
10. **Nested Turtle**: `reverse` of all inner triples at each level, 99 percent in
    `List.reverseAux` on `ttl-coll-deep`. Not fixed.
11. **`hasScope`** over the stack on each block start tag: 2.5 percent of realistic
    HTML, and all of the time on `html-deep`. Not fixed.

After the pass no single Lean function dominates a realistic stage. Reference
counting and allocation (`lean_dec_ref_cold`, `mi_free`, `mi_malloc_small`) are 15
to 24 percent of self samples. `_tlv_get_addr` is 10 to 13 percent; it is the macOS
thread-local read for the allocator and the heartbeat, so that part of the
instruction count belongs to this platform.

Inclusive samples after the pass, percent of the main thread:

- `html-tree`: `Tok.pull` 27, `Tok.step` 21, `process` 41, `inBodyH` 30.
- `xml-ns`: `parseXMLCore` 49, `namespaceWellFormed` 22, `namespaceView` 20.
- `ttl`: `readTurtleIri` 44, `readPrefixedName` 17, `lean_string_data` 17.
- `nt`: `readIriRefBodyFast` 34, `lean_string_data` 30, `readLiteral` 13.

## Changes

Each new fast form has a proof of equality with the old definition and a `@[csimp]`
theorem, except where this list says otherwise. No old definition, proof, `#guard`
or test changed. No public signature changed; `Tok` has one new field with a default.

| change | file | proof |
|---|---|---|
| `insertAt` takes the child list out of the parent before the write | `HTML/TreeBuilder.lean` | none, by the tests below |
| `runAll` takes the tokenizer out of the state during `pull` | `HTML/TreeBuilder.lean` | none, by the tests below |
| `textRun`: a run of plain characters in one step | `HTML/TreeBuilder.lean` | none, by the tests below |
| `detach`: `pop` when the child is last; `moveKids` | `HTML/TreeBuilder.lean` | none, by the tests below |
| `popUntil` and `adoption` read the state before the write | `HTML/TreeBuilder.lean` | none, by the tests below |
| `Tok.finishAttr`: hash from 16 attributes | `HTML/Tokenizer.lean` | none, by the tests below |
| `normalizeNewlinesFast` | `HTML/Tokenizer.lean` | `normalizeNewlines_eq_fast` |
| `matchLitStr` for `pstring`, `peekLit` | `XML/Parser.lean` | `peekLit_eq_fast`, `pstring_eq_fast` |
| `parseAttributesLoop`: no frame per attribute, hash from 16 | `XML/Parser.lean` | `parseAttributes_eq_fast` |
| `changedAttrsLoop`: no `List.zip` | `XML/Parser.lean` | `changedAttrs_eq_fast` |
| `isValidNCNameFast` | `XML/Wellformedness.lean` | `isValidNCName_eq_fast` |

`parseTurtleWithPrefixes` and `parseTurtleFold` keep `cs.length`. The change is worth
about 4 percent of N-Triples and less than the noise of the profile on Turtle.

`tools/lean-tail-recursion-allow.txt`: two lines removed
(`L4Factoidal_XML_parseAttributes`, `L4Factoidal_XML_applyDeclarations`). No line added.

The tree builder has no theorems and uses a state monad, so its changes have no
proof. The argument for `detach` and `moveKids` is the arena rule that a node is in
one child list at most, once, because `insertAt` takes only new or detached nodes.
That rule is read from the eight call sites, and it is not a theorem.

## What this pass could not measure

- **No run on an ESP32-P4, or on any 32-bit or RISC-V target.** All numbers are native
  macOS arm64. The instruction count of a RISC-V build will differ. Lean's object
  header stays 8 bytes on 32-bit, so a `List Char` cell should be 16 bytes, not 24, and
  an `Array Char` slot 4, not 8. This is arithmetic, not a measure.
- **No wasm run.** The `test/stack-use.test.mjs` package gate and the phone emulation of
  trap 12 in `skills/npm-release/SKILL.md` were not run. Native stack figures do not
  predict wasm frames. CI builds run the wasm gates.
- **No Linux run.** `/usr/bin/time -v` gives no instruction count, so the tool needs macOS
  for that column.
- **Bytes allocated and live heap.** Peak RSS is of the process. The Lean allocator
  keeps freed pages, so it is an upper bound of the live heap of a stage. A live-heap
  high-water mark needs a patched runtime.
- **Instructions are not time.** Cache behaviour with a 768 KB L2 and PSRAM is not
  modelled, and a list walk will suffer there more than the instruction count shows.
- **The W3C Turtle and N-Triples suites did not run here:** `third_party/testing/rdf-tests`
  is a submodule that this worktree did not check out. CI runs them. The local check is
  the 391 repository files.
- **`tests/dom/run.sh`:** the jsdom differential did not run here; CI runs it.
  `tests/dom/scaling.mjs` did run: 4 pass, and the 1 expected failure of
  https://github.com/danbri/factoidal/issues/1216 (remove half the children of a node).
- **A whole-library build did not run here**, by instruction. Theorems in modules outside
  the list above are checked by CI only.
- **RDF/XML, TriG, N-Quads and JSON-LD** have no bench shape. They gain from the lexing
  and XML changes, but this pass did not measure them.
- **SPARQL:** only the list-graph `evalSelect` path, not the indexed store path.

## Next steps

1. A `String` cursor reader for Turtle, as `Syntax/StrictFeedText.lean` is for
   N-Triples and N-Quads. It needs new parser forms and equality proofs, so it is a
   project, not a fix. Also, make `foldLinesS` the route for N-Triples on the target.
2. An accumulator through `readObject`, to end the quadratic cost of nested Turtle.
3. An explicit stack for `parseElementW` and `namespaceView`, and a loop for `buildTree`.
4. A count of open `p` elements in `TB`, or a depth limit, for `hasScope`.
5. A resolve shortcut for absolute IRIs with no dot segments: `resolveIri` is 10 percent
   of Turtle. This pass left it out because it has no proof yet.
6. A table of named character references with no work at start.
