# The DOM node tree as an arena in Lean (2026-11-01)

Milestone 6 of https://github.com/danbri/factoidal/issues/1167 (modular wasm
and a browser proof of concept with Lean at its heart). Status: first
implementation. The node tree of the DOM Standard (whatwg/dom commit
`3c53f93a`, main on 2026-11-01) is in `formal/lean4/L4Factoidal/DOM/`. Its
mutation algorithms give the same results as jsdom 30.1.3 on 240,000 random
operations. The HTML parser of milestone 5 gives its tree to it.
Follow-up: https://github.com/danbri/factoidal/issues/1216.

## What the arena is

`Dom` is an array of `Node` records. A node is its index (`NodeId`).

- Fields: node type, node document, namespace, prefix, local name (also the
  doctype name and the PI target), attribute list, data, public and system id,
  parent, child list, host, template contents, and the document type ("html" or
  "xml").
- The node types are Document, DocumentType, DocumentFragment, Element, Text,
  CDATASection, Comment and ProcessingInstruction. There are no `Attr` nodes:
  an attribute is a record in the element's attribute list (DOM §4.9.2).
- Indexes are never reused. A removed node stays in the arena with no parent, as
  a JavaScript reference to a removed node stays valid. So a handle that a host
  gives out (a WIT resource, a wasm export argument) cannot point to a different
  node later. The cost is that a removed subtree is never collected (item 7 of
  https://github.com/danbri/factoidal/issues/1216). A collector would need a
  generation number in each handle.
- A node keeps its parent and an array of its children. The DOM Standard defines
  the previous and next sibling; here they come from the parent's array.
- The template contents of an HTML `template` element (HTML §4.12.3) is a
  separate DocumentFragment. Its host is the element. So the host-including
  inclusive ancestor rule (DOM §4.2.2) applies: a `template` cannot go into its
  own contents. The HTML parser arena keeps the contents as the element's
  children; `DOM.ofTreeBuilder` moves them into the fragment.

Every operation is a total function. An operation that can throw has the type
`Dom → Dom × Except DomError α` (`Res α`): it gives back the arena in both
cases. The check reads the arena; only the success branch changes it.

Walks up the tree (`ancestorWalk`, `hostWalk`) are tail calls with fuel equal
to the arena size. Walks down the tree (`treeOrder`, `cloneNode`,
`isEqualNode`, the dump) are loops with a work list. No walk uses one stack
frame per node. `tools/lean-tail-recursion-audit.py --gate` passes; it lists
one `Array.qsort` over the attributes of one element in the test dump.

## Algorithms implemented

DOM §4.2.3: ensure pre-insert validity (each of its 11 steps, in order),
pre-insert, insert (a DocumentFragment gives its children), append, replace,
replace all, pre-remove, remove, adopt, and move (`moveBefore`). §4.4:
`textContent` (get and set), `normalize`, `cloneNode` (with the cloning steps
of `template`: a deep clone clones the template contents), `isEqualNode`,
`contains`. §4.2.4: get an element by ID. §4.5: `createElement` (valid element
local name of §1.4, ASCII lowercase in an HTML document, the HTML namespace),
`createTextNode`, `createComment`, `createCDATASection`,
`createProcessingInstruction` (the target must match the XML Name production;
`XML.isName` of the XML parser is used), `createDocumentFragment`,
`createDocumentType` (§4.5.1). §4.9: `setAttribute`.

Not implemented (https://github.com/danbri/factoidal/issues/1216): shadow trees
and slots, live ranges, `NodeIterator` and `TreeWalker`, mutation observers,
events, custom elements, the namespace methods (`createElementNS`,
`setAttributeNS`), `Attr` nodes, the template adopting steps across documents,
documents of type "xml" from the XML parser, and the insertion, removing and
moving steps of other specifications. These hooks have no effect when no other
specification is present. So the tree that the algorithms give is the tree of
the standard, but nothing observes the changes.

## How it is tested

1. **WPT tree construction through the DOM arena.** `l4html5lib dom-tree` runs
   the 62 `.dat` files of milestone 5. It compares the expected tree with the
   dump of the DOM arena that `DOM.ofTreeBuilder` makes of the parse. This
   checks the conversion (namespaces, the adjusted foreign attributes, the
   template contents) against real test data.
2. **Differential against jsdom.** `tests/dom/diff.mjs` makes random scripts.
   Each script starts from one of 8 HTML documents. jsdom runs each operation
   while the script is made, so a method is only called on a node whose
   interface has it (for example, `remove()` only on a ChildNode). One operand
   in four is the Document or one of its first nodes in tree order, so the
   Document rules (steps 5 to 11) are reached. `l4dom ops` runs the same
   scripts on the Lean arena. The two outputs must be the same, line by line:
   each result (`ok`, a value, or the DOMException name), and at the end the
   tree of every root that a handle names. `l4dom` also checks the tree
   invariant (`Dom.wellFormed`) at the end of each script. jsdom is a
   reference implementation, not the specification. A disagreement is read
   against the DOM Standard text before either side changes.
3. **Lean checks** (`L4Factoidal/DOM/Tests.lean`, `#guard`, checked at build
   time). They cover `moveBefore`, which jsdom does not have, the template
   host rule, and the clone of template contents.
4. **Scaling** (`tests/dom/scaling.mjs`, skill
   `danbri-function-precrime-checkers`). See § Speed.

## Theorems

`L4Factoidal/DOM/Theorems.lean`. Axioms: propext, Classical.choice, Quot.sound.

- `ensurePreInsertValidity_rejects_ancestor`: when `node` is a host-including
  inclusive ancestor of `parent`, ensure pre-insert validity throws a
  HierarchyRequestError, for every `child` and every list of excluded children.
  This is the rule that keeps an insertion from making a cycle.
- `preInsert_rejects_ancestor`, `replace_rejects_ancestor`: pre-insert and
  replace of an ancestor throw, and give back the arena unchanged.
- `hostIncluding_self`, `appendChild_self`: `n.appendChild(n)` throws and
  changes nothing.
- `remove_parent_none`, `remove_not_child`: after "remove", the node has no
  parent and is not among the children of its old parent.

Not proved: that every operation keeps `Dom.wellFormed` (item 1 of
https://github.com/danbri/factoidal/issues/1216). It is checked at the end of
every differential script.

## Speed

`l4dom ops` on scripts that append n Text nodes to one element (times of the
final build; best of 3):

| Case | n = 40000 | 4n = 160000 | Ratio |
| --- | --- | --- | --- |
| append | 76 ms | 273 ms | 3.6 |
| append, then `normalize` | 81 ms | 289 ms | 3.6 |
| append, then `textContent` | 77 ms | 303 ms | 3.9 |
| append, then a deep clone | 118 ms | 312 ms | 2.7 |
| append n = 10000 and 40000, then remove half | 130 ms | 1717 ms | 13.2 (expected failure) |

Three faults made the first version quadratic. Each was a shared Lean array,
which `Array.push` and `Array.modify` then copy:

1. The harness kept the old arena alive for the error case while an operation
   changed it. Fix: each operation gives back the arena (`Res`).
2. `Dom.push` read the array size after the push. This is the same fault as
   `newNode` of the HTML tree builder (milestone 5 record, § Speed). Fix: read
   the size first.
3. `linkChild` wrote `{ pn with kids := pn.kids.push c }`, so the child array
   was shared during the push. Fix: take the array out of the node first.

With all three, 80,000 appends took 44 s; with none, 0.14 s. `normalize` walked
with `nextSibling`, which searches the parent's array for each Text node
(80,000 siblings: 16 s). It is now one pass over each child array (0.15 s).

The remaining quadratic case is `remove`: with an array of children, one
removal searches the array and makes it again, so the time is proportional to
the number of siblings. Browsers keep sibling links and remove in constant
time. Changing to sibling links (previous and next in each node) makes
remove, insert before and the sibling getters constant time, and makes
`childNodes[i]` linear. That is item 8 of
https://github.com/danbri/factoidal/issues/1216; the scaling test fails as
STALE when remove becomes linear.

## Decisions

- **Specification snapshot.** whatwg/dom `3c53f93a`, the newest commit at the
  time of writing, as for the HTML parser (milestone 5). It has `moveBefore`
  and the 2025 valid element local name rule; jsdom 30.1.3 has the name rule
  and not `moveBefore`.
- **Children as an array, not sibling links.** The array is the form of the HTML
  parser arena, the conversion keeps node indexes, and the theorems about
  `remove` are statements about a list. The measured cost is above.
- **A separate template contents fragment.** The DOM and HTML standards define
  it so, and the host-including rule needs the host link. The parser arena did
  not decide this (milestone 5 record, § Decisions).
- **No Attr nodes and no namespace methods yet.** `setAttribute` is enough for
  the browser proof of concept; `setAttributeNS` and Attr nodes come with the
  WebIDL bindings (https://github.com/danbri/factoidal/issues/1203).
- **Reference for the differential: jsdom.** It runs in Node with no browser, is
  maintained to the current standard, and its parser (parse5) agrees with the
  Lean parser on the 8 source documents. The source documents have no
  processing instructions: the Lean parser follows the 2026 rule
  (whatwg/html `320c05f`), and parse5 makes a bogus comment.

## Relation to the other milestones

- Milestone 1 (wasm components) recommends coarse operations at a component
  boundary. A `NodeId` is a `u32` that never changes meaning, so it can be the
  handle of a WIT resource without an indirection table.
- Milestone 5 (HTML parser): `DOM.parseHtmlDocument` parses into this arena.
- The XML parser (`L4Factoidal/XML/`) gives an inductive tree, not an arena.
  A conversion to a document of type "xml" is item 5 of
  https://github.com/danbri/factoidal/issues/1216.
