# Unicode algorithms in Lean (2026-10-29)

Milestone 4 of https://github.com/danbri/factoidal/issues/1167 (modular wasm and
a browser proof of concept with Lean at its heart). Status: normalization
(UAX #15), text segmentation (UAX #29), the bidirectional algorithm (UAX #9) and
line breaking (UAX #14) are in Lean for Unicode 18.0.0. They give 0 fail on the
seven Unicode conformance files.

Case counts:

- NormalizationTest: one case per data line. A line passes only if every check
  in the file header holds for it (NFC, NFD, NFKC and NFKD of all five
  columns). One more case, `part1-invariance`, checks that every code point
  that Part 1 does not list is unchanged by all four forms.
- BidiTest: one case per pair of a data line and a paragraph direction bit.
- BidiCharacterTest: a case passes only if the paragraph level, the levels and
  the visual order all agree.

The times are wall-clock times of `l4unicode CMD FILE`. They include process
start, reading the file and parsing it in Lean. They were measured on the
4-vCPU cloud VM (Intel Xeon at 2.10 GHz), native build, on 2026-10-29. No
comparison with ICU or another engine was made.

## Specifications and data

- Unicode 18.0.0. UAX #9 revision 52, UAX #14 revision 57, UAX #15 revision
  58, UAX #29 revision 49. Section and rule numbers in the Lean comments are
  the numbers of these revisions.
- UCD files: `third_party/unicode-18.0.0/` (provenance in its `PROVENANCE.md`).
  Milestone 3 started this directory for UTS #46. This milestone adds the
  files that the four algorithms need.
- Conformance files: `third_party/testing/unicode-18.0.0/` (provenance in
  `third_party/testing/unicode-18.0.0-PROVENANCE.md`).

Why 18.0.0: milestone 3 pinned the URL Standard's IDNA tables to 18.0.0,
because the web-platform-tests `IdnaTestV2.json` is generated from the 18.0.0
file. One version for the whole `L4Factoidal/Unicode` and `WHATWG` stack
avoids two property tables for one code point.

Each data module is generated by a script in `tools/unicode/`.
`tests/unicode/run.sh` runs each script with `--check`, and the check fails
when a module does not match the vendored files. The tables are string
literals that `RangeTable.ofText` reads once, so a table compiles in constant
time.

Default values: the generators take the value of a code point that a data
line does not list from the `@missing` line of its file (UAX #44 §4.2.10).
They do not take it from the header prose. LineBreak.txt 18.0.0 has a header
comment that names U+1F000..U+1FAFF as `ID`. But its data lines leave
U+1F8D9..U+1F8FF to `@missing` (`XX`), and LineBreakTest.txt expects `XX` for
U+1F8FF. The first version of the generator used the header prose and needed a
special case for that block. The present version reads only the data lines and
`@missing`, and it gives the same 0 fail with no special case.

## Modules

| Module | Contents |
| --- | --- |
| `Unicode/RangeTable.lean` | sorted range table read from a string literal; binary search |
| `Unicode/NormData.lean` | generated: canonical combining class, full canonical and compatibility decompositions, primary composites |
| `Unicode/Normalization.lean` | `nfd`, `nfc`, `nfkd`, `nfkc` (on `String`), and the same on code point arrays; Hangul by Unicode §3.12 |
| `Unicode/SegmentData.lean` | generated: Grapheme_Cluster_Break, Word_Break, Sentence_Break, Extended_Pictographic, Indic_Conjunct_Break |
| `Unicode/Segmentation.lean` | `graphemeBreaks`, `wordBreaks`, `sentenceBreaks` (boundary positions); `graphemes`, `words`, `sentences` |
| `Unicode/BidiData.lean` | generated: Bidi_Class (with the `@missing` defaults), paired brackets, mirroring, canonical singletons for BD16 |
| `Unicode/Bidi.lean` | P1 to P3, X1 to X10, W1 to W7, N0 to N2, I1, I2, L1, L2; `paragraphs`, `levelsOfText`, `visualOrderLines` |
| `Unicode/LineBreakData.lean` | generated: Line_Break, East_Asian_Width (F, W, H), Extended_Pictographic, the General_Category values the rules use |
| `Unicode/LineBreak.lean` | LB1 class resolution, LB2 to LB31 in one forward pass; `breaks` |
| `Harness/UnicodeConformance.lean`, `Harness/Unicode/*.lean` | `l4unicode`: reads and parses the conformance files in Lean |

All work over input text is in `for` loops over arrays.
`tools/lean-tail-recursion-audit.py --gate` passes, and the work adds no
`partial def` (`tools/lean-hygiene-audit.py`: 163, the baseline).

Bidi and lines: `levels` and `visualOrder` lay out a paragraph as one line, as
the two conformance files do. `visualOrderLines` takes the line ends of a
paragraph (for example from `LineBreak.breaks`). It applies L1 at the end of
each line and L2 to each line.

## Theorems

All three files are imported from `L4Factoidal.lean`. Axioms: at most
propext, Classical.choice and Quot.sound.

- `SegmentationTheorems`: `cutAt_flatten`. If a list is cut at any array of
  positions, the pieces concatenate back to the list. `graphemes_join`,
  `words_join` and `sentences_join` apply this to the three segmentations: the
  segments of a string concatenate back to the string.
- `LineBreakTheorems`: `breaks_contains_end` (LB3: the end of a non-empty text
  is a break opportunity) and `breaks_not_zero` (LB2: the start is not).
- `BidiTheorems`: `revRange_size` and `revRange_perm`. The range reversal
  that L2 uses keeps the array size and gives a permutation of its input.

These are structural properties. No theorem yet connects these functions with
a statement of the rules that is separate from the implementation. The
conformance files are the evidence for the rules.

## Reuse and overlap

The initial Unicode implementation left XPath4 on normalization 16.0.0 and
grapheme clusters 15.1.0. The follow-up for
https://github.com/danbri/factoidal/issues/1195 makes `XPath4/Unicode.lean`
an adapter over Unicode 18.0.0 normalization and removes the duplicate
normalization tables and generator. XPath form handling, FULLY-NORMALIZED and the
collation helper APIs remain at the XPath boundary. WHATWG IDNA also receives
the new normalization through that adapter.

The final combined candidate retains `XPath4/Grapheme.lean` and
`XPath4/GraphemeData.lean` exactly as before, using Unicode 15.1. The shared
Unicode 18 segmentation stays available directly. A prior candidate also
migrated XPath graphemes, producing four visible failures against the pinned
Unicode 15.1 QT4 expectations because Unicode 18 changes GB9c. That XPath
grapheme change is deferred; no fixtures or exclusions changed, and the
remaining migration stays open in the issue above. The case names,
conformance evidence and separately labelled candidate measurements are in
[the integration record](../20261029-qt4-unicode-namespace.md).

The HTML tokenizer of milestone 5 and the URL code of milestone 3 can use
`Unicode/Normalization` and `Unicode/Segmentation` directly. The browser proof
of concept needs `Bidi` and `LineBreak` for text layout.
