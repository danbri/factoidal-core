# Factoidal on iOS and Android: a native library from Lean's C output

Date: 2026-10-29. Proposal, no code. Tracking:
https://github.com/danbri/factoidal/issues/1198.

Owner, 2026-10-29, verbatim: "if we want to facilitate ios and android apps
using it, what is our best path? C on ios?", then "Yes" to: write a design
record and an issue for a native library for iOS and Android. Then, verbatim:
"And if we wanted graphics from lean?(" (section 8).

## 1. Result

Two paths, in this order:

1. **Stage 0, web view.** The current wasm runs in WKWebView (iOS) and in the
   Android WebView. This needs no new toolchain. It cannot run servers, and
   its file access is the web view's storage.
2. **Stages 1 to 6, native library.** Compile the C that Lean already emits
   (the input of the wasm build) for the mobile targets, with the same C ABI
   as the wasm. Swift and Kotlin call that ABI. There is no JIT and no code
   download, so App Store and Play rules do not stop it.

These paths are not suitable:

- `deno compile` (the single-file executables of
  `docs/designissues/2026-10-28-single-file-app.md`) has no iOS or Android
  target.
- An iOS app cannot start another process, so a CLI executable cannot run
  there at all.
- Embedded Node (nodejs-mobile) is large, and on iOS it has no JIT.
- A wasm runtime in the app (WAMR with ahead-of-time compilation, wasm3)
  works, but when the C is available it adds a layer and gives nothing.
- The JavaScriptCore framework on iOS, outside a web view: as far as we know
  it has no `WebAssembly` object, because Apple does not allow JIT in
  third-party apps. To confirm in stage 0.

## 2. What exists

- `formal/lean4/Wasm/build-wasm.sh` takes Lean to C to wasm
  (`skills/lean4-wasm-export/SKILL.md` § The route chosen). Steps 1 to 5
  (lean4 runtime sources, hand-written `lean/config.h` without
  `LEAN_USE_GMP`, core library C regenerated by the native `lean`, runtime
  `.cpp` compiled, mimalloc linked) do not depend on wasm. Only the compiler
  (`emcc`/`em++`) and flags such as `-fwasm-exceptions` do.
- The C ABI in `formal/lean4/Wasm/l4_shim.c`: `l4_init`, `l4_call_c`,
  `l4_call_blob_c`, `l4_call_blob_io_c`, `l4_free_result`, `l4_free_blob`.
  Every op of `Wasm/Dispatch.lean` is reachable through `l4_call_c`, so one
  wrapper per language covers the whole engine.
- Lean native executables (`l4sbm11`, `l4xmpp-serve` and others) build on
  Linux and macOS through Lake. They show that the Lean C output and the
  runtime run natively on arm64, with threads and Lean's own file I/O.
- `docs/designissues/2026-10-29-wasm-components.md` lists 14 changes that the
  Lean runtime needed under WASI. Some apply to any new target (exceptions,
  libuv, threads).

## 3. Targets

| Target triple | Use | Library form |
| --- | --- | --- |
| `arm64-apple-ios` | iPhone and iPad devices | static `.a` in an XCFramework |
| `arm64-apple-ios-simulator` | simulator on Apple silicon | static `.a`, separate XCFramework slice |
| `aarch64-linux-android` (ABI `arm64-v8a`) | Android devices | `libl4factoidal.so` in an AAR |
| `x86_64-linux-android` | Android emulator in CI | `libl4factoidal.so` in an AAR |

32-bit Android (`armeabi-v7a`) is left out. The wasm32 build shows that Lean's
C runs at 32 bits, so this target can be added if a device needs it.

Android needs a shared library, because JNI loads `.so` files. The link uses
`-Wl,-z,max-page-size=16384`, because Google Play requires 16 KB page
alignment for native libraries on Android 15 and later. iOS: the static
library goes into the app binary. The minimum iOS version is a decision
(section 9).

## 4. The build, per target

The order is the order of `build-wasm.sh`. The compiler changes.

1. `lake build` of the library, which writes our modules' C into
   `.lake/build/ir/`. This is unchanged.
2. Get the lean4 runtime sources by a sparse checkout at the toolchain tag,
   then write `lean/config.h`. Keep the wasm choices that do not depend on the
   target: no GMP (`runtime/mpn.cpp`), `LEAN_MIMALLOC` defined and mimalloc
   linked. The skill records the cost of dropping mimalloc.
3. Regenerate the core library C with the native `lean`. This C does not
   depend on the target, so one copy serves all four targets and the wasm.
4. Compile with the target's clang: Xcode clang with
   `-target arm64-apple-ios<ver>` and the iOS SDK sysroot, or the NDK clang
   (`aarch64-linux-android<api>-clang`). Use `-O3 -DNDEBUG`. Use native C++
   exceptions (the default), not `-fwasm-exceptions`.
5. libuv: start as the wasm build does. Compile no `libuv.cpp` or `uv/*.cpp`,
   and keep the `initialize_libuv` stub (`Wasm/l4_stubs.c`). The host then
   does all network and timer I/O, and the native answers match the wasm.
   libuv builds for both platforms, so the stub can go if a Lean-side socket
   is needed later.
6. Initialisation: `l4_init` calls `lean_initialize_runtime_module()`, as in
   the wasm. Lean tasks (threads) are possible natively. They are not used
   until a differential test covers an op that uses them.
7. Link. iOS: `libtool -static`, then `xcodebuild -create-xcframework` over
   the device and simulator slices. Android: `clang -shared` with a small JNI
   C file (`l4_jni.c`), then the AAR.

A size table per target goes into the record when stage 2 lands. Each target
gets the same map-based table as `tools/wasm-size-profile.py`.

## 5. The ABI on each platform

The ABI is the C ABI of `l4_shim.c`, unchanged. The ownership rules are those
of the skill (§ The C ABI and its memory rules): every `char *` result is
released with `l4_free_result`, and every `uint8_t *` output with
`l4_free_blob`.

- **Swift.** A Swift package with a C module map over `l4_shim.h`, and one
  type with `call(op:args:) throws -> String`, `callBlob` and `callBlobIO`
  (`Data` in and out). The Swift code parses no RDF and decides nothing. It
  moves strings and bytes.
- **Kotlin.** The JNI functions in `l4_jni.c`, with `external fun` in one
  Kotlin object. `String` and `ByteArray` cross the boundary.
- Threads: the Lean runtime is called from one thread at a time until a test
  shows that it is safe to do more. The wrappers hold a lock on that thread,
  which is the wasm model.

## 6. Tests

- **Differential test (stage 3).** One corpus of `(op, args, blob)` cases
  runs through the wasm under Node and through the native library on the iOS
  simulator and the Android emulator. The answers must be the same bytes. The
  corpus comes from the existing op tests (`Wasm/*Tests.lean` cases, and the
  npm tests that call `l4_call`). This follows the C primitive rule of
  CLAUDE.md: the same function, a differential test on every target.
- **Gates for the mobile set:** library init, `version`, one parse, one
  query, one SHACL validation, one blob op, and the full corpus
  (simulator/emulator only).
- **CI:** a `mobile` set in `danbri/factoidal-builds`. The macOS runners have
  Xcode and the iOS simulator. The Linux runners can run the Android emulator
  with KVM. This set does not start until the 0.21.0 release closes
  (https://github.com/danbri/factoidal/issues/1148), by the one-owner rule.

## 7. Host I/O and safety

- Iron rule 7 applies: Swift and Kotlin code does I/O only. App sandbox
  files, the network (URLSession, OkHttp or `HttpURLConnection`) and the
  clock are host realisations. RDF, SPARQL, IRI and datatype decisions are in
  Lean.
- Network reads give the retrieval record of
  https://github.com/danbri/factoidal/issues/1035 (headers, redirects, TLS
  details, body SHA-256, credentials removed). Each platform's network API
  exposes a different subset of the TLS fields. The record names the fields
  that the platform did not give. It does not fill them with defaults.
- Servers: iOS suspends an app in the background, so a listener stops. On
  Android, a long-running listener needs a foreground service. A server on a
  phone listens only on loopback, unless an option that starts with
  `--dangerously-` (or the platform equivalent) is set. The combinations of
  https://github.com/danbri/factoidal/issues/1120 apply.
- The experimental code notice of CLAUDE.md is shown in the sample app and in
  each package README.
- Encryption at rest for a storage on the device: the iOS Data Protection
  class and the Android Keystore are the key sources. Each is a host
  realisation and is named in the at-rest notice.

## 8. Graphics from Lean

Lean has no graphics output of its own. ProofWidgets draws in the editor's
infoview, not in an app. The rule follows iron rule 7: **Lean decides what to
draw (layout, geometry, colour, the scene). The host only puts the result on
the screen.** There are three output forms, and each one can cross the ABI as
it is.

| Form | What Lean emits | What the host does | Fits |
| --- | --- | --- | --- |
| (a) SVG text | an SVG document, through the Lean XML writer | web and web view: show it as it is. iOS and Android native have no full SVG renderer, so (b) | static charts, diagrams, documents |
| (b) display list | a Lean inductive of draw commands (path, fill, stroke, text run with a font id, image, clip, transform), as bytes through `l4_call_blob_io_c` | one small interpreter per platform: Canvas 2D, Core Graphics, `android.graphics.Canvas` | interactive views, all platforms |
| (c) RGBA pixels | a framebuffer rasterised in Lean | copy it to the screen: `putImageData`, `CGImage`, `Bitmap.copyPixelsFromBuffer` | the same pixels on every platform; thumbnails; the reference for tests |

Notes:

- **Text** needs font metrics and shaping. For layout in Lean, the host gives
  the metrics of its fonts as an input, which is an assumption named in the
  evidence record. Otherwise Lean emits text runs and the host lays them out,
  and Lean does not know the final positions.
- **PNG output** for (c): `Codec/Crc32.lean` exists. A zlib stream of stored
  (uncompressed) blocks needs no compressor, and Adler-32 is a few lines.
  `Codec/Inflate.lean` can read the result back for a round-trip theorem.
- **Theorems** that the forms allow: every command of a display list is
  inside the viewport, the paths are closed where a fill needs it, and colour
  pairs meet a WCAG contrast ratio. Another theorem: (c) is the rasterisation
  of (b), so the host renderer can be tested against Lean's pixels within a
  stated tolerance.
- **GPU** (Metal, Vulkan, WebGPU): the GPU API stays in the host. Lean can
  emit vertex and index buffers and uniform values as bytes, and shader text
  (WGSL, or MSL for Metal). A redraw on every frame through the string ABI is
  too slow, so it uses the blob ABI. The cost per frame is to be measured
  before any claim.
- **Proposed order:** (b) first, with (c) as its reference rasteriser in
  Lean, then (a) where a vector document is the product. A Lean layout or
  rendering engine needs the same host boundary.
