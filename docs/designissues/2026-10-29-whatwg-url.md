### How the parser is written

The basic URL parser is the standard's state machine, transcribed. One
`Id.run do` block holds url, state, buffer, the three flags and pointer as
mutable variables. A `for` loop runs one state per round. "Decrease pointer by
1" and "start over" are pointer arithmetic, as in the standard. The loop has
fuel `8 × (input length + 2)`. The scheme state starts over at most once, the
authority state rewinds at most once, and every other rewind is one code
point, so the fuel is enough. If the fuel ends, the result is failure. The
self-test parses inputs of 1,000,000 code points of each shape that rewinds,
under a 1 MB stack.

With a state override the standard changes url in place, and it can return
failure after some changes. `ParseResult.failure` therefore carries url as it
is at that point. The setters use that url, as the standard does.

The path state's rule for one segment is a separate function,
`Url.pathSegment`, so that a theorem can state it.

Validation errors are not reported. They do not change the result.

### The domain parser

The 19 October 2026 text renamed "domain to ASCII" to the "domain parser" and
changed one rule. With beStrict false, an ASCII domain is lowercased and is
not checked by UTS #46. The standard gives web compatibility as the reason
(`xn--8i7caa` decodes to `ｗｗｗ`, whose code points are mapped). The first run
of this runner used the older text: 800 tests failed, all of them on ASCII
input. With the new text, 0 fail.

### What is not in Lean

- The `<a>` and `<area>` element URL attributes (HTMLHyperlinkElementUtils)
  need an HTML document: https://github.com/danbri/factoidal/issues/1187.
- A blob URL entry is never present, so the origin of a `blob:` URL comes from
  its path, as the standard says when the entry is null.
- `URLSearchParams` is only its serializer, as the `searchParams` attribute of
  `urltestdata.json` reads it. The WPT `urlsearchparams-*.any.js` files are not
  vendored.
- NFC in UTS #46 uses the Unicode 16.0.0 tables of `XPath4.Unicode`. A
  character that is new in 17.0 or 18.0 and has a canonical decomposition is
  not decomposed. No WPT case reaches this.
- No wasm or npm operation exposes the parser yet.

## Theorems

`WHATWG/URL/Theorems.lean` (URL Standard `845bafca`; RFC 3986 §5.2.4 as
`L4Factoidal.Syntax.removeDotSegments`, the RFC 3986 resolver of the Lean
tree, `Syntax/IriResolve.lean`). `#print axioms`: `propext`,
`Classical.choice`, `Quot.sound` only.

- `pathSegment_segments`: on a URL whose scheme is not "file", `Url.pathSegment`
  acts on the segment list as `segRule`. `segRule` shortens the list on `..`,
  does nothing on `.`, and appends any other segment; a dot segment at the end
  appends the empty segment.
- `rfc3986_removeDotSegments_eq_whatwg`: for `/s1/.../sk` (k ≥ 1, no `/` in a
  segment), `removeDotSegments` gives the URL path serialization of
  `wpFold [] [s1, ..., sk]`.
- `whatwg2026_path_eq_rfc3986`: the two composed. Fold `Url.pathSegment` over
  the segments, from a non-file URL with an empty path. The path serialization
  is `removeDotSegments ("/" ++ "/".intercalate segs)`.

The hypothesis `ReadAlike` says that the two standards read the segment the
same way: a segment is a WHATWG single-dot (double-dot) segment exactly when it
is `.` (`..`). The URL Standard reads `%2e`, `%2E` and their combinations as
dots, and RFC 3986 does not. (RFC 3986 section 2.3 lets a normalizer decode
`%2E` before resolution; `removeDotSegments` does not.)

The proof is a simulation. The output list of RFC 3986's loop (`rfcOut ws`)
holds the root `/` and each WHATWG segment with its `/`, newest first. Each
segment step keeps the relation, and the end of the input gives the same
string.

Not proved: the statement for the whole parser. For a base that is the href of
a parsed http(s) URL and a reference that both read alike,
`(parseUrl ref base).href = resolveIri base ref`. It is measured instead
(above) and tracked in https://github.com/danbri/factoidal/issues/1188. "Read
alike" for a reference means: no scheme, no authority, and no code point that
the URL Standard percent-encodes, decodes or reads as a separator in a special
URL (`%`, `\`, space, `"`, `<`, `>`, `^`, `` ` ``, `{`, `}`, `|`, `'`,
non-ASCII).

## Performance

⚠️ On the 896 cases of `urltestdata.json`, 100 rounds, 4-vCPU VM: Lean
`l4whatwg-url bench` 1691 ms (with base and input parse, all 12 getters and
the hex answer). Node 22.22.0 `new URL` (ada) 306 ms. The Lean code has no
optimisation yet: https://github.com/danbri/factoidal/issues/1189.

## Reuse

- Percent-encode sets, percent-encode after encoding, percent-decode, the
  encodings and UTF-8 decode without BOM: milestone 2 (`WHATWG/Encoding`,
  `WHATWG/URL/PercentEncode`).
- NFC: `XPath4.Unicode.normalize`.
- RFC 3986 resolution: `Syntax.IriResolve` (no second resolver).
- The UTF-8 bytes of a code point: Lean core `String.utf8EncodeChar`, which
  milestone 2 proved equal to the Encoding Standard's UTF-8 encoder.
