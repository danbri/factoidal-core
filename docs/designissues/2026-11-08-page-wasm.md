# The WebAssembly JavaScript API for page scripts, on WasmVM

Date: 2026-11-08. Author: pagewasm, a subagent of session depmap-0e.
Related: https://github.com/danbri/factoidal/issues/1244 (WasmVM engine). Records it joins:

## 1. Result

Page scripts have `WebAssembly`: `validate`, `compile`, `instantiate` (bytes, and a
`Module`), `Module` (`exports`, `imports`, `customSections`), `Instance`, `Memory` (`grow`,
`buffer`), `Table` (`length`, `get`, `set`, `grow`), `Global` (`value`, `valueOf`), `Tag`,
`Exception` (`getArg`, `is`), `CompileError`, `LinkError`, `RuntimeError`, on both script
engines (QuickJS-NG in WasmVM, and BubblePopJS). `compileStreaming` and
`instantiateStreaming` are defined only when the page has `fetch` and `Response`; it has
neither today, so they are undefined. The type reflection proposal's `type()` and
`minimum` are there too.

`WebAssembly` is an accessor on the window until its first read, which runs
`tools/wasmvm/quickjs/webassembly.js` (31 KB) and replaces it with the data property WebIDL
asks for, so pages with no WebAssembly never load it. The QuickJS guest holds it as bytecode
compiled at guest build time, as the prelude (`prelude_bytecode.c`, now with a name
argument); BubblePopJS gets its source (`LeanJS.wasmGlue`). The one difference a script can
see is the property descriptor before that read.

No host WebAssembly engine runs a page module. Lean decodes it (`Binary.decode`),
validates it (`validate`, the same validator as the spec tests), links and instantiates it
(`instantiate`) and runs it (`invokeSteps`, `resumeSteps`) in WasmVM.

## 2. Parts

- `formal/lean4/L4Factoidal/WasmVM/Hosts/PageWasm.lean`: the page's WebAssembly. `State`
  holds the page store (a WasmVM `Store` of its own), the compiled modules, the runs that
  wait for a JavaScript function, the views of `Memory.buffer`, and the budgets (`Config`).
  `core` is every operation; `serve` is the import `foafnaut_dom.wasm_call` on top of it.
- `Hosts/Page.lean`: `Host.wasm` (empty until a script uses the API), `serveExtra` serves
  `wasm_call`, and the page module's instructions count as script time in `Session.run`.
- `Hosts/PageAot.lean`: the read table of `wasm_call` (the request and the view), so the
  Hub's translated QuickJS guest passes them with the call.
- `Hosts/LeanJS.lean`: BubblePopJS natives 24 (`wasm`) and 25 (`detach`) call the same
  `PageWasm.core`; `JS.HostAns` gained `bytes` (a new ArrayBuffer), `writes` (write into an
  argument's ArrayBuffer) and `detach`; `BigInt.asIntN` and `BigInt.asUintN` are new in
  BubblePopJS (the API's i64 conversions).
- `tools/wasmvm/quickjs/qjs_wasmvm_entry.c`: the import `wasm_call(op, handle, ptr, len,
  out, cap, view, viewLen)`, natives `n.wasm(op, handle, payload, view, text)` and
  `n.detach(buffer)`.
- `tools/wasmvm/quickjs/prelude.js`, section "WebAssembly (pagewasm)": WebIDL glue only:
  argument conversion (ToWebAssemblyValue, ToJSValue, `[EnforceRange]`), the interface
  objects, promises, and the loop that calls a JavaScript import when Lean asks for it.

## 3. How a call runs

`instance.exports.f(1, 2)` is op 5 with the function's address and the arguments' bits.
Lean runs the function on the page store. When the module calls a JavaScript import, WasmVM
stops the run (`Outcome.hostCall`); Lean keeps the paused run (`State.paused`, a stack) and
answers "call host function k with these values". The prelude calls the JavaScript
function and answers with op 6 (`resume`) and its results, or with "it threw"; the run goes
on. So:

- the script engine is never entered from Lean: no re-entrant call into QuickJS or
  BubblePopJS, and a page module never runs while a script runs;
- a JavaScript import may call back into WebAssembly (a nested op 5): the paused runs are a
  stack, at most `Config.depth` deep;
- an exception a JavaScript import throws ends the WebAssembly run as a trap; the prelude
  rethrows the same JavaScript value. WebAssembly code can not catch it (a limit, below);
- an exception a module throws and does not catch reaches JavaScript as a
  `WebAssembly.Exception` with its tag and payload.

## 4. Sandboxing and budgets

- One page store per page session, inside the page's host state: a page's modules can
  share memories, tables, globals and functions only through imports and exports, as the
  specification says, and nothing outside the page can name them.
- The page store and the script engine's memory are different Lean values. The only way
  between them is `wasm_call`. `PageWasm.serve_writes` proves what one call can do to the
  script engine's memory: only writes inside its answer buffer `[out, out + cap)` and its
  view `[view, view + viewLen)` (`Writes`, a chain of in-range `writeMem`). It holds for
  every op and whatever the page's modules do.
- Inside the page store, every load and store of a module is checked against its own
  memory: the `LinearMemory` operations take the proof `ea + w ≤ size`, and the loop makes
  the one check (`Exec/Run.lean`, `Bytes.nat_ok`; the refinement cases `case_load`,
  `case_store`, `storeS_mems` in `Proofs/RefineRun.lean`); table accesses are checked
  against the table's size (`tableOOB`). A module reaches only the memories, tables and
  globals of its own instance (its index spaces map to store addresses at instantiation).
- Budgets (`PageWasm.Config`): 4 G instructions for one call from JavaScript (the calls back
  into JavaScript included; out of fuel is a `RuntimeError`); at most 1024 pages (64 MiB) a
  memory, and 4096 pages (256 MiB) for all the page's memories together: a new memory, an
  instantiation and a call are refused while the memories hold more (a module can still
  grow each of its own memories up to 64 MiB inside one call); 64 MiB a module and 256 MiB
  of modules in all; views of at most 64 MiB; 1000 nested calls; tables of at most 10 M
  elements. Nothing a page compiles is freed before the page ends (no garbage collection
  across the boundary). The page module's instructions count in the page's script clock
  (`Session.run`, `LeanJS.Session.run`).

## 5. Memory.buffer

`Memory.buffer` must be an ArrayBuffer the script reads and writes, coherent with the
module's memory. The memory is a `ByteArray` in the page store; the ArrayBuffer is in the
script engine's heap (QuickJS: its linear memory; BubblePopJS: a `ByteArray` in its heap).
A window of one into the other is not possible: WasmVM memories are separate values, and a
Lean `ByteArray` held twice is copied at the next write. So the mechanism is
copy-on-boundary with change detection, the same Lean code for both engines:

- On first `buffer` read the prelude makes an ArrayBuffer of the memory's size; Lean writes
  the memory's chunks that are not zero (op 11) and keeps a shadow: the bytes the script's
  copy holds.
- At each boundary, only while a buffer is live: before a run (op 5, op 6) Lean reads the
  view and compares it with the shadow (one `memcmp`, `ByteArray.beq`); when they differ,
  the 4 KiB chunks that changed go into the memory. After the run it compares the memory
  with the shadow; changed chunks go to the view. Nothing is copied when nothing changed,
  except the read of the view.
- A memory whose size changed (`grow` from JavaScript or `memory.grow` in the module) drops
  its view; the prelude detaches the old ArrayBuffer (`n.detach`, QuickJS
  `JS_DetachArrayBuffer`; BubblePopJS `HostAns.detach`) and the next `buffer` read makes a
  new one, as the API's "refresh the memory buffer".
- A page that never reads `buffer` pays nothing; a page with no WebAssembly pays nothing.

Cost per call with a live buffer of S bytes: one read of S bytes from the script engine's
memory, two compares of S bytes, and the changed chunks. Measured below.

A page module runs on the WasmVM interpreter at the same speed as the QuickJS guest itself
(about 200 M Wasm instructions a second natively). The call path is dominated by the
script engine (QuickJS in WasmVM spends about 4 k instructions on one JavaScript call);
Lean's side of a call is a few microseconds. With a live buffer the cost grows with the
memory's size: about 0.17 ms a MiB a call natively.

On the Hub the QuickJS guest is translated (AOT); `wasmvm-bench page --aot` runs every probe
page and the demo the same way (`"aot":"same"`: logs, commands, clock, body), with the
page's modules still on Lean's interpreter.

## 8. Limits

- A JavaScript exception thrown into WebAssembly ends the run; `try_table` with `catch_all`
  in the module does not see it (the API says it should, as an exception with `JSTag`).
  A `WebAssembly.Exception` thrown by an import is the same. `WebAssembly.JSTag` is not
  defined.
- `exnref` values do not cross to JavaScript (a `TypeError`, as the API says); an
  exception from WebAssembly keeps its tag and payload, not its identity.
- No `shared` memory, no memory64 or table64 descriptors, no type reflection (`type()`),
  no GC types at the boundary (`anyref` and friends are a `TypeError`), no SIMD values
  (`v128` is a `TypeError`, as the API says; WasmVM has no SIMD).
- The ArrayBuffer of `Memory.buffer` can be detached by the script (`transfer`), which the
  API forbids.
- Compilation is synchronous inside the promise job of `compile` and `instantiate`.
- BubblePopJS: strings are code points, so a module name with a lone surrogate differs.
