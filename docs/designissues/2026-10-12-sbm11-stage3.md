## 2. Formats

All integers little-endian. Code: `formal/lean4/L4Factoidal/Storage/Sbm11/`
(`Column.lean`, `Block.lean`, `Manifest.lean`).

Rows and permutations. A quad is `(s, p, o, g)` of 64-bit ids (stage 2;
`g = 0` is the default graph). Permutation PSO (code 0) stores `(p, s, o, g)`,
POS (1) `(p, o, s, g)`, SPO (2) `(s, p, o, g)`, OSP (3) `(o, s, p, g)`, each
strictly increasing in the lexicographic order of the four ids.

Column frame (`Column.frameBytes`): one codec byte, then

    0 constant  value u64                       every row has this value
    1 raw       value u64 per row
    2 delta     varint(zz(prev, v)) per row     prev = 0 before the first row
    3 zstd      reserved; refused by the decoder in stage 3

`zz prev v = 2 (v - prev)` when `prev ≤ v`, else `2 (prev - v) - 1`. A
varint is 7-bit groups, most significant first, bit 7 set on every byte but
the last. The encoder writes 0 when all values are equal, else 2 when the
delta bytes are fewer than `8 × rows`, else 1. The choice is part of the
format: activation re-encodes every column and compares bytes.

PRB1 (`<perm>.prb1`): `"PRB1" 0x01 perm`, then per block four frames
(`c0`, `c1`, `c2`, `g`).

PRM1 (`<perm>.prm1`): `"PRM1" 0x01 perm blockCount:u64 rowCount:u64`, then
92 bytes per block: first row 4 × u64, last row 4 × u64, rows u32, offset
in PRB1 u64, the four frame lengths 4 × u32. Admission (`prmAdmitted`, the
same predicate in the encoder and the decoder): `perm < 4`; each block 1 to
`2^32 - 1` rows, `first ≤ last`; the last row of a block below the first row
of the next (sorted, no overlap); the first block at byte 6 of PRB1, each
next block where the previous ends; `rowCount` the sum.

Blocks: at most B rows (default 4,096). A block also ends at a change of
`c0` when it holds B / 16 rows or more, so a predicate (PSO, POS) or a
subject (SPO) with many rows starts its own block.

SBM11 manifest (`manifest.sbm11`): `"SBM0" 0x0B` (the SBM magic with wire
version 11; SBM0 to SBM10 readers refuse it), the layout label string
`sbm11-gdv1-gdx1-prm1-prb1-pso-pos-spo-osp-merkle-v1`, source length u64,
source SHA-256 (32 bytes), quads u64, dictionary terms u64, artifact count
u32, then per artifact: role string, file name string, length u64,
SHA-256, chunk bytes u32, chunk count u32, Merkle root (32 bytes). Strings
are u32 length and UTF-8 (`ShardManifest.encodeString`); the Merkle
reference is `ChunkedArtifact.Ref` with 65,536-byte chunks
(`ShardManifest.encodeChunkedRef`). The roles are exactly `GDV1`, `GDX1`,
`PRM1-PSO`, `PRB1-PSO`, `PRM1-POS`, `PRB1-POS`, `PRM1-SPO`, `PRB1-SPO`,
`PRM1-OSP`, `PRB1-OSP`, in that order. Each file has a `<file>.merkle`
sidecar of 32-byte leaves; a reader uses a leaf only through a proof to the
manifest root (`PosixRangeIO.readVerifiedRangeCached?`). `CURRENT` is the
existing generation pointer (`GenerationPointer.activateGeneration`).

GDV1 and GDX1 are the stage 2 files, unchanged: the stage 3 packer writes
byte-identical dictionaries (`dict.gdv1` sha256 `bd3e8854…f300e9bf`,
`dict.gdx1` `fdd85d96…f20627c` on olympics, the stage 2 values).

## 3. Theorems

`#print axioms` of each: `propext`, `Classical.choice`, `Quot.sound` or a
subset.

| Theorem | Statement |
| --- | --- |
| `Column.get64_put64`, `get32_put32` | fixed-width fields below `2^64`, `2^32` |
| `Column.getVar_putVar` | the varint of any `n` |
| `Column.unzz_zz` | the zig-zag difference |
| `Column.decodeColumn_encodeColumn?` | `encodeColumn? xs = some bs → decodeColumn xs.length (bs ++ rest) = some (xs, rest)` (the only hypothesis) |
| `Column.decodeColumnAt_eq` | the runtime decoder over a `ByteArray` (into an `Array Nat`) equals `decodeColumn` on every input |
| `Block.decodeBlock_encodeBlock?` | `encodeBlock? off rows = some (m, bs) → decodeBlock m bs = some rows` |
| `Block.decodeBlock_bounds` | a decoded block has `m.rows` rows, strictly increasing, the first is `m.first`, the last `m.last` |
| `Block.encodeBlock?_bounds` | the PRM1 entry the encoder writes holds the block's first and last row and its row count |
| `Block.decodePrm_encodePrm?` | `encodePrm? perm ms = some bs → decodePrm bs = some (perm, ms)` |
| `Block.decodePrm_admitted` | a decoded PRM1 is admitted (sorted, no overlap, contiguous) |
| `Manifest.decodeManifest_encodeManifest?` | `encodeManifest? m = some bs → decodeManifest bs = some m` |
| `Manifest.decodeManifest_admitted` | a decoded manifest is admitted |

Tested and not proved (2026-10-12 update: block skipping is now proved,
`ScanTheorems.blocksFor_complete`, and what `decodeBlockAt` admits,
`BlockAtTheorems.decodeBlockAt_ok`; see
[`2026-10-12-sbm11-end-to-end-theorem.md`](2026-10-12-sbm11-end-to-end-theorem.md)):

- `Column.encodeColumnFast` (the packer's encoder over `Array Nat`) is not
  proved equal to `frameBytes`. The packer decodes every frame it writes
  (`decodeColumnAt`, proved equal to the spec decoder) and compares the
  column; activation re-encodes every decoded column and compares bytes;
  `#guard`s compare it with `frameBytes` on seven columns.
- `Block.decodeBlockAt` (runtime) decodes the four frames with
  `decodeColumnAt` and checks first row, last row and order with its own
  loop (`colsSortedGo`), not proved equal to `decodeBlock`; the tamper cases
  of `stage3_check.sh` and the `#guard`s exercise each check.
- Block skipping (design section 6.10: a block whose key range excludes a
  prefix holds no row with that prefix) is not stated; `scan` and `count`
  rely on it, and `count` of every row and of the q03 prefix equals the
  dump and the scan.
- The four permutations denote one quad set: checked at pack and at
  activation (digest), and by `dump-ids`; no theorem over the packer.
- `zstd` frames (tag 3) are not written and are refused.

## 4. Packer (`Harness/Sbm11Pack.lean`)

`l4sbm11-pack SOURCE OUTDIR [--workers K] [--run-terms N] [--block-rows B] [--sort-rows M]`

1. Four tasks parse byte ranges of the source (stage 2). Each gives the
   distinct non-inline terms of its batch a local number (a hash map of at
   most N / K terms) and keeps the batch's quads as four slots: 0 (default
   graph), `1 + local number`, or an inline id. A full batch writes a term
   run (sorted keys, the stage 2 run format) and a quad run (32 bytes per
   quad, local numbers replaced by the key's rank in the run). A fifth task
   hashes the source.
2. The k-way merge of the term runs writes GDV1/GDX1 as stage 2 and, per
   run, a remap file: the global id of each key of the run, in run order.
3. Each quad run is mapped to global ids through its remap (at most N / K
   ids in memory) and goes to four row buffers. A full buffer (M rows) is
   sorted, by four tasks in parallel, and written as a row run (32 bytes per
   row). Four tasks then merge their permutation's row runs, drop duplicate
   rows, and write PRB1 and PRM1. Then every file is hashed (SHA-256 by the
   HACL* block fold, Merkle leaves) and the manifest is written.

Phase times on olympics (2026-10-12): phase 1 17.5 to 18.0 s, phase 2 3.7 s,
phase 3a (remap, buffers, sorts) 15.5 to 16.6 s, phase 3b (merge, blocks)
1.6 to 2.0 s, hashing and manifest 1.2 to 1.4 s. Temporary disk: about 57 MB
of quad runs and 228 MB of row runs.

The first version took 9.6 s in phase 2: `remaps.set! k (pushW remaps[k]!
id)` reads the buffer out of the array while the array still holds it, so
`push` copied the whole buffer for every key. `Array.modify` (which takes
the element out first) made it 3.7 s. This is the same defect stage 2
recorded for the hash set in the parser's fold accumulator: a value that is
still referenced when it is updated is copied.

### 4.1 Phase 2 was quadratic in the distinct terms (issue 804)

https://github.com/danbri/factoidal/issues/804 (owner, 2026-10-12: "804
yes"). Measured before: olympics 543,967 terms, phase 2 3.4 s; DBpedia
slice 8,877,307 terms, phase 2 799 s of a 1,334 s pack (16.3 times the terms,
234 times the time).

Cause. The merge took each record by comparing the heads of all k term
runs, and k grows with the source: a phase 1 run holds at most run-terms /
workers terms (65,536 by default), so k is about the number of run records
divided by 65,536 (12 runs on olympics, 121 on 8 million records). The cost
is records times k. Evidence: gdb stack samples of the phase 2 thread on a
synthetic source of 4 million lines (121 runs): 11 of 12 samples in the head
scan loop, 9 of them in `cmpBytesLoop`. Phase 3b (the merge of the row runs
of one permutation) and `l4sbm11-dict-pack` phase 2 had the same scan.

Fix (`Harness/RunHeap.lean`, `L4Factoidal/Qlvr/CmpBytesFast.lean`):

1. A loser tree (tournament tree; Knuth, TAOCP vol. 3, section 5.4.1) over
   the run numbers selects the next record: one comparison per level, about
   log2 k per record. Ties go to the smaller run number, the order of the
   old scan. Used by packer phase 2, phase 3b and `l4sbm11-dict-pack`.
2. The tree takes a three-way comparison; a `<` test needed two key
   comparisons when the heads were not in order. Phase 2 also takes one
   comparison per record (not two) for the duplicate and order checks.
3. `cmpBytesFast` skips equal 8-byte words (`ldU64LE`, one load) and ends
   with the byte loop of `cmpBytes`. Theorem `cmpBytesFast_eq` proves it
   equal to `cmpBytes` at every input; `@[csimp] cmpBytes_eq_cmpBytesFast`
   makes the modules that import it (the packer, `l4sbm11-dict-pack`) call
   it. `cmpBytes` stays the specification. Axioms: propext, Quot.sound.
   After step 1, gdb samples put about one third of phase 2 in
   `cmpBytesLoop`: the run heads share long prefixes (`http://...`).

Output is byte-identical to the previous packer: every file of the
generation on the gate fixture (default options, and `--workers 2
--run-terms 6 --sort-rows 5`) and on olympics (21 files); GDV1, GDX1 and the
12 remap files of olympics (`--phase2-only`); GDV1, GDX1 and every remap
file of the synthetic sources at 32, 62, 121, 124, 244 and 417 runs;
`l4sbm11-dict-pack` GDV1 and GDX1 on olympics; all 21 files of the DBpedia
slice generation against the generation of the benchmark record
(`/home/user/bench-data/sbm11/dbpedia`, packed by commit 408898bd; the packer
code did not change between that commit and this work).

Scaling test (`tests/sbm11/phase2_scaling.sh`, part (k) of
`tests/sbm11/run.sh`). `l4sbm11-pack --phase2-only` runs phases 1 and 2,
keeps GDV1, GDX1 and the remap files, and prints `phase2-ms` and (Linux)
`phase2-cpu-ms`, the CPU time of the merge thread. The test packs synthetic
sources of 1, 2 and 4 million lines (`tests/sbm11/gen_distinct_terms.py`)
with `--run-terms 32768` (244, 417 and 836 runs), three times each in rounds
of n, 2n, 4n, and fails when the median at 4n exceeds 4.84 times the median
at n (2.2 per doubling over the two doublings).

With N = 500,000 and `--run-terms 32768`, the previous packer took 7,842,

## 5. Codec decision and block size

The stage 3 size target is met without zstd. Codecs 0, 1 and 2, measured on
olympics (column bytes `c0, c1, c2, g`):

| Permutation | blocks | PRB1 bytes | column bytes | frames const / raw / delta |
| --- | ---: | ---: | --- | --- |
| PSO | 440 | 3,838,384 | 16,250; 1,785,754; 2,032,414; 3,960 | 909 / 0 / 851 |
| POS | 440 | 3,568,326 | 16,250; 1,270,125; 2,277,985; 3,960 | 1,004 / 0 / 756 |
| SPO | 6,902 | 13,888,587 | 1,843,741; 2,376,629; 9,606,093; 62,118 | 6,903 / 2,223 / 18,482 |
| OSP | 2,444 | 3,270,615 | 794,135; 2,295,105; 159,373; 21,996 | 5,243 / 0 / 4,533 |

With B = 16,384: 34,430,273 bytes (1 % smaller; PRM1 256,860 against 940,880
bytes), and every block read is 4 times larger. B = 4,096 is the default:
q03 reads one block of 18,664 bytes.

SPO `c2` (the object of each subject and predicate) is 9.6 MB of the 24.6 MB
of PRB1: the objects of one subject are ids of different classes (IRI,
literal, inline integer: tags 2, 3, 4), so the difference between
neighbours is near `2^60` and the delta varint is 9 or 10 bytes; 2,223 SPO
frames are raw. The design record's estimate for zstd frames (section 6.4)
was 2.2 times smaller than its delta estimate. A zstd encoder in Lean, or a
codec that codes the tag and the payload apart, is the way to reduce it; it
is not needed for the stage 3 target.

## 6. Reader and activation (`Harness/Sbm11Gen.lean`, `Harness/Sbm11Cli.lean`)

`l4sbm11 stats|scan|count|dump|dump-ids|canon|verify|activate|reseal`
(usage in the module header and in skill `shardborough-storage`).

- `scan GEN PERM KEY...` binary-searches the PRM1 entries for the first
  block whose last row is not below the prefix and reads blocks while their
  first row is not above it. Each block is one verified positioned read of
  its four frames.
- `count GEN PERM KEY...` adds the PRM1 row count of each block whose first
  and last row both carry the prefix (sorted rows between them carry it too)
  and reads only the other blocks.
- `activate ROOT NAME`: the manifest decodes and is admitted; each file has
  the manifest's length, SHA-256 and Merkle root, and its sidecar the same
  leaves; the dictionary keys are strictly increasing and their count is the
  manifest's; each PRM1 decodes and its PRB1 ends where the last block ends;
  each block decodes, is sorted between its PRM1 first and last row, and its
  frames are the encoder's frames; each id has a known tag, a rank below the
  term count, an IRI predicate, an IRI or blank-node subject, a default,
  IRI or blank-node graph; the four permutations have the manifest's row
  count and the same quad digest (sum and xor of a 64-bit mix of each quad).
  Then `CURRENT` is written. Measured: 1.2 s files, 0.8 s dictionary, 4.4 s
  blocks; peak RSS 86 MB.

## 8. What Lean taught

- `rw`, `simp only` and `dsimp only` did not return (memory exhausted after
  240 s) on the manifest round trip when the goal held the decoder's later
  `match` arms and the admission `if` with `two64` (a reducible literal) in
  it. Bisected with one `sorry` per step in a scratch file through
  `lake env lean`: `rw [← h32]` with `h32 : _ = 32`, `simp only` with the
  `takeExact` lemma, and `dsimp only` after it each hang. What returned:
  `takeExact_of_length` by `rw`, then `split` on each `match` with the
  equation in the hypothesis, and the decoder cut into a field decoder
  without an `if` and an admission function. Recorded in skill
  `lean4-proof-patterns` section 4.
- `structure ... deriving BEq` gives a `BEq` that is not `LawfulBEq`, so
  `beq_iff_eq` does not apply; `DecidableEq` alone gives the lawful one.
- `obtain` with one more `⟨` than the `∧` nesting fails with a dependent
  elimination error on the first conjunct, not a count error.
- An `Array Nat` of ids below `2^63` holds scalars, no allocation per value,
  and its proofs are over `Nat`; the codecs use it in place of `Array UInt64`.
