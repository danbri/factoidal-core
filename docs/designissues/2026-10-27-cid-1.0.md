# Controlled Identifiers v1.0 in Factoidal (2026-10-27)

Issue: https://github.com/danbri/factoidal/issues/1100 (CID 1.0: one Lean
module; VC Data Integrity and the LWS CID suite to use it).
Specification: https://www.w3.org/TR/cid-1.0/ (W3C Recommendation, 15 May 2025).

## What is where

| Lean module | Specification |
|---|---|
| `L4Factoidal/CID/Multiformats.lean` | §3.1 Base Encode, §3.2 Base Decode, §2.4 Multibase (`z`, `u`), §2.5 Multihash, the §2.2.2 Multikey header tables |
| `L4Factoidal/CID/Document.lean` | §2 data model: `parseDocument`, one `DocError` per MUST; §2.2.1–§2.2.3 verification material; §2.3 `relationship`; §2.2 `methodInForce`; §4.2 context, §4.2.1 context injection, Appendix A media type |
| `L4Factoidal/CID/Retrieve.lean` | §3.3 Retrieve Verification Method, §3.4 Fragment Resolution, §3.5 Processing Errors (with the RFC 9457 object) |
| `L4Factoidal/CID/Tests.lean` | the examples of the Recommendation, one negative case per MUST of §2 and per §3.5 error |
| `third_party/contexts/cid-v1.jsonld` | the §4.2 context, SHA-256 `ea216ecc…de85` as §4.2 states; never fetched at run time |

Users:

* `Authz/SubjectToken.lean` (lws10-authn-ssi-cid): `selectMethod` is §3.3
  with `authentication`, then §2.2 (`methodInForce`), then the JOSE key of
  the material (`materialJwk?`). `Authz/Theorems.lean` `cidKey_method` is
  now derived from `CID.retrieveFromDocument_sound`; `cid_valid_verified`
  is unchanged and still holds.
* `VC/DataIntegrity.lean`: `resolveKey` resolves `verificationMethod`
  through an Ed25519 did:key (as before) or through CID §3.3 with the
  relationship that `proofPurpose` names. `VC/Theorems.lean`
  `resolveKey_cid_document`.

## Theorems

* `CID.retrieveFromDocument_sound`: a method that §3.3 returns came from a
  conforming document whose `id` is the document URL; its absolute `id` is
  the requested URL; its absolute `controller` is the document URL; the
  requested relationship names it; it has no secret-key property.
* `CID.retrieveWith_ok`: the document was one the host fetched from that URL.
* `CID.resolveFragment_sound` (§3.4), `CID.documentUrlOf_url`,
  `CID.parseMethod_no_secret`, `CID.checkJwk_no_private`,
  `CID.decodePublicMultikey_length`, `CID.public_secret_headers_disjoint`,
  `CID.multihashDecode_length`.
* `Authz.cidKey_method` (restated over the module), `VC.DataIntegrity.resolveKey_cid`,
  `VC.DataIntegrity.resolveKey_cid_document`.

## Who fetches

The engine does no I/O (iron rule 7). `CID.documentUrlOf` names the
document; `CID.retrieveWith docs vmId rel` answers `need url` for a
document the host has not fetched. In the authorization server the fetch is
`Authz.lookup` (https only, every address of the host known before the
fetch, no private address unless `--allow-private-fetch`; record
`2026-10-22-authorization-server.md`). In `VC.DataIntegrity.verifyDocument`
the refusal `needDocument url` names the document and the caller passes it
back in `cidDocs`. No npm function exposes the VC path yet (item 9 of the
issue); when one does, it must use the same guard.

## Readings of the text (choices made here)

1. **`u` Multibase.** §2.4 says to apply §3.1 Base Encode with the
   base-64-url-no-pad alphabet. §3.1 is a big-number conversion; for base
   64 that is not RFC 4648 §5 (the one byte `ff`: §3.1 gives `D_`, RFC 4648
   gives `_w`). The Multibase draft and the Multikey implementations use
   RFC 4648. The module uses RFC 4648 for `u` and keeps `baseEncode` for
   the literal reading; `CID/Tests.lean` shows the difference. Question
   for the owner: report this to w3c/cid?
2. **Service `id`.** §2.1.4 says "Each service map MUST contain id, type,
   and serviceEndpoint" and then "The id property is OPTIONAL"; Example 6
   has no `id`. The module takes `id` as optional.
3. **URLs.** "Conforms to the URL syntax" is an RFC 3987 IRI reference
   (absolute or relative, not empty), resolved against the document `id`
   by RFC 3986 §5.2. The document `id` must be absolute (it is the
   canonical URL, §2.1.1). This is not a full WHATWG URL parser (WHATWG
   accepts some strings that RFC 3987 refuses, such as a backslash).
4. **Secret material.** A controlled identifier document is public, so
   `secretKeyMultibase` and `secretKeyJwk` are refused in it (§2.2.3
   "MUST NOT be used if the data structure containing it is public").
   The JWK private members refused in `publicKeyJwk`: `d`, `p`, `q`, `dp`,
   `dq`, `qi`, `oth`, `k`, `priv`.
5. **Multikey headers.** `publicKeyMultibase` of a `Multikey` must be
   base-58-btc with a public header of the §2.2.2 table and the length of
   that type; a secret-key header and an unknown header are errors (§2.2.2,
   "Implementations that adhere to this specification will raise
   errors"). `publicKeyMultibase` of another method type (for example
   `Ed25519VerificationKey2020` in DID documents) must only be Multibase.
6. **Controller of a method (§3.3 step 10).** The absolute `controller`
   must equal the document URL, as the algorithm says. Issue 1100 item 8
   says "or a declared controller"; §3.3 has no such case, so it is not
   implemented.
7. **A method identifier without a fragment** gives
   INVALID_VERIFICATION_METHOD (§3.4 needs a fragment).
8. **Defective examples.** Examples 12–17 have comments and `...`;
   Examples 29 and 35 lack a comma. The tests run them as printed (not
   JSON) and with only the defect removed. In Examples 29 and 35 the
   relationships name `https://controller.example/123#key-N` but the
   methods have ids under another host, so §3.3 finds no method.
9. **Lints, not errors.** The `kid` SHOULD of §2.2.3 (`kidConsistent`).
   Duplicate method ids are not refused (§3.4 note: the behaviour is not
   defined); Fragment Resolution takes the first in document order.

## Behaviour changes for the LWS CID suite

* The `Accept` header for the subject's document is now
  `application/cid, application/cid+json, application/ld+json, application/json`.
* The whole document is checked (§2). Before, only the method was read.
  A document that breaks a MUST of §2 elsewhere (for example a
  `secretKeyJwk`, or an `expires` without a time zone) is now refused.
* `expires` and `revoked` must be `dateTimeStamp` (with a time zone).
  Before, a time without a zone was read as UTC.
* A `kid` that names a method outside the subject's document is refused
  (lws10-authn-ssi-cid dereferences the subject's document).

## §5 Security Considerations

* **5.1 Proving control and binding.** Handled by the users: the
  authorization server checks the signature with the key §3.3 returned for
  `authentication`; the VC verifier with the key for the relationship of
  `proofPurpose`. Binding to physical identity is out of scope.
* **5.2 Identifier ambiguity.** Not handled; no code can decide what an
  identifier refers to. The verifiers report the identifier they checked.
* **5.3 Key and signature expiration.** `methodInForce now`: a method is
  not used at or after `expires` or `revoked`. The authorization server
  always passes its clock; `verifyDocument` checks only when the caller
  passes `now` (a verifier of an old signature may choose not to).
* **5.4 Verification method rotation.** Handled by fetching the current
  document: the authorization server keeps a document for `docTtl` seconds
  (default 60), then fetches it again. A method that is not in the latest
  document is not found (§2.3). No history of documents is kept, so a
  signature by a rotated key does not verify.
* **5.5 Revocation.** `revoked` is checked as in 5.3. 5.5.1: there is no
  record of past document states, so revocation counts from the present
  moment only (the "only safe course" of 5.5.1).
* **5.6 Choosing a Multiformat.** Only `z` and `u` Multibase; Multikey only
  with the §2.2.2 headers.
* **5.7 Encrypted data.** Not applicable; nothing is decrypted from a
  document.
* **5.8 Content integrity.** The §4.2 context is vendored with its SHA-256
  and never fetched. Other external links of a document are not followed.
  The documents themselves are not integrity protected beyond TLS.
* **5.9 Integrity of controllers.** The document `controller` property is
  parsed and returned, never followed: no change control is delegated by
  this code, and no remote document is pinned by hash. A method in another
  document is retrieved from that document (§3.3), never trusted from the
  document that refers to it.
* **5.10 Level of assurance.** Not handled.
* **5.11 Service endpoints for authentication.** The OpenID Connect suite
  uses the `service` of type `lws#OpenIdProvider`; its other checks are in
  `2026-10-22-authorization-server.md`.

## Not done (issue 1100)

* Item 9, npm functions (`cidValidate`, `cidRetrieveVerificationMethod`):
  not in this landing.
* JSON-LD processing of a CID document to RDF is not wired (the context is
  vendored and `injectContext` exists; the VC loader knows the context).
* The `Content-Type` of a fetched document is not checked: the host does
  not pass it to `Authz.recordDoc`. `CID.mediaTypeAccepted` exists for
  that.
