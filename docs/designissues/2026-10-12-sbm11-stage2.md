## 2. Term ids (`Storage/Sbm11/TermId.lean`)

A term id is a `UInt64`; bits 63..60 are a tag, bits 59..0 the payload.

| Tag | Term | Payload |
| ---: | --- | --- |
| 1 | blank node | rank of its key in the dictionary |
| 2 | IRI | rank in the dictionary |
| 3 | literal in the dictionary | rank in the dictionary |
| 4 | inline integer | bits 59..56: index into the 13 integer datatypes (`xsd:integer`, `long`, `int`, `short`, `byte`, `nonNegativeInteger`, `positiveInteger`, `nonPositiveInteger`, `negativeInteger`, `unsignedLong`, `unsignedInt`, `unsignedShort`, `unsignedByte`); bits 55..0: value + 2^55 |
| 5 | inline `xsd:boolean` | 1 (`true`) or 0 (`false`) |

A literal is inline only when its lexical form is the canonical form of
its value (`toString v == lexicalForm` for the integer `v` that
`String.toInt?` reads), the value is in the datatype's value space and in
[-2^55, 2^55). `"072"^^xsd:integer`, `"+72"`, `"-0"` and
`"300"^^xsd:unsignedByte` are not inline; they go to the dictionary as
typed literals (unit tests in `TermId.lean`). Tags 6, 7 and 8 (decimal,
double, date) are a later stage, as section 6.1 says; those literals are
dictionary terms.

`GraphId` is a separate structure: 0 is the default graph, any other value
is the term id of the graph name. `graphId_ofName_ne_default` proves that a
graph name never gets 0.

Two choices differ from section 6.1:

- A blank node is a dictionary term (class 1 key: its label), not a
  sequence number. The packer keeps the source labels, so the id gives the
  label back. Blank-node scoping by the manifest is stage 3 work.
- The rank of tags 1, 2 and 3 is the rank in the whole dictionary, not in
  the class. Classes are contiguous in key order (class byte first), so the
  tag can be read from the rank range too; the decoder checks that the tag
  and the key's class agree.

## 3. Keys and the dictionary bytes (`TermKey.lean`, `Dict.lean`)

A key is a class byte and a body. Unsigned byte order of keys is the
dictionary order.

| Class | Term | Body |
| ---: | --- | --- |
| 1 | blank node | UTF-8 label |
| 2 | IRI | UTF-8 IRI |
| 3 | `xsd:string` literal | lexical form |
| 4 | `rdf:langString` | lexical form, `0x00`, language tag (lower case) |
| 5 | other datatype | datatype IRI, `0x00`, lexical form |
| 6 | `rdf:dirLangString` | lexical form, `0x00`, tag, `0x00`, direction (1 `ltr`, 2 `rtl`) |

Class 5 has the datatype IRI first, so the literals of one datatype are one
contiguous rank range (section 6.1 asks for this; the key text of section
6.2 put the lexical form first). Admission: no triple term (RDF 1.2) in
stage 2; no `0x00` byte in a datatype IRI or a language tag; the language
tag already in lower case (the packer folds it with `normalizeTerm`, RDF 1.1
Concepts section 3.3, so `@en-US` and `@en-us` are one term and one id).

GDV1, `dict.gdv1`, all integers little-endian; SMALL is one byte `n < 255`,
else `0xFF` and `n` as u32:

    "GDV1" 0x01 0x40                     magic, version 1, 64 keys per page
    page*:  SMALL count
            SMALL len(k0) k0             first key in full
            (SMALL shared SMALL len(suffix) suffix)*   front coding

GDX1, `dict.gdx1`:

    "GDX1" 0x01 termCount:u64 pageCount:u64
    entry*: pageOffset:u64 pageLen:u32   12 bytes per page

The page of rank `r` is `r / 64`: id to key is one GDX1 entry read and one
page read. String to id is a binary search over the pages by their first
keys (each probe reads one entry and one page, about 1,080 bytes here) and
a scan of one page.

GDX1 differs from section 6.2, which put the first key of every page into
GDX1 as well. Measured with that heap on 2026-10-12: GDX1 847,873 bytes and
the dictionary 10,022,312 bytes, above the 10 MB target. Without it: 102,021
and 9,276,460. A page starts with its first key in full, so the search reads
it from GDV1.

## 4. Theorems

All in `formal/lean4/L4Factoidal/Storage/Sbm11/`. `#print axioms` of each
lists `propext`, `Classical.choice`, `Quot.sound` only
(`decodeDict_sorted`: `propext`, `Quot.sound`).

| Theorem | Statement |
| --- | --- |
| `TermKeyTheorems.decodeKey?_termKey?` | `termKey? t = some k → decodeKey? k = some t` |
| `TermKeyTheorems.termKey?_injective` | two admitted terms with one key are one term |
| `TermKeyTheorems.termKeyBytes?_eq` | the packer's `ByteArray` key has the bytes of the list key |
| `TermIdTheorems.ofInlineCode?_inlineCode?` | an inline id decodes to its term |
| `TermIdTheorems.ofCode?_toCode?` | `toCode? d t = some n → ofCode? d n = some t`, any dictionary `d` |
| `TermIdTheorems.ofId?_toId?` | the same for the `UInt64` id |
| `TermIdTheorems.toId?_eq_iff` | two terms with ids in one dictionary: same id if and only if same term |
| `TermIdTheorems.graphId_ofName_ne_default` | no graph name has graph id 0 |
| `DictTheorems.decodePage_encodePage` | one front-coded page round trip, with trailing bytes |
| `DictTheorems.decodeGdv_gdvBytes`, `decodeGdx_gdxBytes` | each file |
| `DictTheorems.decodeDict_encodeDict?` | `encodeDict? keys = some (v, x) → decodeDict v x = some keys` (the only hypothesis) |
| `DictTheorems.decodeDict_sorted` | a decoded dictionary is strictly increasing |
| `DictFastTheorems.decodePageAt_eq` | the byte-array page decoder that the lookups run equals the list decoder of the round trip, on every input |

What is tested and not proved:

- The packer writes GDV1 and GDX1 page by page with `encodePage` and
  `entryBytes`, the functions of `encodeDict?`, but no theorem says the
  streamed files equal `encodeDict?` of the key list. `--check --exact`
  compares the bytes: equal on the first 100,000 olympics triples (29,992
  terms, 469 pages; the list encoder is too slow for the whole file).
- `lookupM` returns only ranks of keys equal to the target in a decoded
  page, so a rank it returns is right. That it FINDS every key rests on the
  binary search over first keys (`cmpBytesAt`, not proved equal to
  `cmpKey`); `--check` looks up every key of the olympics dictionary.
- Stage 2 does not connect ids to the stage 3 permutations; the end-to-end
  theorem is https://github.com/danbri/factoidal/issues/776.

## 5. Packer phases 1 and 2 (`Harness/Sbm11DictPack.lean`)

`l4sbm11-dict-pack SOURCE.nt|.nq OUTDIR [--run-terms N] [--workers K]`

1. The source is cut into K byte ranges (default 4) at line starts. Each
   range is read in 64 KiB positioned reads by its own task and parsed by
   the streaming N-Quads parser (`NQuadsFold.feedChunkC`, RDF 1.1 mode; an
   N-Triples line is an N-Quads line). N-Triples and N-Quads lines are
   independent and a blank node keeps its label, so the cut changes no term.
   Each task folds language tags to lower case, drops inline terms, keeps
   the distinct other terms in a hash set and, at N / K terms (N default
   262,144), sorts their keys and writes a run file.
2. A k-way merge of the runs (1 MiB positioned reads per run) drops
   duplicates and writes GDV1 page by page and the GDX1 entries; the runs
   are removed.

Memory is bounded by the K hash sets (N terms in all) and one read buffer
per run; it does not grow with the source. Phase 3 (quad runs over batch
term numbers and their remap files) is stage 3 and is not written.

Measured (`l4sbm11-dict-pack` prints its phase times and VmHWM):

| Run | Phase 1 | Phase 2 | Total | Peak RSS |
| --- | ---: | ---: | ---: | ---: |
| 1 worker, set held in the fold accumulator (first version) | 95.95 s | 2.52 s | 98.47 s | 226,708 kB |
| 1 worker, chunk terms consed onto a list, set outside the fold | 72.65 s | 2.34 s | 74.98 s | 224,636 kB |
| 4 workers | 18.58 s | 3.39 s | 21.96 s | 171,712 kB |
| 4 workers, `splitCompleteLines` as a loop, merge buffers 16 MiB in all (landed) | 11.19 s | 3.01 s | 14.20 s | 140,740 kB |

The first version kept the hash set in the parser's fold accumulator.
`feedChunkC` reads `st.pos` after the fold over `st.acc`, so the set was
shared at the first insert of every 64 KiB chunk and copied whole: 5,153
copies of a set of up to 262,144 terms. Recorded in skill
`lean4-performance` (section "Keyed collections").

Two stack defects in shared code, found by the canary case of section 6
(the tail-recursion audit passed both):

- `NQuadsStreaming.splitCompleteLines` recursed once per character of each
  64 KiB parser chunk (and of a carried partial line). It now runs as
  `splitCompleteLinesTR`, a loop over the reversed buffer, through
  `@[csimp] splitCompleteLines_eq_TR` (proved; the definition and its
  theorems are unchanged). This path is the streaming N-Quads parser of the
  IBK4/IBK5 packers too. Its allow-list line is removed. It also made phase
  1 faster (18.58 s to 11.19 s).
- `Qlvr.mergeSortBy` used `for` loops in `Id.run`; the compiler left them
  as the generic `forIn` loop over closures, one frame per element. It is
  now three tail calls with fuel; its `#guard`s are unchanged.

Where phase 1 time went before these repairs (callgrind, 20,000 triples,
one worker): the
N-Quads reader 50 % (`readNQuad11`), of which `RDF.isIri` 19 % (it
converts every IRI to a `List Char` to find a colon) and UTF-8 decoding of
`String` data 20 %; chunk splitting about 20 %; the dictionary work (term
normalisation, inline test, hash set, key bytes, run sort) about 14 %.

## 6. Tests

- `#guard` unit tests in `TermKey.lean`, `TermId.lean` (canonical and
  non-canonical integers, ranges, booleans, tag and class agreement) and
  `Dict.lean` (SMALL fields, front coding, pages, cut, order, a 200-key
  round trip through `encodeDict?`/`decodeDict`, lookup and key-of-rank of
  every key through the in-memory fetch, absent keys).
- `l4sbm11-dict-pack --check SOURCE OUTDIR`: every key in rank order is
  strictly after the previous one, decodes to a term whose key is the same
  bytes, is not inline, is found by lookup at its rank and is the key of
  its rank; every term of SOURCE is either inline with an id that decodes
  to the same term, or has a rank whose key decodes to the same term; the
  count of distinct dictionary terms of SOURCE equals the term count.
- `tests/sbm11/dict_reference.py SOURCE`: the same two counts by an
  independent reader.
- `tests/sbm11/dict_scaling.sh [--doubled]`: n, 2n, 4n (the first quarter,
  half and all of the olympics file), exit 0. Pack 2.77 s, 5.86 s, 14.20 s
  (bound 9 x n); peak RSS 90,856, 108,808, 140,740 kB (bound 1.25 x n +
  64 MiB); lookup mean 99, 101, 178 us (bound 2 x n + 100 us). Doubled
  source: 32.89 s, 143,212 kB. The first run of `--doubled` failed the 10 %
  bound (149,416 against 134,044 kB, +11.5 %): the merge read 1 MiB per
  run, and the doubled source has 23 runs against 12. The merge now shares
  16 MiB among all runs.
- `tests/stack/run.sh` case `sbm11-dict`: 150,000 subjects, a
  300,000-byte literal (the largest page decode), runs of 20,000 terms (the
  external sort); pack and `--check` at the default stack and under
  `LEAN_STACK_SIZE_KB=512`: pass on both after the two repairs of section 5
  (306,007 terms, 4,782 pages, 112 runs, check failures=0). The whole
  suite: 53 pass, 0 fail (out of 53).
- `python3 tools/lean-tail-recursion-audit.py --gate`: exit 0, no new
  allow-list line; no function of the new modules is recursive in the
  compiled C.

## 7. Not done, and what it needs

- Triple terms (RDF 1.2) have no key: the packer refuses a source with one.
  Needs an issue (a key class for triple terms over the ids of their parts,
  stage 3 or later).
- Inline decimal, double and date (tags 6, 7, 8) are a later stage
  (section 6.1).
- Parser throughput bounds phase 1: about 7.5 MB/s per worker on this
  data after the splitter repair.
  `RDF.isIri` converting each IRI to a `List Char` was 19 % of one worker's
  time before the splitter repair; a `@[csimp]` replacement with `String.contains` is possible (the
  equality closes with `simp [String.contains]`) but changes a module every
  parser imports, so it is left for its own issue.
- No wasm export and no query path read GDV1/GDX1 yet (stage 4).
