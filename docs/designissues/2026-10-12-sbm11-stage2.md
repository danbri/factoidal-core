## 2. Term ids (`Storage/Sbm11/TermId.lean`)

A term id is a `UInt64`; bits 63..60 are a tag, bits 59..0 the payload.

| Tag | Term | Payload |
| ---: | --- | --- |
| 1 | blank node | rank of its key in the dictionary |
| 2 | IRI | rank in the dictionary |
| 3 | literal in the dictionary | rank in the dictionary |
| 4 | inline integer | bits 59..56: index into the 13 integer datatypes (`xsd:integer`, `long`, `int`, `short`, `byte`, `nonNegativeInteger`, `positiveInteger`, `nonPositiveInteger`, `negativeInteger`, `unsignedLong`, `unsignedInt`, `unsignedShort`, `unsignedByte`); bits 55..0: value + 2^55 |
| 5 | inline `xsd:boolean` | 1 (`true`) or 0 (`false`) |
| 9 | triple term (RDF 1.2, since 2026-10-14, section 8) | rank in the dictionary |

A literal is inline only when its lexical form is the canonical form of
its value (`toString v == lexicalForm` for the integer `v` that
`String.toInt?` reads), the value is in the datatype's value space and in
[-2^55, 2^55). `"072"^^xsd:integer`, `"+72"`, `"-0"` and
`"300"^^xsd:unsignedByte` are not inline; they go to the dictionary as
typed literals (unit tests in `TermId.lean`). Tags 6, 7 and 8 (decimal,
double, date) are a later stage, as section 6.1 says; those literals are
dictionary terms.

`GraphId` is a separate structure: 0 is the default graph, any other value
is the term id of the graph name. `graphId_ofName_ne_default` proves that a
graph name never gets 0.

Two choices differ from section 6.1:

- A blank node is a dictionary term (class 1 key: its label), not a
  sequence number. The packer keeps the source labels, so the id gives the
  label back. Blank-node scoping by the manifest is stage 3 work.
- The rank of tags 1, 2 and 3 is the rank in the whole dictionary, not in
  the class. Classes are contiguous in key order (class byte first), so the
  tag can be read from the rank range too; the decoder checks that the tag
  and the key's class agree.

## 3. Keys and the dictionary bytes (`TermKey.lean`, `Dict.lean`)

A key is a class byte and a body. Unsigned byte order of keys is the
dictionary order.

| Class | Term | Body |
| ---: | --- | --- |
| 1 | blank node | UTF-8 label |
| 2 | IRI | UTF-8 IRI |
| 3 | `xsd:string` literal | lexical form |
| 4 | `rdf:langString` | lexical form, `0x00`, language tag (lower case) |
| 5 | other datatype | datatype IRI, `0x00`, lexical form |
| 6 | `rdf:dirLangString` | lexical form, `0x00`, tag, `0x00`, direction (1 `ltr`, 2 `rtl`) |
| 7 | triple term (RDF 1.2, since 2026-10-14, section 8) | `len(sk)`, subject key, `len(pk)`, predicate key, object key (`len`: u32 little-endian) |

Class 5 has the datatype IRI first, so the literals of one datatype are one
contiguous rank range (section 6.1 asks for this; the key text of section
6.2 put the lexical form first). Admission: no triple term (RDF 1.2) in
stage 2 (class 7 since 2026-10-14, section 8); no `0x00` byte in a datatype
IRI or a language tag; the language tag already in lower case (the packer
folds it with `normalizeTerm`, RDF 1.1 Concepts section 3.3, so `@en-US` and
`@en-us` are one term and one id).

GDV1, `dict.gdv1`, all integers little-endian; SMALL is one byte `n < 255`,
else `0xFF` and `n` as u32:

    "GDV1" 0x01 0x40                     magic, version 1, 64 keys per page
    page*:  SMALL count
            SMALL len(k0) k0             first key in full
            (SMALL shared SMALL len(suffix) suffix)*   front coding

GDX1, `dict.gdx1`:

    "GDX1" 0x01 termCount:u64 pageCount:u64
    entry*: pageOffset:u64 pageLen:u32   12 bytes per page

The page of rank `r` is `r / 64`: id to key is one GDX1 entry read and one
page read. String to id is a binary search over the pages by their first
keys (each probe reads one entry and one page, about 1,080 bytes here) and
a scan of one page.

GDX1 differs from section 6.2, which put the first key of every page into
GDX1 as well. Measured with that heap on 2026-10-12: GDX1 847,873 bytes and
the dictionary 10,022,312 bytes, above the 10 MB target. Without it: 102,021
and 9,276,460. A page starts with its first key in full, so the search reads
it from GDV1.

## 5. Packer phases 1 and 2 (`Harness/Sbm11DictPack.lean`)

`l4sbm11-dict-pack SOURCE OUTDIR [--format F] [--base IRI] [--run-terms N] [--workers K]`
(since 2026-10-14 SOURCE is a document in any of the six RDF syntaxes, read
through the source layer; the text of this section describes the N-Triples and
N-Quads route, where the source is cut into byte ranges. Any other syntax is one
range.)

1. The source is cut into K byte ranges (default 4) at line starts. Each
   range is read in 64 KiB positioned reads by its own task and parsed by
   the streaming N-Quads parser (`NQuadsFold.feedChunkC`, RDF 1.1 mode; an
   N-Triples line is an N-Quads line). N-Triples and N-Quads lines are
   independent and a blank node keeps its label, so the cut changes no term.
   Each task folds language tags to lower case, drops inline terms, keeps
   the distinct other terms in a hash set and, at N / K terms (N default
   262,144), sorts their keys and writes a run file.
2. A k-way merge of the runs (1 MiB positioned reads per run) drops
   duplicates and writes GDV1 page by page and the GDX1 entries; the runs
   are removed.

Memory is bounded by the K hash sets (N terms in all) and one read buffer
per run; it does not grow with the source. Phase 3 (quad runs over batch
term numbers and their remap files) is stage 3 and is not written.

Measured (`l4sbm11-dict-pack` prints its phase times and VmHWM):

| Run | Phase 1 | Phase 2 | Total | Peak RSS |
| --- | ---: | ---: | ---: | ---: |
| 1 worker, set held in the fold accumulator (first version) | 95.95 s | 2.52 s | 98.47 s | 226,708 kB |
| 1 worker, chunk terms consed onto a list, set outside the fold | 72.65 s | 2.34 s | 74.98 s | 224,636 kB |
| 4 workers | 18.58 s | 3.39 s | 21.96 s | 171,712 kB |
| 4 workers, `splitCompleteLines` as a loop, merge buffers 16 MiB in all (landed) | 11.19 s | 3.01 s | 14.20 s | 140,740 kB |

The first version kept the hash set in the parser's fold accumulator.
`feedChunkC` reads `st.pos` after the fold over `st.acc`, so the set was
shared at the first insert of every 64 KiB chunk and copied whole: 5,153
copies of a set of up to 262,144 terms. Recorded in skill
`lean4-performance` (section "Keyed collections").

Two stack defects in shared code, found by the canary case of section 6
(the tail-recursion audit passed both):

- `NQuadsStreaming.splitCompleteLines` recursed once per character of each
  64 KiB parser chunk (and of a carried partial line). It now runs as
  `splitCompleteLinesTR`, a loop over the reversed buffer, through
  `@[csimp] splitCompleteLines_eq_TR` (proved; the definition and its
  theorems are unchanged). This path is the streaming N-Quads parser of the
  IBK4/IBK5 packers too. Its allow-list line is removed. It also made phase
  1 faster (18.58 s to 11.19 s).
- `Qlvr.mergeSortBy` used `for` loops in `Id.run`; the compiler left them
  as the generic `forIn` loop over closures, one frame per element. It is
  now three tail calls with fuel; its `#guard`s are unchanged.

Where phase 1 time went before these repairs (callgrind, 20,000 triples,
one worker): the
N-Quads reader 50 % (`readNQuad11`), of which `RDF.isIri` 19 % (it
converts every IRI to a `List Char` to find a colon) and UTF-8 decoding of
`String` data 20 %; chunk splitting about 20 %; the dictionary work (term
normalisation, inline test, hash set, key bytes, run sort) about 14 %.

## 8. Triple terms: key class 7, id tag 9 (2026-10-14)

Work issue: https://github.com/danbri/factoidal/issues/792 item 1. Owner rule
of 2026-10-14 (CLAUDE.md, "Shardborough is a persistent store for very large
data"): SBM11 stores the RDF abstract syntax of RDF 1.1 and RDF 1.2 Concepts,
whatever the source syntax. An RDF 1.2 triple term (`RDF.Term.tripleTerm`:
the subject an IRI or a blank node, the predicate an IRI, the object any term)
is now a dictionary term.

### 8.1 The key

    7  len(sk) sk  len(pk) pk  ok

`sk` is the key of the subject (class 1 or 2), `pk` the key of the predicate
(class 2), `ok` the key of the object (any class, 7 included); `len` is the
byte count of the part after it as a u32, little-endian (`writeU32LE`, the
integer encoding of GDV1). Example: `<<( _:s <a:p> _:o )>>` is
`07 02000000 0173 04000000 02613a70 016f` (a `#guard` in `TermKey.lean`).

Keys of the parts, not their ids (the suggestion of section 7 as written on
2026-10-12). Reasons:

1. An id is a rank, and ranks exist only after phase 2 has merged every key.
   A key over ids would need the ranks of the parts before the triple term's
   own key exists, so a phase 1 run could not be sorted by key, and every
   change of the ranks (compaction drops unused terms, stage 5) would change
   every triple-term key.
2. A key over ids needs every part in the dictionary. An inline integer
   object (tag 4) has no rank, and a subject that occurs only inside triple
   terms would become a dictionary term for that alone.
3. A key of parts decodes without the dictionary: `decodeKey?` stays a pure
   function of the bytes, and its round-trip theorem has no dictionary
   hypothesis.

The cost is that a triple term's key repeats the bytes of its parts, and a
nested triple term's key holds every level.

The object has no length field. It is the last part, and the dictionary
stores the length of every key (front coding, section 3), so a second copy of
it would be redundant. Without it a nested triple term (RDF 1.2 nests in the
object position only) is the suffix of its parent's key; the encoder and the
decoder are each one loop over the levels with no length arithmetic on the
inner key, and the key grows linearly with the nesting depth: 17 bytes per
level with the IRIs `<a:s>` and `<a:p>`, 5,100,011 bytes at depth 300,000
(`l4sbm11-dict-pack --nest-check 300000`).

Order. The dictionary is still sorted by unsigned byte comparison of whole
keys, and classes 1 to 6 keep code point order. Within class 7 the order is
the byte order of the body: first the four length bytes of the subject key
(little-endian, so this is not the numeric order of the lengths), then the
subject key, then the length bytes and the bytes of the predicate key, then
the object key. The keys with one subject key are one contiguous range of
ranks, and so are the keys with one subject key and one predicate key. Class 7
order is not the SPARQL 1.2 order of triple terms; ORDER BY on the id path
decodes them (stage 4 record, section 14).

Admission, encoder and decoder alike: the subject key and the predicate key
have fewer than `2^32` bytes (`partFits`, the width of `len`); the decoder
admits a subject part that decodes to an IRI or a blank node, a predicate
part that decodes to an IRI, and an object part that decodes to any admitted
term, with exact lengths. `normalizeTerm` folds the language tags inside
triple terms too, so `<<( :s :p "x"@EN )>>` and `<<( :s :p "x"@en )>>` are
one key and one id.

### 8.2 The id tag

Tag 9 is a triple term; its payload is the rank, as for tags 1 to 3
(`classTag` gives 9 for a class-7 key, `TermId.isDictTag` is 1, 2, 3 or 9).
A new tag, not tag 3 with a wider meaning, for two reasons: code that reads
tag 3 as a literal stays right (the STRSTARTS rank ranges, the key printer's
classes); and a reader built before this change refuses a generation that
holds a triple term at activation. Measured with `l4sbm11` built from
`origin/main` 1986fdf4 (before this change) on a two-quad generation with
triple terms: `FAIL pso block 0 row 0: id with an unknown tag or a rank past
the dictionary`, `sbm11-activate: refused failures=8`; its `dump` stops with
`unknown tag 9`. The stage 2 decoder (now `decodeAtom?`) returns `none` for
class 7 (`decodeAtom?_classTriple`), but the activation of that code does not
decode keys (it checks their order and their count): the refusal comes from
the id tag check `idOk`, which accepted tags 1 to 5.

Every site that listed the dictionary tags now calls `isDictTag` or
`classTagOfByte`: `ofCode?`, `Sbm11Gen.termOfId`, `Sbm11Query`
`Session.keySlice` and `Session.prefetch`, `Sbm11Cli.idOk`,
`Sbm11Compact.kindOf` and `Sbm11PackLib.tagOfKey`. Left on tags 1 to 3,
most of them refuse a tag-9 id (`ofCode?` gives `none`, `termOfId` "unknown
tag", `keySlice` "not a dictionary id", `idOk` refuses at activation) and
`prefetch` loses only a page prefetch; two would have been silent: compaction
would have copied a tag-9 id unchanged and dropped its key from the new
dictionary, and the packer would have given a class-7 key tag 3. Gate for
both: `tests/sbm11/run.sh` part (m) `compact-equals-fresh-pack` and every
query of the RDF 1.2 gate.

### 8.3 Format names

Coordinator decision, 2026-10-14: the names GDV1 and SBM11 (wire version 11)
stay. Class 7 and tag 9 are byte values that the code before them refuses
(section 8.2: the activation of that code fails with "unknown tag"); no byte
value that code admitted changes meaning; and a generation of RDF 1.1 data
is byte-identical to one packed before the change: the olympics generation
(1,781,625 triples) packed with this code has the same 10 artifacts and the
same `manifest.sbm11` as the stage 3 generation of 2026-10-12
(`dict.gdv1` SHA-256 `bd3e8854…f300e9bf`, `dict.gdx1` `fdd85d96…f20627c`,
compared with `cmp`). Shardborough format rule 2 (a byte change is a new wire
version) is about a byte whose meaning changes; rule 7 of the skill now
states this case.

### 8.5 Loops

`termKey?` and `normalizeTerm` are structural recursions on the object
position (the specifications). The compiled code runs the tail-recursive
twins `termKeyGo` (bytes of the enclosing levels in a reversed accumulator)
and `normalizeGo` (the enclosing levels, put back with `wrapLevels`, a
`List.foldl`) through the `@[csimp]` theorems above. `decodeTripleGo` is a
tail call with fuel (the body length plus one; each level reads at least ten
bytes). `IdQuery.groundTermGo` walks a triple-term pattern the same way.
`python3 tools/lean-tail-recursion-audit.py --gate`: exit 0, no new allow-list
line (`termKey?` and `normalizeTerm` are rows of class `replaced`; the twins
and the decoder are not recursive in the compiled C). `tests/stack/run.sh`
case `sbm11-triple-term`: a triple term nested 300,000 deep (above the wasm
module's 8 MB stack at 32 bytes a frame) through `normalizeTerm`,
`termKeyBytes?`, `decodeKey?` and `termKeyBytes?` again, under the default
stack and under `LEAN_STACK_SIZE_KB=512`: ran, 5,100,011-byte key, encode
1.2 s, decode 0.5 s, peak RSS 310 MB.
