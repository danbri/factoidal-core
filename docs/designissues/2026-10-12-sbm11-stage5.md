## 2. Method

### 2.1 Log and update

`l4sbm11 update GEN ('SPARQL UPDATE' | --file U.ru)` appends one DLB1
batch to `GEN/deltas.dlog` (resolved through `CURRENT`), with the Lean
definitions `l4block-delta-log` uses (`SPARQL/UpdateDelta.lean`,
`Storage/DeltaLog.lean`): entries carry RDF terms. A log that holds an RDF
1.2 term (a triple term or a directional literal) has DLOG version 2, written
by `l4sbm11 update --sparql12` (section 9). Admitted: INSERT DATA, DELETE
DATA, CLEAR, DROP, CREATE. Refused (run.sh
pins both): an update with WHERE, and INSERT DATA with a blank node. Code:
`Harness/Sbm11Delta.lean`.

### 2.2 Replay into an overlay over ids

At open (`Sbm11Query.openOverlaid`, used by `query`, `serve` and `compact`),
the committed batches after `compacted.epoch` are replayed
(`Session.loadOverlay`):

- each term of an added quad is mapped to its id: inline, or the dictionary
  id, or else a new id of tag 14 (`Overlay.tagDelta`) whose payload indexes
  the session's overlay vocabulary. No base id has tag 14, so overlay ids do
  not collide with base ids, and a term has one id (a term with a base id
  never gets a tag-14 id). A removed quad with a term that has no id is in
  no generation and is skipped.
- the state (`Overlay.State`): `ins` and `del` hash sets of quads in SPO
  order, `cleared` graph ids; `Overlay.step` applies one entry.
- per permutation, `Overlay.forPerm` sorts the inserts and deletes into the
  permutation's row order.

`Session.idOf` and `termOf` know the overlay vocabulary, so FILTER constants,
the JSON printer and the reference fallback see the new terms. The ORDER BY
and STRSTARTS shortcuts of stage 4 apply only to tags 1 to 4; a tag-14 id
goes to the reference evaluator path of each.

### 2.3 Merge in the scans

`IdQuery.scanFoldM` (and so every BGP scan, count, stream and the fallback's
quad selection) merges the overlay block by block, as QLever's
`LocatedTriplesPerBlock::mergeTriples` does:

- the inserts with the scan's key prefix, in row order; each goes into the
  first selected block whose last row is not below it (`Overlay.upperIdx`),
  the rest into one chunk after the last block;
- the deletes of a block are the slice between its first and last row
  (`lowerIdx`, `upperIdx`);
- a block with no overlay row in its range and no cleared graph (or a
  constant graph that is not cleared) takes the stage 4 path unchanged
  (metadata shortcuts, partial decodes); a block with overlay rows has its
  four frames read and decoded, its rows with the key prefix merged by
  `Overlay.mergeRows`, and the checks applied row by row.

### 2.4 Compaction through the packer

`l4sbm11 compact GEN OUTDIR` (`Harness/Sbm11Compact.lean`) replaces packer
phase 1 (parse) and runs packer phases 2 and 3 unchanged
(`Sbm11PackLib.packBatches`, split out of `Sbm11Pack.lean` so that both use
one code path):

1. one SPO scan of the overlaid generation marks the used dictionary ranks
   and overlay terms;
2. one term run: the used dictionary keys, read page by page (already in key
   order), merged with the sorted keys of the used overlay terms;
3. a second SPO scan writes one quad run in the phase-1 format (run-local
   numbers, inline ids, graph 0);
4. phase 2 (dictionary, remap), phase 3 (four permutations), hashes and the
   manifest; then `compacted.epoch` (greatest epoch folded) and
   `compacted.source.sha256` (SHA-256 of the source manifest and log), as
   `l4block-shard-compact` writes.

Terms that no remaining quad uses are dropped (olympics: 1, the deleted
label), so the output's dictionary is the one a pack of the same quads
writes, and the artifacts are byte-identical to a fresh pack.

## 3. What is proved

`L4Factoidal/Storage/Sbm11/OverlayTheorems.lean` (`#print axioms`:
`propext`, `Classical.choice`, `Quot.sound`; no `sorry`, no
`native_decide`, no user axiom):

- `filterDel_eq`: for sorted `base` and `del`,
  `filterDel cl base del = base.filter (r ∉ del ∧ ¬ cl r.g)`.
- `unionRows_mem`, `unionRows_sorted`: the sorted union holds the rows of
  both lists and is strictly sorted.
- `mergeRows_spec`: for strictly sorted inputs, `mergeRows cl base del ins`
  is strictly sorted and `r ∈ it ↔ (r ∈ base ∧ r ∉ del ∧ cl r.g = false) ∨
  r ∈ ins`. With `sorted_eq_of_mem_iff` (a strictly sorted list is
  determined by its members) and `mergeRows_eq_of_spec`: the merge equals
  every strictly sorted list of that set; as a multiset, each member once.
- `step_add`, `step_remove`, `step_clear`: over the `Std.HashSet` state the
  reader uses, one replay step changes
  `denote base st r = (base r ∧ r ∉ del ∧ r.g ∉ cleared) ∨ r ∈ ins` as
  INSERT DATA (`∪ {q}`), DELETE DATA (`∖ {q}`) and CLEAR/DROP (graph `g`
  removed) say (SPARQL 1.1 Update sections 3.1.1, 3.1.2, 3.2.2, 3.2.4);
  `replay_append`, `denote_empty`.

The order lemmas used (`lt_irrefl`, `lt_total`) are proved over `Block.Row`
with `ScanTheorems.lt_iff`.

## 4. What is open

Each item is a row of the lemma table (L7e to L7g) or has an issue (issues
linked 2026-10-14).

1. L7e: that `scanFoldM` puts each insert into exactly one chunk and keeps
   row order (tested only; needs L4e, the loop cut into per-block functions).
2. L7f: the term-to-id map of replay (tested only; the session is `IO`).
3. L7g: compaction equals `packSpec` of the updated quads (byte-identical on
   the two test inputs; needs L3c).
4. Updates with WHERE (DELETE/INSERT WHERE) are refused: they need the
   overlaid generation's answer at write time (https://github.com/danbri/factoidal/issues/849;
   run.sh pins the refusal).
5. INSERT DATA with blank nodes is refused, as in `l4block-delta-log`
   (https://github.com/danbri/factoidal/issues/850; run.sh pins the refusal).
6. The log is replayed at every open: each new or removed quad costs its
   term lookups (olympics, 10 entries: 10 ms). A server (`l4sbm11 serve`)
   replays once. The DLOG reader parses the log as a `List UInt8`
   (`Storage/DeltaLog.lean`), so a log of many megabytes costs list memory at
   open; a `ByteArray` reader is needed before large logs
   (https://github.com/danbri/factoidal/issues/851).
7. The overlay is in memory and grows with the log (design 6.7); a
   configured size that triggers compaction is not written
   (https://github.com/danbri/factoidal/issues/851).
8. Closed. The SPARQL tokenizer (`SPARQL/Tokenizer.lean`) was quadratic in
   the request length when this stage landed: `l4sbm11 update` of DELETE DATA
   with 1,000 quads took 2.5 s, 2,000 quads 9.3 s, 4,000 quads 61.8 s (gdb
   samples: every sample in `List.lengthTR` under `tokenizeLoop`).
   https://github.com/danbri/factoidal/issues/802 made it linear on
   2026-10-13 (danbri/factoidal-core 7b3e5af8): 4,000 quads 0.49 s, and the
   `sbm11-delta` stack case sends 8,000 quads (1.60 s).

## 8. The bytes after the committed batches (2026-10-14)

Issue: https://github.com/danbri/factoidal/issues/843. Found during the update
part of https://github.com/danbri/factoidal/issues/792 item 1.

**Defect.** `replayDeltaBatches` stops at the first DLB1 frame that
`parseDeltaBatch` refuses and returns the bytes from that frame.
`Sbm11Delta.readBatches` read those bytes as "a torn suffix (a batch not
committed)" and left them out. It returned a clean flag, but
`Session.loadOverlay` and `Sbm11Compact.runCompact` discarded it. A committed batch that the reader could
not decode (an entry from a newer writer), or a batch damaged in the middle of
the log, was therefore left out with every later batch, with exit 0 and no
message. Measured with the binaries of `cf55723e`: three batches, the second
with an RDF 1.2 triple term. `l4sbm11 query` gave the answer of batch 1 only
(`delta batches 1`). `l4sbm11 compact` folded batch 1 (`epoch=1`), and
`l4sbm11 activate` admitted its output: batches 2 and 3 were lost. The JS
`deltaLogMerge` had the same defect: it returned the N-Quads and dropped the
`torn` field.

**Rule.** `Storage.classifyTail` (`Storage/DeltaLog.lean`) says what the bytes
are:

| Kind | Bytes | Reader |
| --- | --- | --- |
| `torn` | the start of a frame (fewer than 12 bytes that start the fixed magic and version, or a header whose length asks for more bytes than are left); or a complete final frame whose checksum fails | keeps its crash-recovery rule: SBM11 query, serve and compaction and the browser merge use the batches before it, and stderr says `torn final frame left out`; the IBK3 paths, `StoreEndpoint` and every writer refuse the log until the frame is removed |
| `damaged` | a wrong magic or version where a frame starts, or a frame that fails its checksum and is not the final frame | error: every reader stops with a message and a non-zero exit |
| `undecodable` | a frame whose checksum verifies but whose body does not decode | error, also when it is the final frame |

`parseLogChecked` is the decision every native reader takes;
`BrowserLog.mergeChecked` and `LogRead.error?` are the browser's.

**Proved** (`Storage/BrowserLogTheorems.lean` section 7; `#print axioms`:
`propext`, `Classical.choice`, `Quot.sound`): `classifyTail_take` (every cut of
a record the encoder writes is torn), `classifyTail_frame` (the verdict on a
complete frame), `decode_encodeLog_byte_tail`, `decode_encodeLog_damaged`,
`decode_encodeLog_undecodable`, the `mergeChecked_*` theorems (a clean log and
a torn final record merge to the batches before it; a damaged or undecodable
record is an error), and `parseLogChecked_header_append` (the native readers
decide as the browser merge).

**Tests.** `tests/delta-log/run.sh` (SBM11 and IBK3: a torn final frame, cut
or with a failing checksum; a damaged middle batch; an undecodable batch at the
end and in the middle), the `#guard`s of `DeltaLog.lean`, `BrowserLog.lean`,
`Wasm/Ops/DeltaLog.lean` and `StoreEndpoint.lean`, and
`npm/factoidal/test/delta-log.test.mjs`.

**Older readers.** Binaries and npm releases built before this change keep the
defect. There are no users, so no older release is repaired.

## 9. RDF 1.2 terms in the delta log (2026-10-14)

Issue: https://github.com/danbri/factoidal/issues/792 item 1, the update part.
Coordinator decision of 2026-10-14: a new DLOG header version, its own term
codec, the shared term codec unchanged.

**What changed.** `l4sbm11 update GEN ('SPARQL UPDATE' | --file U.ru)
--sparql12` reads the request with the SPARQL 1.2 grammar. INSERT DATA and
DELETE DATA with triple terms (nested in the object position) and directional
literals are stored, replayed into the overlay, answered on the id path and by
the reference fallback, and compacted. Refused, as for RDF 1.1 terms: an
update with WHERE and INSERT DATA with a blank node (section 4, items 4 and
5); the blank-node check now looks inside triple terms
(`UpdateDelta.tripleMentionsBnode`). A DELETE DATA, DELETE WHERE or DELETE
template with a blank node inside a triple term is a parse error of the
reference parser (`UpdateParser.patternTermsHaveBnode`; SPARQL 1.2 does not
allow blank node syntax there; before, only the top level was checked).
`l4factoidal update --sparql12` is the reference for the gate.

**Format.** A DLOG of header version 2 encodes the terms of its DLE1 entries
with `serializeDeltaTerm?` and `parseDeltaTerm` (`Storage/DeltaLog.lean`):

| Term | Version 1 bytes | Version 2 bytes |
| --- | --- | --- |
| IRI, blank node, literal without direction | as in section 6.1 of the storage spec | the same bytes |
| triple term | tag 3 alone, refused by the reader | tag 3, the subject as a term (tag 0 or 1), the predicate as an IRI term (tag 0), the object as a term; a triple term in the object position nests |
| directional literal | no encoding (the writer refuses it) | tag 2, lexical form, datatype, flag 2, language tag, direction byte (1 `ltr`, 2 `rtl`) |

The DLB1 and DLE1 framing is the same in both versions. The shared
`serializeTerm?` and `parseTerm` of BLK0, IBK1, IBK2, PTD1 and TLI1 keep their
admission: they still refuse a triple term and a directional literal.

**Why a new version (format rule 7 of skill `shardborough-storage`).** A new
byte value keeps the format name only when the code before it refuses the new
value loudly. The readers before section 8 did not: `l4sbm11` of `cf55723e`
replays a log whose second batch holds a tag-3 entry, answers with batch 1
only, exit 0, and its compaction loses batches 2 and 3 (section 8). So rule 2
applies: a log that holds an RDF 1.2 term has header version 2, and every
reader before this change refuses that header. Measured with the binaries of
`cf55723e` on a version 2 log written by `l4sbm11 update --sparql12`:
`l4block-delta-log --inspect`, `l4sbm11 query`, `serve`, `compact` and
`update` each exit 1 with `DLOG header is malformed or unsupported`; `compact`
writes no generation, and the log bytes do not change.

**Writer.** `appendPlan?`: a batch with an RDF 1.2 term needs version 2. A new
log is created with version 2. An existing version 1 log gets version 2 in
place before the append: the four bytes at offset 4, written by
`l4_delta_log_write_at_size` (`ffi/block_pread.c`) under the same exclusive
lock and file-size check as the append, then `fsync`; a concurrent append
changes the size, and the writer reads the log again. A crash between the two
writes leaves a version 2 log of version 1 frames, which reads back the same.
A log that holds no RDF 1.2 term keeps version 1 and the bytes of the version
1 writer: three batches of INSERT DATA and DELETE DATA on the RDF 1.2 gate
fixture give a 794-byte log that is byte-identical (`cmp`) between the
`l4sbm11` of `cf55723e` and of this change, and two batches of
`l4block-delta-log --update` on an IBK3 collection give a 304-byte log that is
byte-identical too. For every batch: `appendPlan?_v1`.

**Readers.** `parseLog` reads version 1 with the version 1 codec and version 2
with the version 2 codec, and refuses any other version at the header. The
SBM11 tools (`query`, `serve`, `compact`, `update`) read both. The readers of
IBK3, IBK4 and IBK5 collections (`l4block-shard-activate`,
`l4block-id-v3-query`, `l4block-shard-compact`, the `l4block-delta-log`
writer, `StoreEndpoint`) refuse version 2 (`parseLogCheckedV1`): their block
formats do not store RDF 1.2 terms. `l4block-delta-log --inspect` prints the
version. The browser log of hub post 18 has no header and stays on the
version 1 codec; its update grammar is SPARQL 1.1.

**The overlay.** A term that the base dictionary does not hold gets an overlay
id (tag 14), whatever its kind; a triple term that the base holds keeps its
base id (`Session.idOf` looks in the dictionary first). Joins, DISTINCT,
GROUP BY, COUNT and constants compare ids; the triple functions, ORDER BY and
the printer decode the term (`Session.termOf`), as for the base (stage 4
record, section 14). Compaction re-keys overlay terms with the packer's keys
(class 7 for a triple term), and the compacted generation is byte-identical to
a fresh pack of the updated quads.

**Proved.** `TermCodecTheorems.lean`: `parseDeltaTerm_serializeDeltaTerm?`
(round trip for every term, one hypothesis: the encoder admits it),
`serializeDeltaTerm?_isSome_iff` (the encoder admits exactly `termFitsU32`),
`serializeDeltaTerm?_of_supported` (version 2 writes the version 1 bytes for
every term version 1 admits), `termFitsU32b_iff` (now also over triple terms).
