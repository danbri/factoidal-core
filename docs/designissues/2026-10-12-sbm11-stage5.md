## 2. Method

### 2.1 Log and update

`l4sbm11 update GEN ('SPARQL UPDATE' | --file U.ru)` appends one DLB1
batch to `GEN/deltas.dlog` (resolved through `CURRENT`), with the Lean
definitions `l4block-delta-log` uses (`SPARQL/UpdateDelta.lean`,
`Storage/DeltaLog.lean`): entries carry RDF terms. A log that holds an RDF
1.2 term (a triple term or a directional literal) has DLOG version 2, written
by `l4sbm11 update --sparql12` (section 9). When this stage landed, the
command admitted INSERT DATA, DELETE DATA, CLEAR, DROP and CREATE, and refused
an update with WHERE and INSERT DATA with a blank node. Since 2026-10-14 it
admits every operation of SPARQL 1.1 Update (section 10). Code:
`Harness/Sbm11Update.lean` (the request) and `Harness/Sbm11Delta.lean` (the
log helpers).

### 2.2 Replay into an overlay over ids

At open (`Sbm11Query.openOverlaid`, used by `query`, `serve` and `compact`),
the committed batches after `compacted.epoch` are replayed
(`Session.loadOverlay`):

- each term of an added quad is mapped to its id: inline, or the dictionary
  id, or else a new id of tag 14 (`Overlay.tagDelta`) whose payload indexes
  the session's overlay vocabulary. No base id has tag 14, so overlay ids do
  not collide with base ids, and a term has one id (a term with a base id
  never gets a tag-14 id). A removed quad with a term that has no id is in
  no generation and is skipped.
- the state (`Overlay.State`): `ins` and `del` hash sets of quads in SPO
  order, `cleared` graph ids; `Overlay.step` applies one entry.
- per permutation, `Overlay.forPerm` sorts the inserts and deletes into the
  permutation's row order.

`Session.idOf` and `termOf` know the overlay vocabulary, so FILTER constants,
the JSON printer and the reference fallback see the new terms. The ORDER BY
and STRSTARTS shortcuts of stage 4 apply only to tags 1 to 4; a tag-14 id
goes to the reference evaluator path of each.

### 2.3 Merge in the scans

`IdQuery.scanFoldM` (and so every BGP scan, count, stream and the fallback's
quad selection) merges the overlay block by block, as QLever's
`LocatedTriplesPerBlock::mergeTriples` does:

- the inserts with the scan's key prefix, in row order; each goes into the
  first selected block whose last row is not below it (`Overlay.upperIdx`),
  the rest into one chunk after the last block;
- the deletes of a block are the slice between its first and last row
  (`lowerIdx`, `upperIdx`);
- a block with no overlay row in its range and no cleared graph (or a
  constant graph that is not cleared) takes the stage 4 path unchanged
  (metadata shortcuts, partial decodes); a block with overlay rows has its
  four frames read and decoded, its rows with the key prefix merged by
  `Overlay.mergeRows`, and the checks applied row by row.

### 2.4 Compaction through the packer

`l4sbm11 compact GEN OUTDIR` (`Harness/Sbm11Compact.lean`) replaces packer
phase 1 (parse) and runs packer phases 2 and 3 unchanged
(`Sbm11PackLib.packBatches`, split out of `Sbm11Pack.lean` so that both use
one code path):

1. one SPO scan of the overlaid generation marks the used dictionary ranks
   and overlay terms;
2. one term run: the used dictionary keys, read page by page (already in key
   order), merged with the sorted keys of the used overlay terms;
3. a second SPO scan writes one quad run in the phase-1 format (run-local
   numbers, inline ids, graph 0);
4. phase 2 (dictionary, remap), phase 3 (four permutations), hashes and the
   manifest; then `compacted.epoch` (greatest epoch folded) and
   `compacted.source.sha256` (SHA-256 of the source manifest and log), as
   `l4block-shard-compact` writes.

Terms that no remaining quad uses are dropped (olympics: 1, the deleted
label), so the output's dictionary is the one a pack of the same quads
writes, and the artifacts are byte-identical to a fresh pack.

Reference route (2026-10-15, https://github.com/danbri/factoidal/issues/866 item 3).
`l4sbm11 compact GEN OUTDIR --via-quads` replaces steps 1 to 3 by the packer's
phase 1: one SPO scan of the overlaid generation decodes each row to RDF terms
(`Session.termOf`) and gives the quads of a block, as a batch, to a phase-1 worker
(`Sbm11Pack.openPhase1`), as the producers of the pack do. Step 4 is the same code
(`Sbm11Compact.packCompacted`). The output is byte-identical to the default route's
(`tests/sbm11/run.sh` parts (h), (i) and (m)). The default route stays the default: it
takes about half the time on the olympics generation. The numbers are in section 11.4 of
`2026-10-11-shardborough-vs-qlever.md`.

## 3. What is proved

`L4Factoidal/Storage/Sbm11/OverlayTheorems.lean` (`#print axioms`:
`propext`, `Classical.choice`, `Quot.sound`; no `sorry`, no
`native_decide`, no user axiom):

- `filterDel_eq`: for sorted `base` and `del`,
  `filterDel cl base del = base.filter (r ∉ del ∧ ¬ cl r.g)`.
- `unionRows_mem`, `unionRows_sorted`: the sorted union holds the rows of
  both lists and is strictly sorted.
- `mergeRows_spec`: for strictly sorted inputs, `mergeRows cl base del ins`
  is strictly sorted and `r ∈ it ↔ (r ∈ base ∧ r ∉ del ∧ cl r.g = false) ∨
  r ∈ ins`. With `sorted_eq_of_mem_iff` (a strictly sorted list is
  determined by its members) and `mergeRows_eq_of_spec`: the merge equals
  every strictly sorted list of that set; as a multiset, each member once.
- `step_add`, `step_remove`, `step_clear`: over the `Std.HashSet` state the
  reader uses, one replay step changes
  `denote base st r = (base r ∧ r ∉ del ∧ r.g ∉ cleared) ∨ r ∈ ins` as
  INSERT DATA (`∪ {q}`), DELETE DATA (`∖ {q}`) and CLEAR/DROP (graph `g`
  removed) say (SPARQL 1.1 Update sections 3.1.1, 3.1.2, 3.2.2, 3.2.4);
  `replay_append`, `denote_empty`.

The order lemmas used (`lt_irrefl`, `lt_total`) are proved over `Block.Row`
with `ScanTheorems.lt_iff`.

## 8. The bytes after the committed batches (2026-10-14)

Issue: https://github.com/danbri/factoidal/issues/843. Found during the update
part of https://github.com/danbri/factoidal/issues/792 item 1.

**Defect.** `replayDeltaBatches` stops at the first DLB1 frame that
`parseDeltaBatch` refuses and returns the bytes from that frame.
`Sbm11Delta.readBatches` read those bytes as "a torn suffix (a batch not
committed)" and left them out. It returned a clean flag, but
`Session.loadOverlay` and `Sbm11Compact.runCompact` discarded it. A committed batch that the reader could
not decode (an entry from a newer writer), or a batch damaged in the middle of
the log, was therefore left out with every later batch, with exit 0 and no
message. Measured with the binaries of `cf55723e`: three batches, the second
with an RDF 1.2 triple term. `l4sbm11 query` gave the answer of batch 1 only
(`delta batches 1`). `l4sbm11 compact` folded batch 1 (`epoch=1`), and
`l4sbm11 activate` admitted its output: batches 2 and 3 were lost. The JS
`deltaLogMerge` had the same defect: it returned the N-Quads and dropped the
`torn` field.

**Rule.** `Storage.classifyTail` (`Storage/DeltaLog.lean`) says what the bytes
are:

| Kind | Bytes | Reader |
| --- | --- | --- |
| `torn` | the start of a frame (fewer than 12 bytes that start the fixed magic and version, or a header whose length asks for more bytes than are left); or a complete final frame whose checksum fails | keeps its crash-recovery rule: SBM11 query, serve and compaction and the browser merge use the batches before it, and stderr says `torn final frame left out`; the IBK3 paths, `StoreEndpoint` and every writer refuse the log until the frame is removed |
| `damaged` | a wrong magic or version where a frame starts, or a frame that fails its checksum and is not the final frame | error: every reader stops with a message and a non-zero exit |
| `undecodable` | a frame whose checksum verifies but whose body does not decode | error, also when it is the final frame |

`parseLogChecked` is the decision every native reader takes;
`BrowserLog.mergeChecked` and `LogRead.error?` are the browser's.

**Proved** (`Storage/BrowserLogTheorems.lean` section 7; `#print axioms`:
`propext`, `Classical.choice`, `Quot.sound`): `classifyTail_take` (every cut of
a record the encoder writes is torn), `classifyTail_frame` (the verdict on a
complete frame), `decode_encodeLog_byte_tail`, `decode_encodeLog_damaged`,
`decode_encodeLog_undecodable`, the `mergeChecked_*` theorems (a clean log and
a torn final record merge to the batches before it; a damaged or undecodable
record is an error), and `parseLogChecked_header_append` (the native readers
decide as the browser merge).

**Tests.** `tests/delta-log/run.sh` (SBM11 and IBK3: a torn final frame, cut
or with a failing checksum; a damaged middle batch; an undecodable batch at the
end and in the middle), the `#guard`s of `DeltaLog.lean`, `BrowserLog.lean`,
`Wasm/Ops/DeltaLog.lean` and `StoreEndpoint.lean`, and
`npm/factoidal/test/delta-log.test.mjs`.

**Older readers.** Binaries and npm releases built before this change keep the
defect. There are no users, so no older release is repaired.

## 9. RDF 1.2 terms in the delta log (2026-10-14)

Issue: https://github.com/danbri/factoidal/issues/792 item 1, the update part.
Coordinator decision of 2026-10-14: a new DLOG header version, its own term
codec, the shared term codec unchanged.

**What changed.** `l4sbm11 update GEN ('SPARQL UPDATE' | --file U.ru)
--sparql12` reads the request with the SPARQL 1.2 grammar. INSERT DATA and
DELETE DATA with triple terms (nested in the object position) and directional
literals are stored, replayed into the overlay, answered on the id path and by
the reference fallback, and compacted. When this section landed, an update with
WHERE and INSERT DATA with a blank node were refused, as for RDF 1.1 terms
(section 4, items 4 and 5; both run since section 10); the blank-node check
looked inside triple terms (`UpdateDelta.tripleMentionsBnode`). A DELETE DATA, DELETE WHERE or DELETE
template with a blank node inside a triple term is a parse error of the
reference parser (`UpdateParser.patternTermsHaveBnode`; SPARQL 1.2 does not
allow blank node syntax there; before, only the top level was checked).
`l4factoidal update --sparql12` is the reference for the gate.

**Format.** A DLOG of header version 2 encodes the terms of its DLE1 entries
with `serializeDeltaTerm?` and `parseDeltaTerm` (`Storage/DeltaLog.lean`):

| Term | Version 1 bytes | Version 2 bytes |
| --- | --- | --- |
| IRI, blank node, literal without direction | as in section 6.1 of the storage spec | the same bytes |
| triple term | tag 3 alone, refused by the reader | tag 3, the subject as a term (tag 0 or 1), the predicate as an IRI term (tag 0), the object as a term; a triple term in the object position nests |
| directional literal | no encoding (the writer refuses it) | tag 2, lexical form, datatype, flag 2, language tag, direction byte (1 `ltr`, 2 `rtl`) |

The DLB1 and DLE1 framing is the same in both versions. The shared
`serializeTerm?` and `parseTerm` of BLK0, IBK1, IBK2, PTD1 and TLI1 keep their
admission: they still refuse a triple term and a directional literal.

**Why a new version (format rule 7 of skill `shardborough-storage`).** A new
byte value keeps the format name only when the code before it refuses the new
value loudly. The readers before section 8 did not: `l4sbm11` of `cf55723e`
replays a log whose second batch holds a tag-3 entry, answers with batch 1
only, exit 0, and its compaction loses batches 2 and 3 (section 8). So rule 2
applies: a log that holds an RDF 1.2 term has header version 2, and every
reader before this change refuses that header. Measured with the binaries of
`cf55723e` on a version 2 log written by `l4sbm11 update --sparql12`:
`l4block-delta-log --inspect`, `l4sbm11 query`, `serve`, `compact` and
`update` each exit 1 with `DLOG header is malformed or unsupported`; `compact`
writes no generation, and the log bytes do not change.

**Writer.** `appendPlan?`: a batch with an RDF 1.2 term needs version 2. A new
log is created with version 2. An existing version 1 log gets version 2 in
place before the append: the four bytes at offset 4, written by
`l4_delta_log_write_at_size` (`ffi/block_pread.c`) under the same exclusive
lock and file-size check as the append, then `fsync`; a concurrent append
changes the size, and the writer reads the log again. A crash between the two
writes leaves a version 2 log of version 1 frames, which reads back the same.
A log that holds no RDF 1.2 term keeps version 1 and the bytes of the version
1 writer: three batches of INSERT DATA and DELETE DATA on the RDF 1.2 gate
fixture give a 794-byte log that is byte-identical (`cmp`) between the
`l4sbm11` of `cf55723e` and of this change, and two batches of
`l4block-delta-log --update` on an IBK3 collection give a 304-byte log that is
byte-identical too. For every batch: `appendPlan?_v1`.

**Readers.** `parseLog` reads version 1 with the version 1 codec and version 2
with the version 2 codec, and refuses any other version at the header. The
SBM11 tools (`query`, `serve`, `compact`, `update`) read both. The readers of
IBK3, IBK4 and IBK5 collections (`l4block-shard-activate`,
`l4block-id-v3-query`, `l4block-shard-compact`, the `l4block-delta-log`
writer, `StoreEndpoint`) refuse version 2 (`parseLogCheckedV1`): their block
formats do not store RDF 1.2 terms. `l4block-delta-log --inspect` prints the
version. The browser log of hub post 18 has no header and stays on the
version 1 codec; its update grammar is SPARQL 1.1.

**The overlay.** A term that the base dictionary does not hold gets an overlay
id (tag 14), whatever its kind; a triple term that the base holds keeps its
base id (`Session.idOf` looks in the dictionary first). Joins, DISTINCT,
GROUP BY, COUNT and constants compare ids; the triple functions, ORDER BY and
the printer decode the term (`Session.termOf`), as for the base (stage 4
record, section 14). Compaction re-keys overlay terms with the packer's keys
(class 7 for a triple term), and the compacted generation is byte-identical to
a fresh pack of the updated quads.

### 10.2 Method

1. **Parse and order.** `appendUpdate` reads the log bytes first, parses the
   request (`parseSparqlUpdate`, with `--base` and `--sparql12`), and
   compiles the operations in order into log entries (`Run.compile`). Each
   operation reads the generation, plus the batches of the log, plus the
   entries of the earlier operations of the request (`Run.sync`: the log is
   replayed once, `Session.loadOverlay`; the new entries are stepped into the
   overlay, `Session.stepEntry`, `Session.withOverlay`). A request with no
   WHERE clause and no graph read does not open the generation (INSERT DATA
   without a blank node, DELETE DATA, CLEAR DEFAULT, DROP DEFAULT, LOAD SILENT).
2. **The WHERE clause** (`Run.evalWhere`) runs on the evaluator of `l4sbm11
   query`. If the operation has no USING clause and `IdQuery.translate` accepts
   the pattern, the id path runs (`whereTableM`, `decodeRowsM`); `WITH <g>`
   gives the default-graph patterns of the plan the graph `g`
   (`redirectPlan`). Otherwise the reference evaluator runs (`evalWhere`) over
   the quads that the planner guard selects (`selectedDataset`), in the view
   that `whereDataset` builds for `WITH`, `USING` and `USING NAMED` (section
   3.1.3). stderr names the path of each operation.
3. **The templates** are instantiated from the solution sequence by the
   reference functions: `modifyDeleteQuads`, `modifyInsertQuads` and
   `deleteWhereQuads` call `instQuads`. A template triple with an unbound
   variable, or a literal or a triple term as subject, or a predicate that is
   not an IRI, gives no quad. The entries are the removes of the deletes, then
   the adds of the inserts (`changeEntries`). Both come from the same
   solution sequence (section 3.1.3). A triple of the default graph goes to
   the `WITH` graph (`redirectQuad`).
4. **Graph management** (`clearEntries`, `dropEntries`, `createEntries`,
   `addGraphEntries`, `copyGraphEntries`, `moveGraphEntries`). The harness
   gives these functions the facts they need: whether a named graph exists
   (one scan, which stops at the first block with a quad of the graph), the
   named graphs (one scan of the graph column), the triples of a graph (one
   scan). COPY is a CLEAR of the destination followed by the adds of the
   source triples; MOVE is a COPY followed by a DROP of the source (a CLEAR
   for the default graph). A CLEAR or DROP of a graph that does not exist, and
   a COPY, MOVE or ADD from one, raise the error of section 3.2 unless
   SILENT; a CREATE of one that exists does too.
5. **Admission.** An added quad with a term that the dictionary does not
   admit makes the harness refuse the request before it writes anything: such
   an entry would make every later open of the generation fail
   (`entryAdmitted`).
6. **Append.** The batch is encoded (`appendPlan?`) and appended at the size
   read in step 1 (`appendSyncAtSizeRaw`). A concurrent writer changes the
   size; the request then starts again, with the WHERE clauses evaluated
   again, three times at most.

### 10.3 Fresh blank node labels

Rule (SPARQL 1.1 Update, sections 3.1.1 and 3.1.3.2; the reference semantics
cites section 19.6 for the scope of INSERT DATA labels):

1. A blank node label of INSERT DATA is scoped to the request. The request
   gets one fresh label for each distinct label of its INSERT DATA
   operations. A label that two graph blocks of one operation share denotes
   one node (W3C test `insert-data-same-bnode`). The parser refuses a label
   that two INSERT DATA or DELETE DATA operations of one request share
   (`UpdateParser.bnodeLabelsUniqueAcrossDataOps`, W3C test
   `syntax-update-54`).
2. A blank node label of an INSERT template gets one fresh label for each
   solution and for each label of the template.
3. A fresh label is `sbm11u` followed by the decimal digits of a counter `n`.
   The supply takes the first `n`, from a start value on, such that the label
   is held by none of these: the dictionary of the generation, the labels of
   the log's batches, the labels drawn earlier in the request. The start value
   is the number of labels with the prefix `sbm11u` in the dictionary plus the
   number in the log. It decides only how fast the search ends.
4. The labels are written in the batch. Replay and compaction therefore give
   the same blank nodes (test `replay-equals-compaction`).
5. No reader of the source layer produces a label with the prefix (test
   `no-reader-label`: 10 documents in six syntaxes, with anonymous nodes,
   property lists and collections). A label with the prefix that the
   dictionary holds, from a document or from an earlier update that a
   compaction folded, is skipped (test `skips-base-labels`: the base holds
   `sbm11u0` and `sbm11u2`; test `after-compaction`: the new labels are
   `sbm11u9` and `sbm11u10` after a compaction that holds `sbm11u0` to
   `sbm11u8`).

Harness (`Run.draw`). The lookups are I/O, so the harness looks the next 64
candidates up in the dictionary and in the set of the log's labels
(`Run.examineBlock`) and gives `UpdateStore.chooseGo` the labels it found as
`taken`. The dictionary is read only when it holds a label with the prefix
(`prefixHeld`: two `lowerBound` calls on the key range of class 1 with the
prefix), and the log's set only when the log holds one. The fresh labels of
a request are drawn before any entry is written, in the order: the INSERT DATA
labels, then for each operation the labels of its solutions in order.

Exact labels in the tests (`tests/sbm11/update/labels.nq` holds `sbm11u0` and
`sbm11u2`): the first request, with two labels, gets `sbm11u3` and `sbm11u4`;
the second gets `sbm11u5`; a third with one INSERT DATA label and a template
with two solutions gets `sbm11u6`, then `sbm11u7` and `sbm11u8`.

### 10.4 What is proved

`#print axioms` of `chooseGo_spec`, `drawMany_spec` and `drawMany_nil`:
`propext`, `Quot.sound`. Of every other theorem named here: `propext`,
`Classical.choice`, `Quot.sound`. No `sorry`, no `native_decide`, no user
axiom.

`SPARQL/UpdateStoreTheorems.lean`:

- `chooseGo_spec`: if `chooseGo taken fuel n = some m`, then `n ≤ m` and the
  label of `m` is not taken.
- `drawMany_spec`, `drawMany_nil`: `drawMany` draws `k` labels; the labels are
  pairwise different, none is taken, and the list has length `k`.
- `renameTermGo_eq`, `renameTriple_eq`, `renameQuad_eq`: the renaming of the
  blank nodes of a quad, a loop over the nesting of the triple terms, equals
  the reference's `Term.renameBnodes`.
- `insertDataQuads_eq`, `applyInsertData_eq`: the reference's INSERT DATA is
  the store's quads under the renaming `freshDataBnode`.
- `insertQuadsFor_eq`, `modifyInsertQuads_eq`, `applyModify_eq`,
  `applyDeleteWhere_eq`: the reference's `applyModify` and `applyDeleteWhere`
  equal the computation of `UpdateStore` with the reference's own blank node
  supply (`freshTemplateBnode`). The store differs from the reference only in
  the supply of fresh labels and in the evaluator that produces the solution
  sequence.
- `changeEntries_length`, `changeEntries_def`, `changeEntries_nil`.

`Storage/DeltaLog.lean`: `parseNFramedDeltaEntriesLoop_eq` (the loop gives the
entries that the recursive definition gives, with the accumulator reversed in
front) and `parseNFramedDeltaEntries_eq_fast` (the `@[csimp]` lemma;
`#print axioms` of both: `propext`, `Classical.choice`, `Quot.sound`).

`Storage/Sbm11/UpdateOverlayTheorems.lean`:

- `denote_removes`, `denote_adds`: the replay of a list of removes (adds)
  over the overlay state leaves exactly the quads that are not in the list
  (adds the quads of the list).
- `denote_change`: the replay of `changeEntries D I` gives `(S minus D) union
  I` (section 3.1.3, both sets from the state before the operation).
- `denote_clear_adds`: a CLEAR of graph `g` followed by adds gives `(S minus
  the quads of g) union I` (section 3.2.3, COPY).

Not proved: that the id path and the reference evaluator give the same
solution sequence for a WHERE clause (tested: 10.5; the general theorem is
https://github.com/danbri/factoidal/issues/776), and that the harness's block
lookups find every held label (tested: `labels` group).

The new Lean code is loops and tail calls (`chooseGo`, `renameTermGo`,
`termLabelsGo`, `templateLabelsGo`, the entry builders). The tail-recursion
audit gate (`python3 tools/lean-tail-recursion-audit.py --gate`) passes with no
new allow-list line. An earlier version had a generic monadic `chooseGoM` and
`Array.qsort` in `namedGraphs`; the audit flagged both and they were replaced
(10.8).

### 10.7 What stays open

Items 1 and 2 have an open issue and an expected failure in the `shortfalls`
group of `tests/sbm11/update_where.sh`. Items 3 and 4 were closed on 2026-10-14
(section 11); their tests are assertions in the `scaling` group.

1. https://github.com/danbri/factoidal/issues/855: the store has no slot for
   an empty named graph. A named graph exists exactly when a quad has it. The
   reference keeps the slot of a graph that CREATE or CLEAR leaves empty, so
   the request `CREATE GRAPH <g> ; CLEAR GRAPH <g>` is accepted by the
   reference and refused by the store (the graph does not exist for the
   CLEAR). The tests compare states with the empty graphs dropped on both
   sides, as the Lean W3C runner does.
2. https://github.com/danbri/factoidal/issues/856: a graph named by a blank
   node cannot be named in a log entry (entries carry an IRI). The graph-wide
   forms (CLEAR NAMED, CLEAR ALL, DROP NAMED, DROP ALL) refuse a store that has
   such a graph.
3. Closed 2026-10-14 (https://github.com/danbri/factoidal/issues/857). The
   batch encoder built the batch as a `List UInt8`: 64 to 67 bytes of memory
   for each byte of log. A request with 101,632 solutions gave a batch of 24
   to 36 MB and a peak RSS of 1.5 to 2.3 GB. Now 4 bytes for each byte of log
   (olympics, 36 MB batch: 158 MB).
4. Closed 2026-10-14 (https://github.com/danbri/factoidal/issues/858). The
   replay of the log at every open did one dictionary lookup for each term of
   each entry: 59 to 93 microseconds for each entry on the gate fixture
   (40,000 entries: 2.4 to 3.7 s) and 283 microseconds on olympics (203,264
   entries: 57.6 s). Now 13.5 microseconds for each entry on the
   fixtures (40,000 entries of the gate fixture: 660 to 762 ms) and 3.5 to 4.9 s on
   olympics. A compaction still removes the cost. The size of the overlay has a
   limit: section 11.2.3.

### 10.8 What failed on the way

- `l4sbm11 dump` and `l4sbm11 export` read the BASE of a generation, not the
  overlay. The first version of the state check dumped the uncompacted
  generation and compared a state without the log. The check now compacts

### 11.2 Method

#### 11.2.1 The log as a byte array (issues 857 and 851)

`Storage/DeltaLogBytes.lean` reads and writes the DLOG bytes (versions 1 and 2)
with positions in a `ByteArray`. The functions are `parseLogCheckedBA`,
`parseLogCheckedV1BA`, `classifyAt`, `logHeaderVersionAt?` for the reader and
`appendPlanBA?` for the writer. The list functions of `Storage/DeltaLog.lean`
stay the specification. One entry payload at a time goes through the list
parser and the list serialiser (about 100 bytes), so the codecs of the terms
(`DeltaTermCodec.v1` and `.v2`) are unchanged.

Every loop over the bytes of the log is a tail call. The generated C has
`goto _start` and no self call in `listOfRangeGo`, `sumGo`, `entriesAt`,
`replayGo`, `pushList` and `pushEntries?`; `tools/lean-tail-recursion-audit.py
--gate` has exit 0.

Callers: `Sbm11Delta.readBatches` (replay at open), `Sbm11Update.appendUpdate`
(the writer: the plan's bytes go to the positioned append `appendSyncAtSizeRaw`
with no list), `ShardActivate`, `ShardDeltaCompact`, `ShardMerkleMaterialize`,
`DeltaLogTool` and `StoreEndpoint` (the IBK3 paths). `l4sbm11 update` prints
`batch encode`, `append` and the peak RSS after the compile and after the encode.

#### 11.2.2 The replay in dictionary order (issue 858)

The old replay called `Dict.lookupM` for each occurrence of each term. Its binary
search reads a whole page (one GDX1 entry and one GDV1 page) at each of about 13
probes, and then one more page. A positioned read of the store is `open`,
`fstat`, `pread` and `close` of the file (`strace`), so a lookup was about 28
reads and 112 system calls. About half of the old replay was system time
(olympics: 30 s of 57.6 s).

`Session.prefillBaseIds` (`Harness/Sbm11Query.lean`) runs before the entries are
applied:

1. It collects the distinct terms of all entries (`entryTerms`): the terms are
   normalised and the terms with an inline code are left out.
2. It builds the dictionary key of each term (`termKeyBytes?`) and sorts the keys
   (`Dict.cmpBytesAt`, `Qlvr.mergeSortBy`).
3. It walks the keys with `Dict.lookupWalkM` (`L4Factoidal/Storage/Sbm11/DictFinger.lean`).
   The walk keeps a finger: the page of the last key and its keys. A key that is
   not above the last key of the finger's page needs no read. A key in the next
   page costs one page read (kept as `ahead` for a run of keys in the gap after
   the page). A key far from the finger costs what `lookupM` costs.
4. It keeps the dictionary id of each term, or `none`, in `Session.baseIds`.
   `Session.idOf` reads `baseIds` before it reads the dictionary. The ids that the
   log gives to terms the dictionary does not hold stay in `ovIds`, in the order
   the entries are applied, so `Session.idOrNew` gives the same ids as before.
5. The caller empties `baseIds` after the replay. `Run.sync` (the entries of the
   earlier operations of one request) does the same for its pending entries.

The hash sets of the replay (the term set, `baseIds`, `ovIds`, and `ins` and
`del` of the overlay state) are sized for one entry each. A set that grows hashes
every term again: it took the replay of 40,000 entries of the gate fixture from
840 to 960 ms down to 695 to 790 ms, and olympics from 4,128 to 4,531 ms down to
3,507 to 4,043 ms. `SBM11_REPLAY_LOOKUP=each` skips steps 1 to 4: the replay as it was. It is
the oracle of the test in 11.4.

`deltaText` (the stderr line of `query`, `serve` and `compact`) now also names
`log bytes N` and `dictionary terms looked up N`.

#### 11.2.3 The size limit of the log (issue 851)

`l4sbm11 update GEN REQUEST --max-overlay-entries N --max-overlay-bytes N` refuses
a request that would take the log past N entries or N bytes of log file. The
environment variables `SBM11_MAX_OVERLAY_ENTRIES` and `SBM11_MAX_OVERLAY_BYTES`
set the same limits when the flags are absent. There is no limit by default. A
log that holds exactly N is within the limit. The checks are:

1. before the request is evaluated: the log is already over the limit;
2. after the entries are known: the log plus the entries of the request;
3. after the batch is encoded: the log file plus the bytes of the batch.

A refusal exits 1, writes nothing, and says `Run 'l4sbm11 compact GEN OUTDIR'
and 'l4sbm11 activate ROOT NAME' to fold the log into a new generation, then
repeat the request.` A number that is not decimal is a usage error (exit 2).
`l4sbm11 serve` prints `serve: overlay size: N log entries in B batches, M bytes
of log, I inserted quads, D deleted quads, T new terms` and says whether the log
is within the limit that the environment sets. The decision is
`OverlayLimit.exceeded` (`Storage/Sbm11/OverlayLimit.lean`).

### 11.3 What is proved

All have `#print axioms` with `propext`, `Classical.choice` and `Quot.sound` only.
No `sorry`, no `native_decide`, no user axiom.

- `Storage/DeltaLogBytesTheorems.lean`: each byte array function equals its list
  function on the window it reads: `readU32LE_win`, `listOfRange_eq`,
  `sumRange_eq`, `parseEntry_win`, `entryAt_eq`, `entriesAt_eq`, `bodyAt_eq`,
  `parseDeltaBatchWith_win`, `replayBatchesAt_eq`, `parseLog_eq`, `classifyAt_eq`,
  `parseLogChecked_eq`, `parseLogCheckedV1_eq`, and for the encoder
  `pushEntry?_eq`, `pushEntries?_eq`, `bodyBA?_eq`, `batchBA?_eq`,
  `appendPlanBA?_eq`. `appendPlan?_csimp`, `parseLogChecked_csimp` and
  `parseLogCheckedV1_csimp` make the compiled code of the list API run the byte
  array functions, so the round-trip theorems of `DeltaLogCodecTheorems` and the
  tail rules of `BrowserLogTheorems` describe the code that runs. The `#guard`s of
  `DeltaLogBytes.lean` compare the two encoders and the two readers at every cut
  and at every changed byte of a version 1 log and a version 2 log.
- `Storage/Sbm11/DictFingerTheorems.lean`: over the bytes `encodeDict?` writes,
  every page that `pageNextM` (and `findPageM`, `stepPageM`) gives is the page of
  the key (`Bracket`: its first key is not above the key and the first key of the
  next page is above it), with its keys (`findPageM_spec`, `stepPageM_spec`,
  `pageNextM_spec`); the scan of such a page gives the rank of the key exactly when
  the key is in the dictionary (`rank_of_bracket`, the end of `lookupM_encodeDict`
  for any page). `lookupNextM_dictOk` and `lookupNextM_eq_lookupM`: one step of
  the walk answers as `lookupM` does. `lookupWalkM_dictOk`,
  `lookupWalkM_eq_lookupM` and `walkM_encodeDict`: `lookupWalkM` uses the finger
  only for a key that is not below the key before it, so a walk over any list of
  keys, in any order, answers the rank of every key. The sort is therefore a
  matter of speed. `walkM` is the specification of the `for` loop of
  `prefillBaseIds` and is `noncomputable`: the tail-recursion audit would count a
  compiled recursion over the keys.
- `Storage/Sbm11/OverlayLimit.lean`: `exceeded_none` (no limit set: nothing
  passes it), `exceeded_iff` (a size passes the limit exactly when it is above a
  limit that is set), `exceeded_mono` (a larger log passes every limit a smaller
  log passes).

The earlier theorems keep their statements: `OverlayTheorems`,
`UpdateOverlayTheorems`, `DeltaLogCodecTheorems`, `lookupM_encodeDict`.

What is measured, not proved:

- That the replay in dictionary order gives the overlay state and the ids of the
  replay with one lookup for each term. The glue is `IO` and `Std.HashMap`. The
  proof covers the lookup of each key. The test is the `replay` group (11.4).
- The speed and memory numbers.
- That the dictionary files meet the encoder's output: the stage 2 assumption.

### 11.7 What failed on the way

- The first memory bound of `batch-encoder-memory` (16 bytes for each byte of
  log plus 64 MiB) left 3 % of room: the peak of the whole process (139.8 MB for
  the 2.5 MB request) is reached while the SPARQL request is parsed, and the
  encoder adds nothing to it. The assertion now bounds the increase that the
  encoder causes (at most 8 bytes for each byte of log) and the whole process at
  16 bytes plus 96 MiB.
- The replay test `replay-time` passed at 840 to 960 ms against its bound of
  1,000 ms. A bound with 4 % of room fails on a busy machine. Sizing the hash
  sets took it to 695 to 790 ms.
- The header of `DeltaLogBytesTheorems.lean` named four theorems that did not
  exist (`batchAt_eq`, `parseLogAt_eq`, `parseLogCheckedBA_eq`,
  `parseLogCheckedV1BA_eq`). It now names the theorems that exist.
- `walkM`, the specification of the walk, failed the tail-recursion audit (class
  `length`, a cycle): it is a recursion over a list that is never run. It is
  `noncomputable`.
- The first design of `lookupWalkM` took the order of the keys as a hypothesis
  of the theorem. The walk now compares each key with the key before it, so the
  theorem has no hypothesis on the order and does not depend on the merge sort.

## 12. Named graphs: every graph name of the dataset (2026-10-15)

Issues: https://github.com/danbri/factoidal/issues/855 (a named graph with no
triple) and https://github.com/danbri/factoidal/issues/856 (a graph named by a
blank node).

### 12.1 Decision

Coordinator decision, 2026-10-15: SBM11 stores the RDF dataset of RDF 1.1
Concepts section 4 as that section defines it. A dataset has one default graph
and zero or more named graphs. A named graph is a pair of a graph name (an IRI
or a blank node) and an RDF graph, and that RDF graph can be empty. So:

- SBM11 keeps every graph name of the dataset, also the name of a graph that
  has no triple.
- A graph name can be a blank node on every path: pack, log, update, query,
  compaction and export.
- The rule "a graph exists when it has a quad" is removed.

SPARQL 1.1 Update needs the same model. Section 3.1.5 (CLEAR) removes the
triples of a graph and keeps the graph. Section 3.2.1 (CREATE) adds a graph
with no triple, and section 3.2.2 (DROP) removes the graph. CLEAR NAMED, CLEAR
ALL, DROP NAMED and DROP ALL apply to all named graphs, so also to a graph with
no triple and to a graph named by a blank node.

The work lands in five steps, each with its gates: the format (12.2), the
producers, the log, the queries and the export, and the tests.

### 12.2 The graph list (GNL1)

A quad names a graph that has a triple. It cannot name a graph that has no
triple. So a generation keeps the names of its named graphs in one more file,
`graphs.gnl1` (`Storage/Sbm11/GraphList.lean`):

    "GNL1"  count u64 LE  id u64 LE * count

Each id is the dictionary id of a graph name: tag 1 (blank node) or tag 2
(IRI). The ids are strictly increasing, and the list is not empty. A graph
name is a term of the dictionary, also when no quad has it.

**When a generation has the file.** A generation whose dataset has a named
graph has `graphs.gnl1`, and the file holds every named graph of the dataset,
empty or not. A generation whose dataset has no named graph has no file. Its
manifest has the ten roles of stage 3, and its bytes do not change. The
manifest names the ten files of `roles` or the eleven files of
`rolesWithGraphs` (`GNL1` after the dictionary), and nothing else
(`Manifest.rolesAdmitted`). The layout string does not change.

**Writer.** Phase 3a of the packer takes the graph id of every quad (not 0,
the default graph). It sorts each buffer, removes repeats and writes a run.
`writeGraphList` merges the runs with the loser tree of the permutation merge
(one buffer for each run), writes `graphs.gnl1`, reads the file back with
`GraphList.decodeAt` and compares the count. Compaction writes the list
through the same `packBatches`.

**Readers.** Activation (`verifyGenIn`) checks that the list decodes, that each
id is below the term count and decodes to an IRI or a blank node, and that the
graph of every PSO row is in the list. `l4sbm11 stats` prints `named-graphs:`.
`l4sbm11 graphs GEN` prints the named graphs of the base, one term on each
line in id order: the list, or the graph names of the quads for a generation
that has no list.

**Why the format keeps its name (format rule 7 of skill
`shardborough-storage`).** Measured with the binaries of `e185eb00` (the
`origin/main` before this change) on the gate fixture packed by this change
(2 named graphs, so the generation has GNL1):

- (a) No byte value that the older code admits changes its meaning. A manifest
  of ten roles means what it meant: the named graphs are the graph names of
  the quads.
- (b) The older code refuses the new file. `verify` and `activate`: `FAIL: the
  manifest does not decode or is not admitted`, `refused failures=1`, exit 1.
  `stats`, `dump`, `query`, `serve` and `compact`: `does not decode as an
  SBM11 manifest`, exit 1; `compact` writes no output directory. The older
  `update` refuses (exit 1, log bytes unchanged) every request that reads the
  generation: CREATE, DROP, CLEAR and DELETE WHERE. It appends an INSERT DATA
  or a DELETE DATA without blank nodes without opening the generation (exit
  0). The entries of those requests mean the same to the new reader. So no
  older reader drops an empty named graph without a message.
- (c) A generation without a named graph is byte-identical. The default graph
  of the gate fixture (41 quads) and `tests/sbm11/update/labels.nq` (4 quads):
  21 files each, every file `cmp`-equal between the packer of `e185eb00` and
  this one. The `verify` of `e185eb00` admits both packs.

A generation that has a named graph now has a different manifest (eleven
roles). The older readers refuse it, so such a generation must be packed again
for them. There are no users.

### 12.3 What is proved

`Storage/Sbm11/GraphListTheorems.lean`:

| Theorem | Statement | `#print axioms` |
| --- | --- | --- |
| `decode_encode?` | `encode? xs = some bs → decode bs = some xs`; the only hypothesis is the encoder's admission | `propext`, `Quot.sound` |

No hypothesis states a conclusion. `ManifestTheorems.decodeManifest_encodeManifest?`

### 12.5 The producers declare the named graphs

A producer of quads states the triples of a named graph. It cannot state a named
graph with no triple. So a batch of `QuadSource` (`RDF/QuadSource.lean`) now has
two arrays: `quads`, and `graphs`, the names of the named graphs that the source
declares, with or without a triple. A consumer takes the union: the named graphs
are the declared names and the graph names of the quads. A batch is never empty:
it has a quad or a graph name.

| Producer | What it declares |
| --- | --- |
| `QuadSource.ofDataset` | each named graph of `Dataset.named`, when the cursor starts on it (`Cursor.take`), so also a graph with no triple |
| `QuadSource.ofArray`, the HDT producer | nothing: their named graphs are the graph names of their quads |
| a file (`fileRangeSource`, the source layer) | each graph block of a TriG document, also `<g> { }` and `_:b { }` (the TriG chunk fold hands over a block with no triple when it opens, `Source.trigStepD`); each named graph of a JSON-LD document (`Source.foldDatasetD`); nothing for N-Triples, N-Quads, Turtle and RDF/XML |

The source layer has a declaration consumer, `Source.Decl` (`α → Subject → α`).
`Reader.feedD`, `Reader.finishD`, `ByteReader.feedD` and `ByteReader.finishD` take
it; `feed` and `finish` pass `noDecl`, so a consumer of quads only sees what it saw
before (`foldDatasetD_noDecl`). The reference parsers keep an empty graph block as
a named graph with no triple: `TriG.addTriplesTo` creates the graph before it adds
the triples (`ensureGraphOf`, `NQuads.ensureNamed`), and so does the indexed
accumulator (`ensureNamedFast`). Until this change an empty graph block was
dropped. The W3C TriG suites have no evaluation test with an empty graph block; the
three positive syntax tests with one (`trig-kw-graph-03`, `-10`, `-11`) pass, and the

block whose one statement is dropped leaves an empty named graph).

The packer: phase 1 gives each declared name a dictionary term, also when no quad
has it, and writes it to a graph run of the batch (`graphs-W-J.tmp`); phase 3a

### 12.6 The log: graph names and graph slots

**Graph names.** A log entry names a graph by a `DeltaGraphName`
(`Storage/DeltaLog.lean`): an IRI (a plain `Iri`, as before) or a blank node and
its label. `add`, `remove` and `clear` take an optional graph name (`none` is the
default graph); `drop` and `create` take a graph name.

**DLOG version 3.** A DLOG of header version 3 holds the entries of version 2 and
entries that name a graph by a blank node:

| Graph name | Versions 1 and 2 | Version 3 |
| --- | --- | --- |
| default graph (`add`, `remove`, `clear`) | graph tag 0 | the same byte |
| IRI (`add`, `remove`, `clear`) | graph tag 1, the string | the same bytes |
| blank node (`add`, `remove`, `clear`) | no encoding (the writer refuses it) | graph tag 2, the label |
| IRI (`drop`, `create`) | entry tag 3 or 4, the string | the same bytes |
| blank node (`drop`, `create`) | no encoding | entry tag 5 (`drop`) or 6 (`create`), the label |

The terms are encoded as in version 2. So every entry that version 2 admits has
the same bytes in version 3, and a version 3 reader reads the frames of the
writers of versions 1 and 2. The codec is one function with a flag
(`DeltaTermCodec.bnodeGraphs`); `DeltaTermCodec.v3` sets it.

**Why a new version (format rules 2 and 7 of skill `shardborough-storage`).** An
entry that names a graph by a blank node has a graph tag (2) or an entry tag (5,
6) that versions 1 and 2 do not have. The readers before section 8 (`cf55723e`)
replay the batches before a frame that they cannot decode and answer with exit 0
(section 9), so condition (b) of rule 7 fails and rule 2 applies, as it did for
the RDF 1.2 terms: a log that holds such an entry has header version 3, and a
reader before this change refuses the log at the header, before it uses a batch.
Measured with the binaries of `e185eb00` (the `origin/main` before this work) on
a version 3 log: the packer of `e185eb00` packed `tests/sbm11/update/bnode-graph.nq`
(so the generation has no graph list, and the older reader opens it), and the
`l4sbm11 update` of this change wrote CLEAR NAMED: one batch of two CLEAR entries,
header version 3, 105 bytes. The `l4sbm11` of `e185eb00`: `query`, `serve`,
`compact` and `update` exit 1 with `the DLOG header is malformed or unsupported`;
`compact` writes no output directory, and `update` leaves the log bytes unchanged.
Its `l4block-delta-log --inspect` (the log copied into an IBK3 generation) exits 1
with `DLOG header is malformed or unsupported`. The tools of this change read the
log: `query` replays it, and `l4sbm11 graphs` of the compacted generation lists
both graphs, now with no triple (`_:g`, `<http://ex.org/g1>`).

**A CREATE entry and an older reader.** Entry tag 4 (CREATE of a graph named by
an IRI) has the same bytes as before, and the writers before this change wrote
it too. A reader before this change does not keep a graph that a CREATE entry
adds and that no quad fills (the shortfall of
https://github.com/danbri/factoidal/issues/855), so it shows that graph as
absent. Such a reader opens only a generation without a graph list (section
12.2), and the gap is the one it had before this change. ADD, COPY and MOVE now
also write a CREATE entry for a named destination (below); an older reader
ignores it in the same way. Measured on a generation that the packer of
`e185eb00` packed: after `CREATE GRAPH <http://ex.org/gx>` by this change (a
version 1 log), the `l4sbm11 update` of this change refuses a second CREATE of
the graph (it exists), and the one of `e185eb00` accepts it (exit 0).

**Writer.** `appendVersion`: a batch with an entry that names a graph by a blank
node (`entryNeedsV3`) needs version 3, a batch with an RDF 1.2 term version 2; a
log keeps its version until a batch needs a higher one, and never goes back. An
existing log gets the new version in its header in place before the append (the
four bytes at offset 4, under the append lock, as for version 2;
`AppendPlan.setVersion`). A log that holds no such name keeps its version and
its bytes (`appendVersion_noV3`, `serializeDeltaEntryPayloadWith?_v3_eq_v2`).
The writers of IBK3, IBK4 and IBK5 collections write version 1 only
(`serializeDeltaBatch?`, which refuses a blank node graph name).

**Readers.** `parseLog` reads versions 1, 2 and 3 and refuses any other at the
header. The SBM11 tools read all three. The readers of IBK3, IBK4 and IBK5
collections refuse versions 2 and 3 (`v1Refusal?`, `parseLogCheckedV1`). The
browser log of hub post 18 has no header and the version 1 codec, which refuses a
blank node graph name.

**Graph slots in the overlay.** The replay state (`Storage/Sbm11/Overlay.lean`)
has two more sets: `created` (graphs that CREATE, or an INSERT into a graph that
did not exist, added) and `dropped` (graphs that DROP removed). The named graphs
of the overlaid generation are `denoteNamed`: a graph the log created, or a base
named graph (the graph list GNL1, or the graph names of the base quads) that the
log did not drop. CLEAR keeps a graph (section 3.1.5), DELETE keeps it (sections
3.1.2, 3.1.3), DROP removes it (section 3.2.2), CREATE adds it (section 3.2.1).
CREATE gives a graph name that the dictionary does not hold an overlay id. ADD,
COPY and MOVE write a `create` entry for a named destination: the reference
creates the destination also when the source has no triple
(`Dataset.setGraph`; `UpdateStore.createSlot`).

**Update.** `l4sbm11 update` reads graph existence from the overlaid named
graphs (`Session.hasNamedGraph`, `Session.namedGraphIds`). CLEAR NAMED, CLEAR
ALL, DROP NAMED and DROP ALL write one entry for each named graph, also for a
graph with no triple and for a graph named by a blank node. Until this change the
store refused the graph-wide forms on a store with a graph named by a blank node,
and accepted CREATE of a graph that existed with no triple.

**Compaction.** Both routes write the named graphs of the overlaid generation
into the graph list of the new generation: the default route marks their names as
used and writes them to a graph run of the batch; `--via-quads` gives them to the
phase-1 worker as declared graph names. The new dictionary holds the name of a
graph with no triple.
