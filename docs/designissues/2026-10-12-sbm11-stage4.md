## 2. The query path

```

              [--reference-render] [--reference]
l4sbm11 serve GEN          one query per stdin line, one SPARQL JSON line out
l4sbm11 prm-check GEN      PrmAt.decodePrmAt against Block.decodePrm, every PRM1
l4sbm11 frame-check GEN    FrameWords.decodeWords against decodeColumnAt, every frame
```

reason="..." predicates=K graphs=G quads=N`, then the rows, constants looked

65,536-byte Merkle chunks), open, execution and total time, peak RSS.

### 2.1 Fragment (`IdQuery.translate`)

SELECT with variables, `*`, `(COUNT(*) AS ?n)`, `(COUNT(?x) AS ?n)`; DISTINCT;
a WHERE tree of triple patterns, group joins, FILTERs and one level of
`GRAPH <iri>` / `GRAPH ?g`; GROUP BY variables; ORDER BY variables; LIMIT,
OFFSET. A FILTER is admitted when its expression is `Expr.backendLocal` (the
repository's set of operators that read only their operands: comparisons,
logical operators, BOUND, STR, LANG, DATATYPE, string functions without
REGEX, numeric and date accessors, IF, COALESCE, IN) and every variable it
reads occurs in a triple pattern of its own group; then every row of the
group binds the variable, and the FILTER can run after the joins of the
whole BGP with the same answer. Since 2026-10-13 also OPTIONAL groups at
the top level of the WHERE clause (section 10). Everything else (OPTIONAL
outside section 10's fragment, UNION, MINUS, EXISTS, NOT EXISTS,
sub-SELECT, property paths, BIND, VALUES, SERVICE, other aggregates, COUNT
DISTINCT, REDUCED, HAVING, FROM, ASK, CONSTRUCT, DESCRIBE, nested GRAPH, a
FILTER over a variable its group does not bind) is refused with a reason and
goes to the fallback.

### 2.2 Plan rules

The rules of `Qlvr.evalBgpM` (the measured model of the qlvr record), with
the four SBM11 permutations:

- Constants: a BGP constant is mapped to its id (inline, or a GDX1 binary
  search and one GDV1 page: `Dict.lookupM`); a constant with no id makes its
  pattern empty. A BGP constant matches by RDF term identity: `?g dbp:year
  1936` matches nothing when the data says `"1936"^^xsd:int` (q15).
- Permutation: the one whose leading columns are the bound positions
  (PSO/POS/SPO/OSP cover every set of bound positions: s → SPO, p → PSO or
  POS, o → OSP, s+p → PSO or SPO, s+o → OSP, p+o → POS); of those, one whose
  next column is the variable a merge join wants. A default-graph pattern
  checks graph id 0; `GRAPH <g>` checks the id of `g` (in the key when s, p
  and o are bound); `GRAPH ?g` outputs the graph column, id 0 excluded.
- Block skipping by PRM1: a binary search for the first block whose last row
  is not below the key prefix, then blocks while their first row is not above
  it. A block whose first and last rows both carry the prefix is full: its key
  columns are not decoded. A column is constant over a block when the first
  and last rows agree on it and every column before it (rows are sorted),
  and the graph column when the block has one row or a 9-byte graph frame in
  9 or more rows (the canonical encoder writes a constant frame exactly when
  all values are equal; activation re-encodes every frame). A block whose
  constant graph is not the one asked for is not read; a block with no
  needed column is not read (COUNT(*) of q01 reads 0 bytes).
- Reading: one verified positioned read of the needed frames of a block;
  the key columns are decoded in full, the key range found by binary search,
  and every other column decoded for that range only, stopping after its
  last row (`FrameWords.decodeWordsRange`).
- Order: least estimate first (PRM1 row counts of the selected blocks), then
  the connected pattern of least estimate. Merge join when the left table is
  sorted on the join variable and the next pattern can be scanned sorted on
  it, else hash join on all shared variables, built on the smaller side.
- Streaming: a single pattern without ORDER BY, DISTINCT or aggregate is
  answered block by block (FILTER, OFFSET, LIMIT per block; LIMIT stops the
  scan). A single pattern with COUNT is counted block by block, a constant
  group column counting a whole block at once.
- Terms only for output rows: SPARQL JSON is written from the dictionary key
  bytes (`keyShape`, `keyJsonInto`; one decoded page per 64 keys, kept packed
  in a page cache of at most 2,048 pages per session). The printer is
  compared byte for byte with `jsonOfTerm` on every oracle query
  (`--reference-render`) and on sample terms.

### 2.3 The reference fallback

The quads the planner guard of `quadEntriesForQuery` selects:
`ShardManifest.queryQuadConstantPredicates?` (the predicates every triple
pattern and path names) and `queryGraphNames?` (the graphs read), the same

## 3. FILTER on ids and its semantics

A FILTER conjunct is evaluated in one of three ways (`IdQuery.compileFilter`):

1. `?v = c` and `c = ?v` with `c` an IRI, an `xsd:string` literal or a
   language-tagged literal without direction: the row is kept exactly when
   the id of `?v` is the id of `c` (normalised as the packer normalises).
   `valueCompare` gives true for two IRIs only when equal, for two literals
   of one datatype only when language tag (case-insensitive) and lexical form
   are equal, and false or an error otherwise; data tags are stored in lower
   case, so this is term identity on stored terms. `sameTerm(?v, c)` and
   `sameTerm(?v, ?w)` are id equality (RDF term identity, ids injective:
   `TermIdTheorems.toId?_eq_iff`).
2. `STRSTARTS(?v, "s")` with a simple literal without U+0000: the keys of
   class 3 (`xsd:string`) and 4 (`rdf:langString`) that start with
   `[class] ++ s` are one rank range of the dictionary,
   `[lowerBound P, lowerBound (P ++ [0xFF]))` (no key holds 0xFF), so a
   dictionary literal of those classes passes exactly when its rank is in
   one of the two ranges: no dictionary read per row (q16: 21.9 ms warm, was
   674 ms reading every label). `STRENDS`, `CONTAINS` test the key bytes.
   Any other id goes to the reference evaluator.
3. Any other admitted expression: the reference evaluator
   (`ebvOrFalse (Expr.evalIn {} mu e)`, the FILTER of
   `QueryPattern.lowerWith`) on the decoded terms of the variables it reads,
   once per distinct tuple of ids (memo keyed by the ids; ids are injective,
   so equal ids give equal terms). `FILTER(?x = 72)` over `"72"^^xsd:int` is
   decided here, by value: `?age >= 72` in q11 gives the oracle's 34 rows;
   the gate fixture's `FILTER(?a = 72)` keeps `"72"^^xsd:int`,
   `"072"^^xsd:integer` (a dictionary term, non-canonical) and
   `"72.0"^^xsd:decimal`, as the reference engine does.

Proved: `IdQueryTests.ebvOrFalse_evalIn_and`: a FILTER of `a && b` keeps a
row exactly when the FILTERs of `a` and `b` both do, so conjuncts are applied
one by one (axioms `propext`, `Classical.choice`, `Quot.sound` at most).
Tested (`#guard`s in `IdQueryTests.lean`, on 23 sample terms: IRIs, blank
nodes, simple, string, language-tagged and typed literals, inline and
dictionary integers, decimal, double, booleans): rule 1 against
`Expr.evalIn` for every constant and term; the key-byte string tests and the
rank-range rule against STRSTARTS, STRENDS, CONTAINS; `DictRange.lowerBoundM`
against its definition on an encoded dictionary.

Defect found in the reference evaluator (needs an issue): `Expr.evalIn`
reads a bound numeric or boolean literal as its value (`literalPromote`),
and `sameTerm` then compares values and forms: `sameTerm(?v, "72"^^xsd:integer)`
with `?v` bound to `"72"^^xsd:integer` is false, and `"01"^^xsd:integer`
against `"1"^^xsd:integer` is true. W3C `expr-builtin/sameTerm-simple`
expects 14 rows; `l4factoidal query` answers 18 over the original Turtle.
The id path answers 14 (term identity). The sameTerm `#guard` excludes the
promoted datatypes and says why.

ORDER BY is section 15.1 as the reference evaluator orders
(`sparqlOrderValue` of `Expr.evalIn` of the variable). A column of only
blank nodes and IRIs is sorted by id (key order is class byte, then UTF-8,
which is code point order, `strCompare`); a column of only inline integers by
bits 55..0 (value + 2^55 for every integer datatype); any other column by
the numbers of its distinct values sorted with `sparqlOrderValue`. Both
shortcuts are `#guard`ed against `sparqlOrderValue` on the samples. q07 is
in code point order (QLever's ICU order differs, record 3.3).

## 7. What failed on the way, and what Lean taught

- **A second reference makes every append copy.** The first printer took
  the output buffer, returned `none` for some keys and then the caller
  appended to the same buffer: the buffer had two references during the
  call, and each append inside copied the whole output. q19 (39,768 rows)
  took 3.7 s; deciding the key's shape first, so that each branch holds the
  buffer once, made it 0.36 s. Same class as the stage 2 and 3 records'
  shared hash set and `remaps[k]!`.
- **Heap fragmentation costs time here.** A dictionary page cache of 64
  `ByteArray`s per page raised q19's peak RSS to 98 MB against 31 MB with no
  cache, and was slower: on this VM `clear_page_erms` (first touch of new
  memory, transparent huge pages) was 50 % to 67 % of the profile. One packed
  `ByteArray` per page: 48 MB, 0.36 s.
- **`for` loops with several mutable variables allocate per iteration.** The
  first word decoder (`for` with `acc`, `ended`, `i`) spent 22 % in
  `mi_malloc`/`mi_free`; the same loop as a tail call with every value an
  argument (`FrameWords.deltaGo`) does not allocate, and q03 warm went from
  2.0 ms to 0.8 ms; decoding only the key range of the other columns, 0.6 ms.
- **An `Option` pair per varint.** `Column.decodeColumnAt` (proved) returns
  `some (n, i)` per varint and builds an `Array Nat`; `FrameWords` keeps it
  as the reference and is tested equal on every frame of the generation.
- **A doc comment cannot precede `#guard`** (parse error); use `/- -/`.
- **Process start-up is a fixed cost here.** `l4sbm11` with no arguments
  takes 18 to 21 ms (median of 9) against 10 to 12 ms for `l4qlvr`; most of
  it is kernel page faults while the 11 MB binary initialises its modules.
  The process targets of the small queries cannot be met while that is so.

## 9. Verification as a reader option

Owner, 2026-10-12, verbatim: "In that case yes definitely make merkel
reading an application level option. Now!" Issue:
https://github.com/danbri/factoidal/issues/796. The format does not change:
the packer still writes the Merkle roots in the manifest and the `.merkle`
sidecars, and `l4sbm11 verify` and `activate` still check every file's
length, SHA-256, Merkle root and sidecar.

### 9.1 The option

`Harness.Sbm11Gen.Verify` is `merkle` or `none`. `Sbm11Gen.openGen` and
`Sbm11Query.openSession` take it as their first argument; the scan, count,
dump and query entry points read it from the opened generation
(`Gen.verify`). The library has no default.

| | `merkle` (the reads of sections 2 to 6) | `none` |
| --- | --- | --- |
| open | manifest decoded; the `.merkle` sidecars of GDV1, GDX1 and each opened PRB1 read and their leaves checked against the manifest root | manifest decoded; every file's length checked against the manifest (`stat`, no read) |
| PRM1 | read whole, length and SHA-256 checked, decoded | read whole, length checked, decoded |
| GDX1 | read whole on first use, length and SHA-256 checked | one `pread` per entry or header |
| PRB1 frames, GDV1 pages | each read widened to the 65,536-byte chunks it touches; each chunk read once, checked by its Merkle proof, kept in a cache | one `pread` of exactly the needed bytes; no cache |
| a changed byte | refused when its chunk is read | NOT detected (read as data) |

`none` relies on activation: `CURRENT` is written only after the full check,
so a generation `CURRENT` names was correct when it was activated. It does
not detect a change after activation (disk corruption, an edit). PRM1 is
still read whole: the plans binary-search the block metadata array
(`IdQuery.Store.metas`), and reading PRM1 entries one by one would change
the store interface of `IdQuery`, which is outside this change.

CLI: `l4sbm11 query|serve|scan|count|dump|dump-ids ... --verify merkle|none`.
Default: `none` when a `CURRENT` pointer names GEN (GEN is a collection root
with `CURRENT`, or the parent of GEN has a `CURRENT` that names GEN),
`merkle` for any other directory (`Sbm11Gen.cliDefaultVerify`). `--help`
(the usage text), `--explain` (`plan: verify=none (default: CURRENT names

`Storage/Sbm11/OptJoin.lean` (the left outer join). Theorems:

### 10.1 Fragment

The parser builds `{ base OPTIONAL { g1 } ... OPTIONAL { gk } FILTER(f) }` as
`filter f (leftJoin (... (leftJoin base g1 true) ...) gk true)`, with the
FILTERs of each group around that group. Admitted:

- the base: a group of section 2.1 (triple patterns, group joins, FILTERs,
  one level of GRAPH), with at least one triple pattern;
- each OPTIONAL group: triple patterns of the default graph and
  `backendLocal` FILTERs whose variables the group's own triple patterns
  bind; no GRAPH, no nested OPTIONAL, UNION or MINUS;
- a variable of a group that the base's triple patterns do not bind occurs in
  no other group; a FILTER beside the OPTIONALs reads only variables of the
  base's triple patterns. So every variable that a group shares with
  anything outside it is bound by the base, in every left row (the
  well-designed patterns of Pérez, Arenas and Gutierrez, "Semantics and
  complexity of SPARQL", 2009), and no group uses a variable that an earlier
  group binds;
- projection, `*`, `COUNT(*)`, `COUNT(?x)`, GROUP BY, ORDER BY, DISTINCT,
  LIMIT, OFFSET as in section 2.1, over the variables of the base and of the
  groups.

Refused, so the reference fallback answers (gate `ref-optional-*`): a nested
OPTIONAL; a variable two groups share that the base does not bind; a FILTER
in a group over a variable of the base; a FILTER beside the OPTIONAL over a
group variable (`FILTER(!BOUND(?f))`); OPTIONAL before the triple patterns
(`Join(LeftJoin({}, P1), P2)`); GRAPH in a group.

Why a group's FILTER may read only the group's variables. SPARQL 1.1 section
18.2.2.5 makes `OPTIONAL { P FILTER(F) }` the `LeftJoin(G, P, F)` of section
18.5, F evaluated on the merged solution. The reference evaluator (and the
F* engine) evaluate `LeftJoin(G, Filter(F, P), true)`, F on the group's row
only, so a base variable in F reads as unbound
(https://github.com/danbri/factoidal/issues/815, known-defects case
`SPARQL-OPT-FILTER-SCOPE`). When F reads only variables that every row of
the group binds, the two readings give the same answer
(`leftJoin_filter_right`), and the id path equals the reference. When issue
815 is fixed, the restriction can be removed.

### 10.2 Algorithm

1. The base: `evalBgpM`, then its FILTERs and the FILTERs beside the
   OPTIONALs (each output row has its left row's values on the base
   variables, so a FILTER over them can run before the joins). A base of one
   pattern is scanned sorted on a variable it shares with the first group.
2. Per group, in order: `evalBgpM` of its patterns (the first scan sorted on
   the left table's sort variable when the group has that variable), the
   group's FILTERs on its rows, then `OptJoin.leftOuterJoin`:
   - inner pairs of left and right row indices with equal shared columns,
     in left-row order and per left row in right-row order: `Qlvr.mergeGo`
     when both tables are sorted on a shared variable, else a hash index of
     the right rows probed in left-row order (the cross product when no
     variable is shared);
   - `outerPairs`: each left row with its pairs, else the row with `none`;
   - output columns: the left columns gathered by the left indices, the
     right variables the left does not have gathered by the right indices,
     id 0 (`OptJoin.unbound`) for `none`. The left row order and sort
     variable are kept, so the next group can merge again.
3. Then section 2's steps. Id 0 is no term id (`TermId`: tags 1 to 5 and 14)
   and no column holds graph id 0, so: the renderer leaves an id 0 binding
   out; ORDER BY maps it to the error value, which section 15.1 orders first,
   as the reference does; DISTINCT and GROUP BY compare it as an id (one
   value); `COUNT(?x)` counts the rows where `?x` is not 0
   (`countItems`, SPARQL 1.1 section 18.5 Count).

The right side is scanned in full: d11 reads all 197,044 `dbo:deathDate`
rows for 1,083 left rows. Using the left keys to skip right blocks is
https://github.com/danbri/factoidal/issues/809; nothing here blocks it (the
right scan is `evalBgpM` with a preferred sort variable).

### 10.3 What is proved

`Storage/Sbm11/OptJoinTheorems.lean` (lemmas L5g and L5g′ of the
end-to-end record; axioms `propext`, `Classical.choice`, `Quot.sound` at
most):

| Theorem | Statement |
| --- | --- |
| `outerPairs_eq` | over the index arrays of the inner pairs (`innerSpec`: every `(i, j)` with `cand i j`, in order), `outerPairs` gives `ljSpec`: each left row with its accepted right rows in order, or `(i, none)` |
| `outerPairs_merge` | the same over the index arrays of `Qlvr.mergeGo`, join columns non-decreasing on both sides (from `MergeTheorems.mergeGo_spec`) |
| `ljSpec_left_row` | (a) every left row occurs in the output |
| `ljSpec_mem_some`, `ljSpec_mem_none`, `ljSpec_complete` | (b) an output row is an accepted pair, or a left row that accepts no right row; every accepted pair is in the output |
| `ljSpec_count_row`, `ljSpec_length` | (c) left row `i` occurs `max 1 c` times, `c` the right rows it accepts; the length is the sum over the left rows |
| `leftJoin_decode` | over rows of ids, decoding `idLeftJoin L R` gives SPARQL 1.1 `leftJoin` (section 18.5, `SPARQL/Algebra.lean`) of the decoded rows with condition `true`, as a list (same rows, same order), when `Term.eqb` of two decoded ids is id equality on the ids that occur |
| `idLeftJoin_eq_ljSpec`, `outerPairs_leftJoin` | `idLeftJoin` is `ljSpec` with id compatibility as the candidate relation; so the index arrays `outerPairs` builds, mapped to rows and decoded, are that `leftJoin` |
| `leftJoin_filter_right` | `LeftJoin(Ω1, Ω2, c) = LeftJoin(Ω1, Filter(c2, Ω2), true)` when `c` on each compatible merge is `c2` on its right row |

The decoding hypothesis holds for the ids of a generation except where
`Term.eqb` identifies two stored terms with different ids: two
`rdf:XMLLiteral` lexical forms with one exclusive canonical form (language
tags are stored in lower case). The inner joins of section 2.2 make the same
assumption.

Open (lemma L5g″, tested): that the `Table` `leftOuterJoin` builds
(`gather`, `gatherOpt` over `ByteArray` columns) denotes the rows of
`idLeftJoin`, that the hash path computes `innerSpec` (`Std.HashMap`), and
that on two id tables whose shared variables are bound in every row, id
compatibility is equality of the shared columns. The same step is open for
the inner join (L5a′, L5b). Tested by 9 `#guard`s in `OptJoinTheorems.lean`
(merge, hash with one and two shared columns, cross product, empty sides,
unbound ids in the left table: `leftOuterJoin` against `idLeftJoin` of the
tables' rows) and by the gate queries.

### 10.6 What failed on the way

- **A `let` before a `match` runs in every branch.** `OptJoin.innerPairs`
  first bound the hash pairs with a `let` before the `match` on the sort
  variable, to use them in the two fallback branches. Lean evaluates it in
  every branch: the merge path built a `Std.HashMap` of the 197,044 right
  rows and dropped it. d11 warm was 50.2 ms; with the hash path in its own
  function (`hashInner`) called only in its branches, 18.5 ms (medians of
  15). Found with `valgrind --tool=callgrind` (`hashPairs` called once per
  run in runs that printed `merge on ?p`); `perf` has no build for this
  kernel. Recorded in `skills/lean4-performance`.
- **The stack gate shares its fixture directory.** `tests/stack/run.sh`
  writes to `/tmp/factoidal-stack-fixtures` unless `STACK_FIXTURES` is set;
  a run in the main checkout at the same time removed the SBM11 fixtures
  under this run (`l4sbm11-pack: no such file or directory`). Run it with
  `STACK_FIXTURES` in the worktree or a scratch directory.
- **The stack case keeps 300 bytes of each answer.** The first OPTIONAL
  query of the `sbm11-query` case projected `?s ?n`; the value the check
