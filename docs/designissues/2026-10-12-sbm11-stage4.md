## 2. The query path

Code: `formal/lean4/L4Factoidal/Storage/Sbm11/IdQuery.lean` (pure, generic
over the monad of a `Store`), `Harness/Sbm11Query.lean` (the `IO` store,

```

              [--reference-render] [--reference]
l4sbm11 serve GEN          one query per stdin line, one SPARQL JSON line out
l4sbm11 prm-check GEN      PrmAt.decodePrmAt against Block.decodePrm, every PRM1
l4sbm11 frame-check GEN    FrameWords.decodeWords against decodeColumnAt, every frame
```

### 2.1 Fragment (`IdQuery.translate`)

SELECT with variables, `*`, `(COUNT(*) AS ?n)`, `(COUNT(?x) AS ?n)`; DISTINCT;
a WHERE tree of triple patterns, group joins, FILTERs and one level of
`GRAPH <iri>` / `GRAPH ?g`; GROUP BY variables; ORDER BY variables; LIMIT,
OFFSET. A FILTER is admitted when its expression is `Expr.backendLocal` (the
repository's set of operators that read only their operands: comparisons,
logical operators, BOUND, STR, LANG, DATATYPE, string functions without
REGEX, numeric and date accessors, IF, COALESCE, IN) and every variable it
reads occurs in a triple pattern of its own group; then every row of the
group binds the variable, and the FILTER can run after the joins of the
whole BGP with the same answer. Since 2026-10-13 also OPTIONAL groups at
the top level of the WHERE clause (section 10). Everything else (OPTIONAL
outside section 10's fragment, UNION, MINUS, EXISTS, NOT EXISTS,
sub-SELECT, property paths, BIND, VALUES, SERVICE, other aggregates, COUNT
DISTINCT, REDUCED, HAVING, FROM, ASK, CONSTRUCT, DESCRIBE, nested GRAPH, a
FILTER over a variable its group does not bind) is refused with a reason and
goes to the fallback. Since 2026-10-13 (section 12): a FILTER outside
`backendLocal`, or over a variable no pattern binds, runs on the decoded rows
after the joins; ASK, CONSTRUCT and a SELECT clause outside this fragment
(expressions, aggregates other than COUNT, COUNT DISTINCT, HAVING, GROUP BY
or ORDER BY an expression, REDUCED) run the WHERE clause on ids and the
reference post-processing on the decoded solutions. EXISTS, NOT EXISTS, FROM
and DESCRIBE stay refused.

### 2.2 Plan rules

The rules of `Qlvr.evalBgpM` (the measured model of the qlvr record), with
the four SBM11 permutations:

- Constants: a BGP constant is mapped to its id (inline, or a GDX1 binary
  search and one GDV1 page: `Dict.lookupM`); a constant with no id makes its
  pattern empty. A BGP constant matches by RDF term identity: `?g dbp:year
  1936` matches nothing when the data says `"1936"^^xsd:int` (q15).
- Permutation: the one whose leading columns are the bound positions
  (PSO/POS/SPO/OSP cover every set of bound positions: s → SPO, p → PSO or
  POS, o → OSP, s+p → PSO or SPO, s+o → OSP, p+o → POS); of those, one whose
  next column is the variable a merge join wants. A default-graph pattern
  checks graph id 0; `GRAPH <g>` checks the id of `g` (in the key when s, p
  and o are bound); `GRAPH ?g` outputs the graph column, id 0 excluded.
- Block skipping by PRM1: a binary search for the first block whose last row
  is not below the key prefix, then blocks while their first row is not above
  it. A block whose first and last rows both carry the prefix is full: its key
  columns are not decoded. A column is constant over a block when the first
  and last rows agree on it and every column before it (rows are sorted),
  and the graph column when the block has one row or a 9-byte graph frame in
  9 or more rows (the canonical encoder writes a constant frame exactly when
  all values are equal; activation re-encodes every frame). A block whose
  constant graph is not the one asked for is not read; a block with no
  needed column is not read (COUNT(*) of q01 reads 0 bytes).
- Reading: one verified positioned read of the needed frames of a block;
  the key columns are decoded in full, the key range found by binary search,
  and every other column decoded for that range only, stopping after its
  last row (`FrameWords.decodeWordsRange`).
- Order: least estimate first (PRM1 row counts of the selected blocks), then
  the connected pattern of least estimate. Merge join when the left table is
  sorted on the join variable and the next pattern can be scanned sorted on
  it, else hash join on all shared variables, built on the smaller side.
- Streaming: a single pattern without ORDER BY, DISTINCT or aggregate is
  answered block by block (FILTER, OFFSET, LIMIT per block; LIMIT stops the
  scan). A single pattern with COUNT is counted block by block, a constant
  group column counting a whole block at once.
- Terms only for output rows: SPARQL JSON is written from the dictionary key
  bytes (`keyShape`, `keyJsonInto`; one decoded page per 64 keys, kept packed
  in a page cache of at most 2,048 pages per session). The printer is
  compared byte for byte with `jsonOfTerm` on every oracle query
  (`--reference-render`) and on sample terms.

### 2.3 The reference fallback

The quads the planner guard of `quadEntriesForQuery` selects:
`ShardManifest.queryQuadConstantPredicates?` (the predicates every triple
pattern and path names) and `queryGraphNames?` (the graphs read), the same
definitions as the IBK4/IBK5 path. With predicates: a PSO scan of each
predicate, all graphs; else an SPO scan of every row; then the graph filter.
The rows are decoded into a `Dataset` (`QuadDataset.datasetOfQuads`) and the

a variable it is the whole generation (gap:
https://github.com/danbri/factoidal/issues/775).

## 3. FILTER on ids and its semantics

A FILTER conjunct is evaluated in one of three ways (`IdQuery.compileFilter`):

1. `?v = c` and `c = ?v` with `c` an IRI, an `xsd:string` literal or a
   language-tagged literal without direction: the row is kept exactly when
   the id of `?v` is the id of `c` (normalised as the packer normalises).
   `valueCompare` gives true for two IRIs only when equal, for two literals
   of one datatype only when language tag (case-insensitive) and lexical form
   are equal, and false or an error otherwise; data tags are stored in lower
   case, so this is term identity on stored terms. `sameTerm(?v, c)` and
   `sameTerm(?v, ?w)` are id equality (RDF term identity, ids injective:
   `TermIdTheorems.toId?_eq_iff`).
2. `STRSTARTS(?v, "s")` with a simple literal without U+0000: the keys of
   class 3 (`xsd:string`) and 4 (`rdf:langString`) that start with
   `[class] ++ s` are one rank range of the dictionary,
   `[lowerBound P, lowerBound (P ++ [0xFF]))` (no key holds 0xFF), so a
   dictionary literal of those classes passes exactly when its rank is in
   one of the two ranges: no dictionary read per row (q16: 21.9 ms warm, was
   674 ms reading every label). `STRENDS`, `CONTAINS` test the key bytes.
   Any other id goes to the reference evaluator.
3. Any other admitted expression: the reference evaluator
   (`ebvOrFalse (Expr.evalIn {} mu e)`, the FILTER of
   `QueryPattern.lowerWith`) on the decoded terms of the variables it reads,
   once per distinct tuple of ids (memo keyed by the ids; ids are injective,
   so equal ids give equal terms). `FILTER(?x = 72)` over `"72"^^xsd:int` is
   decided here, by value: `?age >= 72` in q11 gives the oracle's 34 rows;
   the gate fixture's `FILTER(?a = 72)` keeps `"72"^^xsd:int`,
   `"072"^^xsd:integer` (a dictionary term, non-canonical) and
   `"72.0"^^xsd:decimal`, as the reference engine does.

Proved: `IdQueryTests.ebvOrFalse_evalIn_and`: a FILTER of `a && b` keeps a
row exactly when the FILTERs of `a` and `b` both do, so conjuncts are applied
one by one (axioms `propext`, `Classical.choice`, `Quot.sound` at most).
Tested (`#guard`s in `IdQueryTests.lean`, on 23 sample terms: IRIs, blank
nodes, simple, string, language-tagged and typed literals, inline and
dictionary integers, decimal, double, booleans): rule 1 against
`Expr.evalIn` for every constant and term; the key-byte string tests and the
rank-range rule against STRSTARTS, STRENDS, CONTAINS; `DictRange.lowerBoundM`
against its definition on an encoded dictionary.

Defect found in the reference evaluator (needs an issue): `Expr.evalIn`
reads a bound numeric or boolean literal as its value (`literalPromote`),
and `sameTerm` then compares values and forms: `sameTerm(?v, "72"^^xsd:integer)`
with `?v` bound to `"72"^^xsd:integer` is false, and `"01"^^xsd:integer`
against `"1"^^xsd:integer` is true. W3C `expr-builtin/sameTerm-simple`
expects 14 rows; `l4factoidal query` answers 18 over the original Turtle.
The id path answers 14 (term identity). The sameTerm `#guard` excludes the
promoted datatypes and says why.

ORDER BY is section 15.1 as the reference evaluator orders
(`sparqlOrderValue` of `Expr.evalIn` of the variable). A column of only
blank nodes and IRIs is sorted by id (key order is class byte, then UTF-8,
which is code point order, `strCompare`); a column of only inline integers by
bits 55..0 (value + 2^55 for every integer datatype); any other column by
the numbers of its distinct values sorted with `sparqlOrderValue`. Both
shortcuts are `#guard`ed against `sparqlOrderValue` on the samples. q07 is
in code point order (QLever's ICU order differs, record 3.3).

## 7. What failed on the way, and what Lean taught

- **A second reference makes every append copy.** The first printer took
  the output buffer, returned `none` for some keys and then the caller
  appended to the same buffer: the buffer had two references during the
  call, and each append inside copied the whole output. q19 (39,768 rows)
  took 3.7 s; deciding the key's shape first, so that each branch holds the
  buffer once, made it 0.36 s. Same class as the stage 2 and 3 records'
  shared hash set and `remaps[k]!`.
- **Heap fragmentation costs time here.** A dictionary page cache of 64
  `ByteArray`s per page raised q19's peak RSS to 98 MB against 31 MB with no
  cache, and was slower: on this VM `clear_page_erms` (first touch of new
  memory, transparent huge pages) was 50 % to 67 % of the profile. One packed
  `ByteArray` per page: 48 MB, 0.36 s.
- **`for` loops with several mutable variables allocate per iteration.** The
  first word decoder (`for` with `acc`, `ended`, `i`) spent 22 % in
  `mi_malloc`/`mi_free`; the same loop as a tail call with every value an
  argument (`FrameWords.deltaGo`) does not allocate, and q03 warm went from
  2.0 ms to 0.8 ms; decoding only the key range of the other columns, 0.6 ms.
- **An `Option` pair per varint.** `Column.decodeColumnAt` (proved) returns
  `some (n, i)` per varint and builds an `Array Nat`; `FrameWords` keeps it
  as the reference and is tested equal on every frame of the generation.
- **A doc comment cannot precede `#guard`** (parse error); use `/- -/`.
- **Process start-up is a fixed cost here.** `l4sbm11` with no arguments
  takes 18 to 21 ms (median of 9) against 10 to 12 ms for `l4qlvr`; most of
  it is kernel page faults while the 11 MB binary initialises its modules.
  The process targets of the small queries cannot be met while that is so.

### 10.1 Fragment

The parser builds `{ base OPTIONAL { g1 } ... OPTIONAL { gk } FILTER(f) }` as
`filter f (leftJoin (... (leftJoin base g1 true) ...) gk true)`, with the
FILTERs of each group around that group. Admitted:

- the base: a group of section 2.1 (triple patterns, group joins, FILTERs,
  one level of GRAPH), with at least one triple pattern;
- each OPTIONAL group: triple patterns of the default graph and
  `backendLocal` FILTERs whose variables the group's own triple patterns
  bind; no GRAPH, no nested OPTIONAL, UNION or MINUS;
- a variable of a group that the base's triple patterns do not bind occurs in
  no other group; a FILTER beside the OPTIONALs reads only variables of the
  base's triple patterns. So every variable that a group shares with
  anything outside it is bound by the base, in every left row (the
  well-designed patterns of Pérez, Arenas and Gutierrez, "Semantics and
  complexity of SPARQL", 2009), and no group uses a variable that an earlier
  group binds;
- projection, `*`, `COUNT(*)`, `COUNT(?x)`, GROUP BY, ORDER BY, DISTINCT,
  LIMIT, OFFSET as in section 2.1, over the variables of the base and of the
  groups.

Refused, so the reference fallback answers (gate `ref-optional-*`): a nested
OPTIONAL; a variable two groups share that the base does not bind; a FILTER
in a group over a variable of the base; a FILTER beside the OPTIONAL over a
group variable (`FILTER(!BOUND(?f))`); OPTIONAL before the triple patterns
(`Join(LeftJoin({}, P1), P2)`); GRAPH in a group.

Why a group's FILTER may read only the group's variables. SPARQL 1.1 section
18.2.2.5 makes `OPTIONAL { P FILTER(F) }` the `LeftJoin(G, P, F)` of section
18.5, F evaluated on the merged solution. Until 2026-10-13 the reference
evaluator (and the F* engine, which still does) evaluated
`LeftJoin(G, Filter(F, P), true)`, F on the group's row only, so a base
variable in F read as unbound
(https://github.com/danbri/factoidal/issues/815, known-defects case
`SPARQL-OPT-FILTER-SCOPE`, now an F* defect). When F reads only variables
that every row of the group binds, the two readings give the same answer
(`leftJoin_filter_right`), and the id path equals the reference. The Lean
parser now builds `LeftJoin(G, P, F)` (`optionalGroup`; theorems
`evalIn_optionalGroup_filter` and `conjunction_true_iff` in
`SPARQL/OptionalFilterScope.lean`), and `IdQuery.flattenOptional` reads that
condition: it admits F when F reads only the group's variables and refuses it
otherwise, so `ref-optional-filter-outer.rq` takes the reference fallback,
which answers section 18.2.2.5. Admitting a base variable in F on ids is
open.

### 10.2 Algorithm

1. The base: `evalBgpM`, then its FILTERs and the FILTERs beside the
   OPTIONALs (each output row has its left row's values on the base
   variables, so a FILTER over them can run before the joins). A base of one
   pattern is scanned sorted on a variable it shares with the first group.
2. Per group, in order: `evalBgpM` of its patterns (the first scan sorted on
   the left table's sort variable when the group has that variable), the
   group's FILTERs on its rows, then `OptJoin.leftOuterJoin`:
   - inner pairs of left and right row indices with equal shared columns,
     in left-row order and per left row in right-row order: `Qlvr.mergeGo`
     when both tables are sorted on a shared variable, else a hash index of
     the right rows probed in left-row order (the cross product when no
     variable is shared);
   - `outerPairs`: each left row with its pairs, else the row with `none`;
   - output columns: the left columns gathered by the left indices, the
     right variables the left does not have gathered by the right indices,
     id 0 (`OptJoin.unbound`) for `none`. The left row order and sort
     variable are kept, so the next group can merge again.
3. Then section 2's steps. Id 0 is no term id (`TermId`: tags 1 to 5 and 14)
   and no column holds graph id 0, so: the renderer leaves an id 0 binding
   out; ORDER BY maps it to the error value, which section 15.1 orders first,
   as the reference does; DISTINCT and GROUP BY compare it as an id (one
   value); `COUNT(?x)` counts the rows where `?x` is not 0
   (`countItems`, SPARQL 1.1 section 18.5 Count).

The right side is scanned in full: d11 reads all 197,044 `dbo:deathDate`
rows for 1,083 left rows. Using the left keys to skip right blocks is
https://github.com/danbri/factoidal/issues/809; nothing here blocks it (the
right scan is `evalBgpM` with a preferred sort variable). Since section 11
(2026-10-13) the group's first scan takes the left keys as candidates when
the rule of section 11.1 selects it.

## 11. Sideways information passing (issue 809, 2026-10-13)

Issue: https://github.com/danbri/factoidal/issues/809 (ordered by the owner
on 2026-10-12: "Yes 809"). Measurement and proposal: the issue body. Before
this change every right scan of a join read and decoded the whole key range
of its predicate and built a `Table` of all its rows, then joined: DBpedia
d05 decoded 4.0 million rows for 1,130 answers. Method: Neumann and Weikum,
"Scalable join processing on very large RDF graphs", SIGMOD 2009.

Code: `Storage/Sbm11/Sip.lean` (the frame-level search and gather),
`IdQuery.lean` (`sipRange`, `sipChunk`, `scanBlockSipM`, `scanFoldSipM`,
`scanSipTableM`, `sipRule`, `sipCands`, `scanForJoinM`; the planner calls
`scanForJoinM` for every join scan), `Harness/Sbm11Query.lean` (`--sip`).
Theorems: `SipTheorems.lean`, `SipScanTheorems.lean`,
`SemiJoinTheorems.lean`.

### 11.1 The rule

A scan takes candidates when all of these hold (`IdQuery.scanForJoinM`):

- it is the right scan of a join (inner join, merge or hash), or the first
  scan of an OPTIONAL group's BGP (the left outer join of section 10);
- its sort variable `v` (the column after its key) is a variable of the left
  table;
- `16 × left rows < estimate`, the estimate being the PRM1 rows of the
  scan's selected blocks (`sipRule`, factor `Store.sipFactor`). At sixteen,
  a block of 4,096 rows holds on average fewer than 256 candidate rows. The
  scan still decodes the join column of every block it reads, so the
  saving is in the other columns, in the blocks no candidate can match, and
  in the rows the join does not read. No other factor was measured; section
  11.5 has one case where every block holds a candidate (no block skipped),
  and it is still faster than the full scan;
- the candidates pass two checks at run time (`sipCheck`): they are in
  non-decreasing order, and every value of the left column `v` is a
  candidate. The candidates are the distinct values of that column, in
  order (the column as it is when the left table is sorted on `v`, else
  sorted by `mergeSortBy`). The proofs use only the two checks; the sort has
  no theorem (`SipScanTheorems.sipCands_sound`).

Otherwise the full scan runs. `l4sbm11 query --sip auto|always|off`: `auto`
is the rule above (default), `always` uses factor 0 (candidates whenever
the join shape allows them; for tests), `off` never. `--explain` adds
`sideways ?v: K candidates, blocks skipped B, key values tested T, rows
gathered G` to each scan with candidates, and a last line `total: rows
decoded ...` (of a full scan the rows of its table, of a scan with
candidates the rows gathered).

### 11.2 Algorithm

Per block of the scan (`scanBlockSipM`), after the PRM1 tests of
`scanBlockM` (key prefix, `blockPlan`):

1. **Block skipping.** `sipRange` gives the values the join column can hold
   in the block's rows with the key prefix: from the first row's value when
   the first row carries the prefix (else 0) to the last row's value when the
   last row carries it (else the largest word). `Sip.mayHold` with a binary
   search hint (`lbHint`) decides whether a candidate lies in that range; if
   not, the block is not read.
2. **The join column alone.** The needed frames and the join column's frame
   are read (one positioned read). `Sip.findWords` decodes the join column:
   a delta frame (the codec of a sorted id column) value by value with no
   output for a row that does not match; a raw or constant frame through
   `FrameWords.decodeWords` and then the same loop over words. Each value in
   the key range is tested with a candidate pointer: from the pointer, the
   first candidate not below the value (`probeFrom`); the value is a
   candidate when that candidate equals it. The pointer starts at the
   block's binary search hint and moves forward with the values (the key
   range is in order of the join column). The test answers membership from
   any start value (`probe_mem`), so the hint is not part of the
   correctness argument. Values of a delta frame can only be decoded in
   order, so the search over the rows is a merge (a galloping search over
   the rows needs random access to the values); over the candidates the
   pointer advances one candidate at a time, at most once per candidate per
   block.
3. **The other columns at the found rows.** `Sip.gatherWords` decodes each
   other needed column at the found rows only: a delta frame in one pass
   that stops after the last found row and writes nothing for the other
   rows; a raw or constant frame through `decodeWords`, then by index. Key
   columns already decoded for the key range are picked by index
   (`pickWords`). The found values of the join column are the column itself.
4. `chunkOfCols` with the found rows, as `blockChunk` does with the key
   range.

No `Table` of the whole key range is built. With a delta overlay (stage 5)
a block that holds overlay rows is merged as before and its chunk filtered
(`sipFilterChunk`); this branch has tests and no theorem (L7e is open for
the full scan too). A scan with candidates runs on one thread (the parallel
block scan of https://github.com/danbri/factoidal/issues/799 is for full
scans).

Every new loop is a tail call with fuel (`deltaFindGo`, `wordsFindGo`,
`deltaGatherGo`, `advGo`, `lbHintGo`, `sortedGo`, `dedupGo`, `allMemGo`)
or an `Array.foldl` (`pickWords`); the C has `goto _start` for each.

### 11.6 What failed on the way

  query as refused. `--sip` is now passed only when `SBM11_SIP` is set. Found
  before the run, by reading the script against the base build's

### 12.1 What runs on ids now

`translate` first flattens the WHERE clause as before (BGPs, group joins,
FILTERs, one level of GRAPH, the top-level OPTIONALs of section 10). Then:

1. **Residual FILTERs.** A FILTER conjunct that is EXISTS-free but not
   `backendLocal` (REGEX, LANGMATCHES, casts such as `xsd:integer(?x)`,
   IRI(), STRDT, STRLANG, hash functions, UUID), or that reads a variable no
   pattern of the WHERE clause binds (`FILTER(!BOUND(?zz))`), is a residual
   conjunct (`FKind.residual`). It is evaluated by the reference FILTER on
   the decoded terms of the variables it reads, once per distinct tuple of
   ids (a memo keyed by the ids; 0 for an unbound variable), after all
   triple patterns of the BGP are joined. A conjunct is admitted only when
   every variable it reads is bound in every solution of its group
   (`scopeVars`: the triple-pattern variables of the group and the `?g` of
   each `GRAPH ?g` inside it) or is bound by no pattern of the whole WHERE
   clause (`whereVars`). Then its value on a row of the joined BGP is its
   value on the group's row that the joined row extends, which is the scope
   SPARQL 1.1 section 18.2.2.6 gives it. A conjunct that reads a variable
   bound outside its group (`{ ?s ex:age ?a { ?s ex:name ?n FILTER(?a > 1) } }`,
   or `?g` inside its own `GRAPH ?g`) is refused: inside the group the
   variable is unbound, after the joins it is bound.
2. **FILTERs beside OPTIONALs.** `{ base OPTIONAL { g } FILTER(f) }` is
   `Filter(f, LeftJoin(base, g))`. When `f` reads only base variables it is
   applied to the base rows, as in section 10; otherwise it is applied after
   the left joins, as a residual conjunct on the rows they output
   (`Plan.postFilters`; an id `OptJoin.unbound` is an unbound variable). A
   FILTER inside an OPTIONAL group that reads a base variable stays refused
   (https://github.com/danbri/factoidal/issues/815).
3. **The reference post-processing** (`PostSpec`). Every ASK and CONSTRUCT,
   and every SELECT that the id projection does not run (a SELECT
   expression, an aggregate other than COUNT, COUNT DISTINCT, HAVING, GROUP
   BY or ORDER BY an expression, REDUCED, a trailing VALUES block, a WHERE
   clause with no triple pattern), runs the WHERE clause on ids, decodes the
   rows into solution mappings (`decodeRowsM`; every variable of the WHERE
   clause, each distinct id decoded once), and calls the reference
   evaluator's own post-WHERE function on that sequence (section 12.2). A
   WHERE clause with no triple pattern is one solution with no binding,
   then its FILTERs. Refused: an EXISTS or NOT EXISTS anywhere outside the
   WHERE clause (`Query.expressionsOutsidePatternExistsFree`: it reads the
   active graph, which the id path does not build), and DESCRIBE (its
   description reads statements that no pattern of the query selects).
4. **The first rows only.** `firstRowsOf` gives the number of WHERE
   solutions the answer reads: 1 for an ASK with no GROUP BY, HAVING,
   trailing VALUES, OFFSET or LIMIT; OFFSET + LIMIT for a SELECT or
   CONSTRUCT with LIMIT and no grouping, ORDER BY, DISTINCT, REDUCED or
   trailing VALUES. `whereTableM` then keeps that many rows; a single
   pattern streams and its scan stops after them.

COUNT(*) and COUNT(?x) with GROUP BY variables stay on ids as before
(`selectOnIds`, the counted path).

### 12.2 The reference function of each step, and what is left to prove

### 13.1 The interface

`IdQuery.Store` no longer gives the engine the whole PRM1 array:

| Until issue 805 | Now |
| --- | --- |
| `metas : Nat → ExceptT String m (Array BlockMeta)`: every PRM1 entry of a permutation; the engine selected the blocks of a key with `blocksFor` | `blockCount : Nat → ExceptT String m Nat`: the block count of the PRM1 header (for the statistics) |
| | `blocksForRange : Nat → Array UInt64 → ExceptT String m (Array BlockMeta)`: the entries of the blocks of a permutation that may hold a row with the key prefix, in row order; the reference is `IdQuery.metasFor metas key = (blocksFor metas key).map (metas[·]!)` |

The scans (`scanFoldM`, `scanFoldSipM`) loop over the positions of the
returned array with the body they had (`scanBlockM`, `scanBlockSipM`); the
estimate of a pattern is `selRows` of that array (the rows of the selected
blocks, as `estimate` was); `divide?` and the parallel scan of
`Harness/Sbm11Query.lean` cut those positions into ranges. The plans did
not change: `--explain` gives identical plan lines (estimates, block counts,
join order) before and after on all 40 queries of section 13.4.

### 13.2 The search

`L4Factoidal/Storage/Sbm11/PrmRange.lean`. A `Reader` gives the block count,
the entry of one block and the entries of a range of blocks. `rangeM`:

1. `lo`: the first block whose last row is not below the key prefix, by
   `searchM`, a binary search with fuel `log2 n + 2` that reads one entry
   per probe (the search of `firstBlockGo`);
2. `hi`: the first block from `lo` whose first row is above the key prefix,
   by the same search;
3. the entries of blocks `[lo, hi)`, by one read.

`arrayReader ms` reads an array (the in-memory store of the tests and
theorems). `bytesReader read count` reads a PRM1 file through `read off len`,
a positioned read: one entry is the 92 bytes at `22 + 92 k`, a range the
`92 (hi - lo)` bytes at `22 + 92 lo`. `openM` reads the 22-byte header
(magic, version, permutation code, block count) and checks the file length
of the manifest against `22 + 92 count`.

The query session (`Sbm11Query.Session.perm`, `Session.rangeFor`) opens a
permutation with `openM`: under `none` one `pread` of 22 bytes; under
`merkle` the PRM1 `.merkle` sidecar is read and its leaves checked against
the manifest root first, and every PRM1 read goes through the file's
verified chunk cache (a 65,536-byte chunk is read once and checked by its
Merkle proof). `rangeFor` runs `rangeM (bytesReader read count) key` and
keeps the answer for the key (at most 256 keys per permutation; the
generation does not change while the session is open). For d01 the SPO
search reads 31 entries and the header: 2,874 PRM1 bytes.

What the query path checks of PRM1: before, `decodePrmAt` checked the whole
file's admission (`prmAdmitted`: blocks sorted, contiguous, fields in range)
at every open. Now the reader checks the header, the file length and that
each entry it reads decodes; the order of the blocks, which the binary
searches need, is what activation (`l4sbm11 activate`, `verify`) checked
for the files that `CURRENT` names, and under `merkle` every byte read is
the byte the manifest's Merkle root commits to. Each block that a scan reads
is still checked against its PRM1 entry (`decodeBlockAt`: first and last
row, order, frame lengths).

### 13.3 What is proved

`L4Factoidal/Storage/Sbm11/PrmRangeTheorems.lean` (lemmas L4a′ and L2d′ of
the end-to-end record, section 13 there):

- `searchPure_spec`: the binary search over a test that is monotone below
  `n` (false, then true), with `h - l < 2^f`, returns the least index of
  `[l, h)` where the test holds, or `h`; `searchM_pure`: `searchM` with
  probes that answer a pure test is that search; `searchPure_firstBlockGo`:
  the first search is `IdQuery.firstBlockGo`.
- `rangeM_array` (L4a′): over the PRM1 entries of an admitted permutation
  (`prmAdmitted`), `rangeM (arrayReader ms) key = pure (metasFor ms key)`.
- `rangeM_bytes` (L2d′): when `PrmAt.decodePrmAt b = some (p, ms)` and
  `read off len` returns `b.extract off (off + len)`, `openM` gives
  `ms.size` and `rangeM (bytesReader read n) key = pure (metasFor ms key)`:
  the binary search over positioned reads gives the same entries as decoding
  the whole file and selecting. Parts: `openM_bytes`, `entryOfM_bytes`,
  `sliceOfM_bytes`, `entryAt_extract` (an entry read from a slice of the
  file is the entry at the shifted position), `decodePrmAt_some`.
- `scanFoldM_tuples_prm`: lemma L4e for a store whose `blocksForRange` and
  `blockCount` are `rangeM` and `openM` over positioned reads of a PRM1 file
  that decodes; the PRM1 admission is not a hypothesis (it follows from the
  decoding).
- L4e and L4i (`ScanFoldTheorems.scanFoldM_tuples`, `scanFoldM_columns`,
  `SipScanTheorems.scanFoldSipM_tuples`, `scanFoldSipM_filter`) are restated
  with the hypotheses `st.blocksForRange spec.perm spec.key = pure (metasFor
  ms.toArray spec.key)` and `st.blockCount spec.perm = pure ms.length` in
  place of `st.metas spec.perm = pure ms.toArray`; `forIn_metasFor` turns
  the loop over positions into the loop over `blocksFor`.

No hypothesis restates its conclusion: the hypotheses are the decoding of
the PRM1 file, the admission of the permutation, the definition of the
store's reads, and the activation checks of L4e. `#print axioms` of
`rangeM_array`, `rangeM_bytes`, `scanFoldM_tuples_prm`, `scanFoldM_tuples`,
`scanFoldM_columns`, `scanFoldSipM_tuples`: `propext`, `Classical.choice`,
`Quot.sound`. Not proved: that the host's `pread` and the verified chunk
reader return the file's bytes (the I/O boundary).

### 13.7 What failed on the way

- **A `simp` that did not terminate.** `decodePrmAt_some` first called
  `simp [..., hsz]` with `hsz : b.size = 22 + 92 * rd64 b 6` in the simp
  set. The whole file then needed 13.8 GB and was killed by the

  6 GB guard found the one call; with `hsz` out of the simp set the whole
  file checks with a peak of 1.3 GB.
