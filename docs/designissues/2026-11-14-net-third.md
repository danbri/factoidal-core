# Networking, third phase (2026-11-14): service workers, cookies on the network, element requests, WebSocket

Follows `2026-11-14-net-svg.md`. Every decision below is made in Lean; the hosts move bytes.

## Service workers (`Net/ServiceWorkerScope.lean`, prelude)

`navigator.serviceWorker` registers a worker on the dedicated worker core: the script runs in a
`ServiceWorkerGlobalScope`, then `install` and `activate` run as extendable events, and the
registration's `installing`, `waiting` and `active` follow, with `statechange` and `updatefound`.
`Client.postMessage` and `ServiceWorker.postMessage` cross as bytes, as a dedicated worker's
messages do. No `fetch` event is dispatched and no page is controlled (`controller` is null):
requests never go through a service worker. Registrations live in the page session's memory.

Lean decides `register()`'s URLs (web_api 154): an `http`/`https` script with a potentially
trustworthy origin, script and scope of the document's origin, no encoded `/` or `\` in their
paths, and the scope within the script's directory (a `Service-Worker-Allowed` field never widens
it). Matching a client URL (web_api 155) takes the longest registered scope that is a prefix.

The WPT runner loads `.any.serviceworker.html` over HTTPS, as the WPT manifest does
(`force_https`).

## Cookies on the network (`Net/Cookies.lean`, `Net/PageFetch.lean`, `Net/Xhr.lean`)

One in-memory jar a page session (`Net.Xhr.State.cookies`) serves `document.cookie` and the
network. A request made with credentials (Fetch §4.5: not "omit", and "include" or the page's
own origin; never on the Hub, whose browser has its own jar) carries the jar's cookies for its
URL's host, path and scheme; a cross-site request carries only `SameSite=None` cookies; a
preflight carries none. The answer's `Set-Cookie` fields are stored before the next hop is
planned; a response to a cross-site request sets only `SameSite=None` cookies. Nothing is
written to disk. The scriptSession action `cookies` empties the jar for the test driver
(WebDriver "Delete All Cookies"); no web_api op does it.

## Element requests for hosts (`Net/Subresource.lean`, document op `subresource`)

A host that loads a page asks the engine for each image, font, sheet, script or media request,
one step a call: the engine answers the request to make, a failure, or done; the host makes
each request and keeps the bytes. No-cors without `crossorigin`, cors with it; scheme, local
address, DNS pin, mixed content, redirects, CORS, `Referer` and `Sec-Fetch-*` are
`Net.PageFetch`'s. A cross-origin no-cors answer is marked opaque: the engine may draw it, a
script may never read it. No cookies. The hosts are wired by the pages work.

## WebSocket (`Net/WebSocket.lean`, web_api 156 to 161)

The URL (`ws`/`wss`, `http`/`https` mapped, no fragment, never `ws:` from an `https` page), the
subprotocols (tokens, no repeats), a blocked port, the address rules of the page's requests (the
connection's `http`/`https` form goes through `PageFetch.plan`), the opening handshake
(`Sec-WebSocket-Accept` with HACL* SHA-1, no extension, a subprotocol only if asked for), the
frames (client frames masked with fresh entropy; server frames unmasked, no RSV bit, known
opcodes, whole control frames of at most 125 bytes, text in UTF-8), ping/pong, the closing
handshake and `close()`'s arguments are Lean's. The host opens one TCP or TLS connection, writes
what the engine gives in order and hands back what it reads. The WPT runner connects only to
wptserve's `ws`/`wss` ports by WPT's names; the desktop host (`native_net.ts`, `run_html.ts`)
connects to the address the engine chose, TLS checked against the URL's name (tested against a
local echo server with the RFC 6455 key); the Hub has no sockets yet and fails such connections
without sending anything.

## EventSource (`Net/EventSource.lean`, web_api 162)

The request is a page request (CORS, credentials, the address rules, `Last-Event-ID`), made
through an `XMLHttpRequest` class of the realm's own; whether the answer is an event stream
(200, `text/event-stream`) and its events (BOM, line ends, comments, fields, dispatch, the last
event ID carried over) are Lean's. The stream is read when the response ends, then the
connection is made again after the reconnection time.
