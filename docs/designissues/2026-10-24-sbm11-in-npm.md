# SBM11 in the wasm module and npm, for Node and the browser

Status: stages approved by the owner on 2026-10-25 (OKR https://github.com/danbri/factoidal/issues/1009). Stage 1 landed with section 6. Stage 2 in part (the pack in memory): section 7.
Date: 2026-10-24. Base: `main` at `87033eb`.
Issue: https://github.com/danbri/factoidal/issues/1007. Related: https://github.com/danbri/factoidal/issues/1006.

Owner, 2026-10-24, verbatim:

> "SBM11 should be in NPM. NPM is usable from webplatform and node. And all CLIs should be built from facilities exposed via API too."

> "For example https://danbri.github.io/londat/docklands/ uses Factoidal statefully in browser, storing data on browser disk, and exposing SPARQL to app. This should use our latest storage paradigm which is SBM11!"

## 1. State on 2026-10-24

- SBM11 is the Shardborough baseline (owner, 2026-10-12: "Consider smb11 our baseline for shardcore").
- The wasm module has no SBM11 operation. In the npm 0.13.0 wasm, the string "SBM11" occurs 3 times, each in a refusal message (for example "IBK4 and IBK5 store no named graph without a triple ... use SBM11").
- The npm command `factoidal` packs and queries IBK3, IBK4 and IBK5 only (`PACK_LAYOUTS` in `npm/factoidal/bin/factoidal.mjs`; default IBK3 until 2026-10-25, IBK5 since). The IBK3 layout kept a repeated triple: https://github.com/danbri/factoidal/issues/1006 (fixed).
- Every SBM11 command is a native Lean executable under `formal/lean4/Harness/` (`Sbm11Cli`, `Sbm11Pack`, `Sbm11Query`, `Sbm11Update`, `Sbm11Compact`, `Sbm11Export`, `PlannerSbm11IO`). `Wasm/build-wasm.sh` skips every `Harness_*` translation unit. So no SBM11 command is built from an API operation, which the owner's rule above requires.
- `docs/designissues/2026-10-12-parallel-block-scans.md`: "WASM: the SBM11 query harness is native only (`Harness/Sbm11*`, file `pread`)".
- The consumer named by the owner: https://danbri.github.io/londat/cwplans/kg/ (linked from the Docklands page) loads `@factoidal/core@0.7.1` from jsDelivr, reads an IBK5 store (wire version 10, 1,046 predicate blocks, 44 MB) over HTTP, and keeps the blocks in Cache Storage. It writes nothing to browser disk.

## 2. What the Lean tree already gives

- The SBM11 read path is pure and takes its bytes through a read function in any monad: `PrmRange.bytesReader {m} [Monad m] (read : Nat → Nat → ExceptT String m ByteArray)`. `FileGenTheorems.store_written` proves that the store read through it over the files' bytes is `MemGen.store`, under the named assumption `ReadsWritten` (each positioned read returns the bytes the packer wrote).
- The pure packer specification `PackSpec.packSpec` with `den_packSpec`, `packSpec_written`, `packSpec_check` (issue https://github.com/danbri/factoidal/issues/776).
- The wasm boundary patterns for host IO: `Storage/GenerationVerify.lean` (a `Reader m` over artifacts that a host supplies), `Wasm/ExtHost.lean` (a host call-out realised by C and `EM_JS`), and the IBK store ops that take byte regions (`storeOpen` through `l4_call_blob_io`).

## 3. Positioned reads per host

| Host | Positioned read | Write |
|---|---|---|
| Node, Deno | `fs` read at offset | `fs` write |
| Browser, dedicated worker | OPFS `FileSystemSyncAccessHandle.read({ at })` | OPFS `write({ at })`, `flush()` |
| Browser, remote store (londat kgx) | HTTP `Range` request | none |

The module asks for `(file, offset, length)` and gets bytes. The host never decides a format, a name or a digest (iron rule 7).

## 4. Stages

1. SBM11 query in wasm. Move the query front-end out of `Harness/` into a library module with no `IO.FS` (a session over a host read function), and add ops `sbm11Open`, `sbm11Query`, `sbm11Close`. Node host over `fs`. Exit: `tests/sbm11/census.sh` queries give the same answers through the wasm ops as through `l4sbm11` on the same generation.
2. SBM11 pack in wasm. The packer over host-supplied input chunks and host writes, as `Wasm/Ops/Pack.lean` does for IBK. `factoidal pack` defaults to SBM11. Exit: byte-identical generation against `l4sbm11 pack` on the corpus ladder; the cases of `test/pack-is-a-set-1006.test.mjs` pass for SBM11.
3. Update, delta log and compaction in wasm. `factoidal update` and `compact` on SBM11.
4. Browser store in OPFS. A worker host over `FileSystemSyncAccessHandle`; pack, query and update persist across reloads. A remote read-only host over HTTP `Range`.
5. Commands built from the API. `l4sbm11` subcommands become thin callers of the same ops; the entry-point gate maps `cli:pack`, `cli:query`, `cli:update`, `cli:compact` to registered stages.
6. Consumer. londat `kgx` packed as SBM11 with the new engine; `cwplans/kg/worker.js` on the SBM11 ops.

## 5. Risks

- Wasm32 memory: SBM11 uses 64-bit term ids and the native path uses a worker pool and page caches sized for a 4-vCPU VM. The wasm session needs bounded caches and one thread at first.
- The native path reads with `pread`; the proof assumption `ReadsWritten` is the same for a host read function. Session caches are not covered by a theorem on either path.
- Packing is memory-bound (`docs/designissues/2026-09-05-shard-pack-profile-and-memory.md`); a browser pack is for small and medium inputs until a streamed SBM11 pack is measured.

## 6. Stage 1 as built (2026-10-25)

- `L4Factoidal/Storage/Sbm11/HostSession.lean`: the query session over a `Host` value (`readAt file off len`, `size file`). No `IO.FS`, no thread, no extern. It decodes with the library functions the native session uses (`Dict.pageM`, `Dict.lookupM`, `DictRange.lowerBoundM`, `PrmRange.openM`, `PrmRange.rangeM` over `bytesReader`, `GraphList.decodeAt`) and runs the same engine (`IdQuery.translate`, `runPlanM`, `runPostM`, `IdGroup.runNestedM`, the reference evaluator over `selectedDataset`). It resolves `CURRENT` by the rule of `Harness.GenerationPointer.resolveStoreDirectory`.
- `Wasm/HostRead.lean`, `ffi/l4_hostread.c`: the two host call-outs. Emscripten: EM_JS onto `globalThis.__factoidalReadAt(source, file, off, len)` and `__factoidalFileSize(source, file)`. Native: `pread` of `source/file`.
- `Wasm/Ops/Sbm11.lean`: ops `sbm11Open`, `sbm11Query`, `sbm11Close` (callIO). `l4factoidal sbm11-query GEN` calls them natively.
- npm: `openSbm11(source)` and `registerSbm11Source(source, reader)` (`lib/sbm11.mjs`; Node reader `lib/sbm11-node.mjs`).
- Measured: `SBM11_HOST=1 tests/sbm11/census.sh` over the W3C SPARQL 1.0 and 1.1 evaluation tests: 605 executed; for 605 of 605 the ops gave the bytes and the path of `l4sbm11 query` (597 on the id path, 8 on the reference fallback). npm: `test/sbm11-host.test.mjs` over `test/fixtures/sbm11-tiny` (13 queries, expected bytes from native `l4sbm11 query`).
- Olympics (1,781,625 triples, packed by `l4sbm11-pack`), `tests/sbm11/host_compare.sh` over the 21 oracle queries of `tests/qlvr/queries`: 21 of 21 with the same bytes and path as `l4sbm11 query --threads 1`, and the same time within the variation between runs (q19 200 ms against 196 ms, q20 203 against 232, q21 294 against 277, 2026-10-25, 2-vCPU container). Two repairs were needed for that: the result bytes leave the op as the out region of `l4_call_blob_io` and not as a JSON string (q20 writes 18.8 MB), and each query runs on references of its own (`Session.localize`; record in `skills/lean4-performance` section "Values that two threads can reach").
- Not in stage 1, each tracked on https://github.com/danbri/factoidal/issues/1009: the Merkle check of each read (`Verify.merkle`; this path checks lengths, as `Verify.none` does natively); the delta-log replay (stage 3; a generation with a log is refused at open); the OPFS reader (stage 4); threads.

## 7. Stage 2 as built (2026-10-25): pack in memory

Status: the first part of stage 2 landed. The pack is in memory; the streamed pack over host chunks and host writes, and `factoidal pack` on SBM11, are not done.

- `L4Factoidal/Storage/Sbm11/PackBytes.lean`: `packFiles h qs decl sourceBytes sourceSha` gives every file that `l4sbm11-pack` writes into its output directory, as `(name, bytes)`: the ten or eleven data files (GDV1, GDX1, GNL1 when there is a named graph, PRM1 and PRB1 per permutation), a `.merkle` sidecar per file, and `manifest.sbm11`. It does not give `CURRENT`, which activation writes. `packText h fmt base text` reads the document as one `Dataset` through `Source.parseDocument` (RDF 1.2) and packs it. The bytes come from the functions the native packer calls (`PackStream.Pages.push`, `PackStream.Cut.push`, `encodePrm?`, `GraphList.encode?`, `encodeManifest?`, `BlockMerkle.leafWith` and `rootWith`), over arrays in memory in place of run files. The hash is a parameter (`BlockMerkle.Hasher`): the `#guard`s use pure Lean SHA-256, the op and the native check HACL* SHA-256. Every walk over input-sized data is a tail call with fuel or `Array.foldl`; the sort is `Qlvr.mergeSortBy`. The `#guard`s check the file count, that the manifest decodes, and that GDV1, GDX1, PRM1 and PRB1 equal the bytes of `PackSpec.packSpec`.
- `Wasm/Ops/Sbm11Pack.lean`: blob-IO op `sbm11PackFiles(syntax, base, index)`, the document as the IN region, file `index` as the OUT region with `{"index","count","name","bytes","quads","terms","graphs"}`. The module keeps the files of the last document (one memo entry), so a host that asks for index 0 to `count - 1` with the same document packs once; the answer for the last index clears the memo. `l4factoidal sbm11-pack SOURCE OUTDIR` calls the op natively.
- npm: `packSbm11(text, { syntax, base })` resolves to a `Map` of file name to bytes; `mapReader(files)` is a reader for `openSbm11` over files in memory (`lib/sbm11.mjs`). Test `test/sbm11-pack.test.mjs`; its pack cases skip on a wasm module that has no `sbm11PackFiles` op (the module is rebuilt in danbri/factoidal-builds).
- Measured, native: `l4sbm11 packfiles-check SOURCE GEN` compares every file. `test/fixtures/sbm11-tiny`: 23 of 23 files identical. `SBM11_PACKFILES=1 tests/sbm11/census.sh` over the W3C SPARQL 1.0 and 1.1 evaluation inputs (packed by `l4sbm11-pack --workers 1`): 605 of 605 generations with every file identical. `chinook.rml.nt` of the CSVW suite (62,765 triples, 6,047,143 bytes): 21 of 21 files identical, 1.5 s for parse, pack and compare. `third_party/qudt/QUDT-all-in-one-OWL.ttl` (130,404 triples): 21 of 21 identical against `l4sbm11-pack --via-dataset`; the default `l4sbm11-pack` (chunked Turtle reader) refuses this file at byte 640,783 (`prefix:Atto`, a prefixed name whose prefix is `prefix`), which the whole-document Turtle parser reads.
- Not done in stage 2: the streamed pack (input chunks in, files out as they are made); `factoidal pack` defaulting to SBM11; the cases of `test/pack-is-a-set-1006.test.mjs` for SBM11; a wasm build and the npm pack cases run against it.

## 8. The Merkle check on the host path (2026-10-27)

An external review of 0.18.0 found that `openSbm11` answered queries over a changed store with no error: `dict.gdv1` with "hello" changed to "HELLO" answered "HELLO"; `spo.prb1` with one changed bit answered no rows; `manifest.sbm11` with one changed bit near its end answered as before. The host session checked lengths only (the native `Verify.none`).

- `L4Factoidal/Storage/Sbm11/HostVerify.lean`: the decisions, pure. `admit h a sidecar`: the chunk size is 65,536 bytes, the `.merkle` sidecar has the manifest's count of 32-byte leaves, and the leaves rebuild the manifest's root; the proof table (`BlockMerkle.Tree`) is kept. `checkChunk h ad i bytes`: the chunk has the manifest's length and its proof reaches the root (`ChunkedArtifact.verifyChunkWith`). `HostVerifyTests.lean`: `#guard`s over a generation that `PackBytes.packFiles` packs, with one changed bit in GDV1, GDX1, GNL1, PRM1, PRB1, a sidecar, and each of the last 40 bytes of the manifest (chunk size, chunk count, root of `osp.prb1`); each is refused and the error names the file.
- `HostSession`: `openSession host v h`. Under `merkle` (the default of the ops) the open admits the sidecar of every file, so a changed Merkle reference refuses the open even for a file the query does not read. Every read is widened to its chunks; each chunk is checked once and kept (at most 256 per file, `MemoCache.insertEvict`). `none` keeps the earlier behaviour.
- Ops: `sbm11Open(source, optionsJson)` with `{"verify":"merkle"|"none"}`, envelope member `verify`. npm: `openSbm11(source, { verify })`, `store.verify`.
- Not bound: the manifest has no digest of its own. The session reads only the names, lengths and Merkle references, which the checks bind; the full-file SHA-256, the source length and digest, and the counts are checked by `sbm11Verify` (activation) only.
- Measured (wasm, Node, Apple M-series laptop, other agents running; medians of 5): chinook.rml.nt (62,765 triples, 1.19 MB packed): open 0.2 ms under both; a query that decodes every literal 105 ms (merkle) against 106 ms (none). 200,000 synthetic triples (6.0 MB packed): open 0.4 ms against 0.1 ms; the same query 1,140 to 1,179 ms against 1,166 to 1,178 ms; its first run 1,220 against 1,231 ms (62 chunk reads against 7,667 exact reads). The cost of the check is inside the variation between runs.
- Tests: native-smoke 402 of 402; `SBM11_HOST=1 tests/sbm11/census.sh` 605 of 605 with the bytes and path of `l4sbm11 query`; npm 1,792 pass, 0 fail, 1 skip (esbuild not installed).
