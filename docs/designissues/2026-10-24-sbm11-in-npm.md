# SBM11 in the wasm module and npm, for Node and the browser

Status: plan. Needs owner approval of the stages. No code changed with this record.
Date: 2026-10-24. Base: `main` at `87033eb`.
Issue: https://github.com/danbri/factoidal/issues/1007. Related: https://github.com/danbri/factoidal/issues/1006.

Owner, 2026-10-24, verbatim:

> "SBM11 should be in NPM. NPM is usable from webplatform and node. And all CLIs should be built from facilities exposed via API too."

> "For example https://danbri.github.io/londat/docklands/ uses Factoidal statefully in browser, storing data on browser disk, and exposing SPARQL to app. This should use our latest storage paradigm which is SBM11!"

## 1. State on 2026-10-24

- SBM11 is the Shardborough baseline (owner, 2026-10-12: "Consider smb11 our baseline for shardcore").
- The wasm module has no SBM11 operation. In the npm 0.13.0 wasm, the string "SBM11" occurs 3 times, each in a refusal message (for example "IBK4 and IBK5 store no named graph without a triple ... use SBM11").
- The npm command `factoidal` packs and queries IBK3, IBK4 and IBK5 only (`PACK_LAYOUTS` in `npm/factoidal/bin/factoidal.mjs`; default IBK3 until 2026-10-25, IBK5 since). The IBK3 layout kept a repeated triple: https://github.com/danbri/factoidal/issues/1006 (fixed).
- Every SBM11 command is a native Lean executable under `formal/lean4/Harness/` (`Sbm11Cli`, `Sbm11Pack`, `Sbm11Query`, `Sbm11Update`, `Sbm11Compact`, `Sbm11Export`, `PlannerSbm11IO`). `Wasm/build-wasm.sh` skips every `Harness_*` translation unit. So no SBM11 command is built from an API operation, which the owner's rule above requires.
- `docs/designissues/2026-10-12-parallel-block-scans.md`: "WASM: the SBM11 query harness is native only (`Harness/Sbm11*`, file `pread`)".
- The consumer named by the owner: https://danbri.github.io/londat/cwplans/kg/ (linked from the Docklands page) loads `@factoidal/core@0.7.1` from jsDelivr, reads an IBK5 store (wire version 10, 1,046 predicate blocks, 44 MB) over HTTP, and keeps the blocks in Cache Storage. It writes nothing to browser disk.

## 2. What the Lean tree already gives

- The SBM11 read path is pure and takes its bytes through a read function in any monad: `PrmRange.bytesReader {m} [Monad m] (read : Nat → Nat → ExceptT String m ByteArray)`. `FileGenTheorems.store_written` proves that the store read through it over the files' bytes is `MemGen.store`, under the named assumption `ReadsWritten` (each positioned read returns the bytes the packer wrote).
- The pure packer specification `PackSpec.packSpec` with `den_packSpec`, `packSpec_written`, `packSpec_check` (issue https://github.com/danbri/factoidal/issues/776).
- The wasm boundary patterns for host IO: `Storage/GenerationVerify.lean` (a `Reader m` over artifacts that a host supplies), `Wasm/ExtHost.lean` (a host call-out realised by C and `EM_JS`), and the IBK store ops that take byte regions (`storeOpen` through `l4_call_blob_io`).

## 3. Positioned reads per host

| Host | Positioned read | Write |
|---|---|---|
| Node, Deno | `fs` read at offset | `fs` write |
| Browser, dedicated worker | OPFS `FileSystemSyncAccessHandle.read({ at })` | OPFS `write({ at })`, `flush()` |
| Browser, remote store (londat kgx) | HTTP `Range` request | none |

The module asks for `(file, offset, length)` and gets bytes. The host never decides a format, a name or a digest (iron rule 7).

## 4. Stages

1. SBM11 query in wasm. Move the query front-end out of `Harness/` into a library module with no `IO.FS` (a session over a host read function), and add ops `sbm11Open`, `sbm11Query`, `sbm11Close`. Node host over `fs`. Exit: `tests/sbm11/census.sh` queries give the same answers through the wasm ops as through `l4sbm11` on the same generation.
2. SBM11 pack in wasm. The packer over host-supplied input chunks and host writes, as `Wasm/Ops/Pack.lean` does for IBK. `factoidal pack` defaults to SBM11. Exit: byte-identical generation against `l4sbm11 pack` on the corpus ladder; the cases of `test/pack-is-a-set-1006.test.mjs` pass for SBM11.
3. Update, delta log and compaction in wasm. `factoidal update` and `compact` on SBM11.
4. Browser store in OPFS. A worker host over `FileSystemSyncAccessHandle`; pack, query and update persist across reloads. A remote read-only host over HTTP `Range`.
5. Commands built from the API. `l4sbm11` subcommands become thin callers of the same ops; the entry-point gate maps `cli:pack`, `cli:query`, `cli:update`, `cli:compact` to registered stages.
6. Consumer. londat `kgx` packed as SBM11 with the new engine; `cwplans/kg/worker.js` on the SBM11 ops.

## 5. Risks

- Wasm32 memory: SBM11 uses 64-bit term ids and the native path uses a worker pool and page caches sized for a 4-vCPU VM. The wasm session needs bounded caches and one thread at first.
- The native path reads with `pread`; the proof assumption `ReadsWritten` is the same for a host read function. Session caches are not covered by a theorem on either path.
- Packing is memory-bound (`docs/designissues/2026-09-05-shard-pack-profile-and-memory.md`); a browser pack is for small and medium inputs until a streamed SBM11 pack is measured.
