# A WebDAV server for file browsers, over local and remote LWS storages

Date: 2026-10-27. Issue: https://github.com/danbri/factoidal/issues/1066 (stage 1).

Owner, 2026-10-27, verbatim:

> "Also implement a WEBDAV server that native file browsers can connect to to
> see factoidal-powered stuff eg initially lws client and server, Client uses
> config markdown files"

## Result

`factoidal webdav-serve CONFIGDIR [--port N] [--host ADDRESS] [--users FILE]
[--cert FILE --key FILE]` serves WebDAV
(RFC 4918, classes 1 and 2). Its root collection holds one folder per mount.
A mount is one Markdown file. A `local` mount is an `lws-serve` storage
directory; an `lws` mount is a remote LWS storage, reached through the Lean
LWS client.

Every WebDAV decision is in Lean (`formal/lean4/L4Factoidal/WebDAV/`). The
Node host (`npm/factoidal/webdav/server.mjs`) carries sockets, files and
fetches only (iron rule 7; `tools/host-purity-lint.sh` covers it).

## State across a restart

https://github.com/danbri/factoidal/issues/1078. The server's state
(`Server.DavState`: the dead properties per resource, the locks, the counter
of lock tokens) is kept in `CONFIGDIR/.webdav-state.json`
(`State.stateFileName`). The engine defines the form
(`L4Factoidal/WebDAV/State.lean`, `stateText` and `stateOfText`); the host
reads and writes the file only.

    {"format":"factoidal-webdav-state","version":1,"serial":N,
     "props":[{"key":"/m/a.txt","props":[{"ns":"urn:x"|null,"local":"colour","value":V}]}],
     "locks":[{"token":"urn:uuid:…","root":{"segs":["m","a.txt"],"slash":false},
               "infinite":B,"exclusive":B,"owner":V|null,"timeout":N,"expires":N}]}
    V = {"node":[EVENT,…],"bindings":[[PREFIX,NAMESPACE],…]}
    EVENT = ["e",TAG,[[NAME,VALUE],…],CHILDREN] | ["t",TEXT] | ["c",COMMENT]
          | ["d",CDATA] | ["p",TARGET,DATA]

A dead property value keeps the element the client wrote, as written, and
the namespace bindings in force at it (`Xml.DeadValue`), so a value reads
back the same after a restart. Its tree is a flat list of events: an element
gives its tag, attributes and number of children, and its children follow.
`nodeEvents` and `nodeOfEvents` are each one loop (a stack of sibling lists,
a stack of open elements).

Start: `webdavOpen` takes `now` (the host's clock) and names the state file
in its first `need.read`. A missing file is an empty state. A text that
`stateOfText` refuses stops the start: the error names the file and the
reason (for example `.webdav-state.json: format version 2 is not known (this
engine reads version 1)`). Locks with `expires` at or before `now` are not
loaded.

Each request: when the text of the state after the request differs from the
text last read or written, the response envelope carries
`write: {path: ".webdav-state.json", text, mode: "0600"}`. The host writes a
new file in the same directory, flushes it, and renames it over the state
file before it sends the response.

Checks: the `#guard`s of `State.lean` (a state with nested values, bindings,
CDATA, a comment, a processing instruction and two locks reads back equal;
refusals of malformed text, another format, another version, a malformed
lock, a child count larger than the children) and of `Tests.lean` § "State
across a restart" (the state the server makes after PROPPATCH, MKCOL and two
LOCKs reads back equal in both loopbacks; after a restart the property is
there, a PUT without the token is 423 and UNLOCK with the token is 204; a
lock that expired before the restart is not loaded; a value 5,000 elements
deep reads back equal). The round trip is checked by these `#guard`s, not by
a theorem. `tests/webdav/server.mjs`: a dead property and a lock survive a
restart of `webdav-serve`; a malformed state file stops the start (exit 1).

## Login and HTTPS

https://github.com/danbri/factoidal/issues/1108. Expert review requested:
https://github.com/danbri/factoidal/issues/1117. Every decision is in
`formal/lean4/L4Factoidal/WebDAV/Login.lean`; the handle
(`Wasm/Ops/WebDAV.lean`) keeps the users, the cache and the request a login
holds back.

The users file (`--users FILE`):

    # comment lines and empty lines are not users
    alice:pbkdf2-sha256:600000:SALT_B64:HASH_B64

* NAME: one or more characters, no `:`, no control character. A name given
  twice stops the start.
* `pbkdf2-sha256`: the only scheme.
* ITERATIONS: decimal digits, 100,000 to 10,000,000.
* SALT_B64: base64 (RFC 4648 §4, padded) of at least 16 bytes.
* HASH_B64: base64 of the 32-byte PBKDF2-HMAC-SHA256 (RFC 8018 §5.2) of the
  password's UTF-8 bytes. No Unicode normalisation on either side.

A line the reader refuses stops the start: `users.txt:2: the iteration count
99999 is below 100000`. A missing file, or a file with no user, stops it too.
`webdav-user FILE NAME [--iterations N]` adds the line or replaces the line
of that name in place, keeping every other line.

Start: `webdavOpen` takes `login: {users, tls, host}` from the host. With a
users file, `Login.transportAllowsBasic` must hold: TLS, or a loopback
`host` (`127.0.0.0/8`, `::1` with or without brackets, `localhost`). The
first `need.read` names the users file (an absolute path).

Each request, before WebDAV (`Login.gate`, then `Login.finish`):

| Request | Result | Derivation |
| --- | --- | --- |
| no `Authorization`, not `Basic`, token not base64, no `:`, user-id not UTF-8 | 401 | none |
| known user, cache hit | the WebDAV answer | none |
| known user, no hit | the WebDAV answer when the derived bytes equal the stored hash (`ctEq`), else 401 | one |
| unknown user | 401 | one (default count, salt from the secret) |
| credentials, name or address over the failed-login limit (section "Failed-login limit") | 429 with `Retry-After` | none |

A derivation is the envelope
`{"ok":true,"need":{"op":"pbkdf2-hmac-sha256","key":PASSWORD_B64,"data":SALT_B64,"iterations":N,"bits":256}}`;
the host runs `answerCipherRequest` (`npm/factoidal/lib/cipher-host.mjs`,
`crypto.subtle.deriveBits`) and gives `{"ok":B64}` or `{"refused":true}` to
`webdavResume`. A refusal is a 401.

The cache: one entry per user, `tag = SHA-256(secret ‖ u32be(len name) ‖
name ‖ password)`, the stored hash, and `expires = now + 300`. The secret is
SHA-256 of a label and the 32 random bytes of `webdavOpen`, so it is new at
each start. A hit needs the tag and the stored hash equal by `ctEq` and the
clock before `expires`; a failed login writes nothing. The cache is never
written to a file.

TLS: `--cert` and `--key` go together; the host reads both PEM files and
listens with `https.createServer({cert, key})`. With TLS the users file is
accepted on any address.

Checks: the `#guard`s of `Login.lean` (the reader and each refusal, the
loopback rule, the Basic reader, the decision with and without the cache,
the expiry, a changed stored hash, `webdav-user`'s line edits) and theorems
`gate_none` (no `Authorization`: 401, no derivation), `finish_unknown` (an
unknown user is never allowed, whatever the host answers) and
`finish_refused`. `tests/webdav/server.mjs` § login and
`tests/hub/hub_webdav_test.mjs` (with a self-signed certificate from
`openssl req -x509`) run them through the CLI.

## Failed-login limit

https://github.com/danbri/factoidal/issues/1119. Owner, 2026-10-28, verbatim:
"Does “no rate limit” expose our server passwords to automated hacking tools?
In which case default to protection but have a
—dangerously-disable-ratelimits option ?" The numbers below are the
implementer's. Decisions: `Login.Failures`, `Login.limitsOf`, `Login.gate`,
`Login.finish` in `formal/lean4/L4Factoidal/WebDAV/Login.lean`.

* Keys: `name:` and the user name as sent (an unknown name is counted the
  same way, so the answers do not tell which names exist), and `address:`
  and the client address (`clientPrefix`: IPv4; `::ffff:a.b.c.d` as IPv4;
  IPv6 by its /64 prefix). The host gives the socket's `remoteAddress` with
  each request; it decides nothing.
* Counter: a fixed window from the key's first failure. A key with
  `maxFailures` (default 5) failures in a live window (default 60 s) is
  blocked until the window ends.
* `Login.gate`: no credentials or not Basic: 401, not counted. Else, when the
  name key or the address key is blocked: 429 Too Many Requests (RFC 6585
  §4) with `Retry-After` (seconds until the later window ends), before the
  cache is read and with no derivation. The right password gets 429 too.
* `Login.finish`: a derivation that does not allow the request (wrong
  password, unknown name, host refusal) is one failure on both keys. A
  success changes no counter.
* Memory: at most 10,000 live counters. A new key in a full table evicts
  the counter with the oldest window that is not blocked and is not a key of
  the attempt; a blocked counter is never evicted, so a flood cannot end a
  block early. When there is no place for an attempt's new keys, the attempt
  gets 429 until the first window ends (fail closed). The rate of new
  failures is bounded by the derivations the host can run (each one is
  PBKDF2 with at least 100,000 iterations, one request at a time), so with
  the default window the table does not fill.
* Cost, accepted: anyone can block a user name for one window at a time by
  sending wrong passwords for it (a denial of service against that name).
  The window is short, and the block ends at a stated time.
* `--dangerously-disable-ratelimits`: no counter, no 429; `ready.warnings`
  carries a text that the CLI prints on standard error at start, after the
  EXPERIMENTAL notice. With `--login-limit` or `--login-window`, or without
  `--users`, the start stops.

Checks: `#guard`s in `Login.lean` (under the limit, at the limit, the right
password while blocked, the name blocked from every address and the address
for every name, window expiry, no credentials not counted, unknown name the
same as a known one, success counts nothing, a cached user still blocked,
disabled, eviction keeps a blocked counter, a full table answers 429, the
address key, the options); theorems `gate_limited`, `check_blocked`,
`gate_no_derive_of_blocked` (with the limit on, no derivation is asked for
when the attempt's name key or address key is blocked) and
`check_disabled`. `tests/webdav/server.mjs` § login runs them through the
CLI: 401 401 401 then 429 for wrong passwords, `Retry-After`, 429 for the
right password, 207 after a 2 s window, 401 (not 429) after 9 failures with
`--dangerously-disable-ratelimits` and its warning.

## Mount files

    # Display name
    - kind: local
    - path: ./alice-storage
    - writable: true

    Free text below the list is for people and is ignored.

Reading (`L4Factoidal/WebDAV/Config.lean`, one loop over the lines):

1. The mount name is the file name without `.md`. It may not be empty, start
   with `.`, or hold `/`, `\` or a control character.
2. The first line that starts with `# ` gives the display name (default: the
   mount name).
3. The first run of lines that start with `- ` is the settings list. It ends
   at the first line that does not start with `- `; an empty line ends it.
4. Each item is `- key: value`. The value is the text after the first `:`,
   with spaces removed at both ends. Nothing after the value is a comment.
5. Lines in a fenced code block (between lines that start with three
   backquotes) are not read. A CR before the line end is removed.

| Key | Values | Applies to | Default |
| --- | --- | --- | --- |
| `kind` | `local`, `lws` | all | required |
| `path` | a directory, relative to CONFIGDIR | local | required |
| `storage` | `snapshot`, `files` | local | what the directory holds |
| `base` | an `http`/`https` IRI that ends with `/` | local | `http://localhost/` |
| `url` | an `http`/`https` URL (a `/` is added at the end) | lws | required |
| `auth` | `none`, `did-key`, `bearer` | lws (local: `none` only) | `none` |
| `key-file` | a file, relative to CONFIGDIR | lws, `did-key` | required with `did-key` |
| `token-file` | a file, relative to CONFIGDIR | lws, `bearer` | required with `bearer` |
| `writable` | `true`, `false` | all | `true` for local, `false` for lws |

The start stops, with `FILE:LINE: reason` (line 0 is shown as `FILE:`), on: an
item with no `:`, an unknown key, a key given twice, a value outside its set,
a key that does not apply to the kind, a missing required key, a local
directory that does not exist, a token file that does not exist, a key file
that is not a P-256 private JWK. Theorem `scan_known`: a file the reader
accepts holds no unknown key.

`did-key`: the key file is a JWK with `kty: EC`, `crv: P-256` and `d`. When it
does not exist, the engine makes one from 32 bytes of the host's random
source (SHA-256 of a label, the bytes and a counter, the first valid scalar)
and the host writes it with mode 0600, never over an existing file. The
mount acts as the key's `did:key` (multicodec 0x1200, the compressed point,
base58btc); `webdav-serve` prints it at start.
Two mounts that name one absent key file (after `.` segments are removed:
`alice.jwk` and `./alice.jwk` are one file) get one key, made by the first
(found on 2026-10-27 while writing the hub page `docs/web/hub/webdav.md`: the
engine made a key for each mount and the start stopped with `EEXIST`).

`bearer`: the token file holds an access token, sent as `Authorization:
Bearer` to every URL under `url`.

## How a request runs

```
file browser --HTTP--> host --webdavStep--> engine: handle cx state request
                                              |  a Prog: pure (response, state)
                                              |       or call op (answer -> Prog)
          host <--{lws: request}-- local mount: one LWS request (Local.lean)
          host --lwsStep (openLwsStorage, no socket)--> the storage handle
          host <--{fetch: request}-- lws mount: the LWS client machine (Remote.lean)
          host --fetch--> remote storage
          host --webdavResume(answer)--> engine ... until {response}
```

`Backend.Prog` is a program over six storage operations:

| Operation | LWS request (local) | LWS client op (remote) |
| --- | --- | --- |
| `head p` | `HEAD p` | `head` |
| `list p` | `GET p`, `Accept: application/lws+json` | `list` (every `next` page) |
| `get p` | `GET p` | `read` |
| `put p ct body onlyNew` | `PUT p` with `Content-Type`; `If-None-Match: *` when `onlyNew` | `update`, precondition `none` or `ifNoneMatchStar` |
| `delete p` | `DELETE p`; `Depth: infinity` for a container | `delete`, `recursive` for a container |

A program is data, so one handler (`Server.handle`) runs in three places: in
`#guard`s against `LWS.step MemStore` (directly, and through the LWS client
against the same server), and through the host against a real directory or a
real remote storage. Copy is `get` and `put` (a collection: `put` of the
container, then each member); move is copy, then `delete`.

The engine keeps the request in flight in the handle (the program's
continuation; for a remote mount, the client's state). The host serves one
request at a time.

## The mapping between WebDAV and LWS

* `/` is the server's own collection of mounts; no storage is asked.
* `/<mount>/a/b` is the storage path `/a/b`; `/<mount>/a/b/` is the container
  `/a/b/`. A path with no `/` at the end that is not a data resource is tried
  as a container (clients name collections both ways).
* Segments are percent-decoded to UTF-8 and written in one spelling
  (`Path.encodeSegment`); a fragment, an empty, `.` or `..` segment, or a
  decoded `/`, `\` or NUL is refused (400).
* LWS container = collection, data resource = file. Linksets, ACL resources
  and the storage description are not members of a listing, so they are not
  shown.
* `DAV:getetag` = the LWS `ETag`; `DAV:getcontenttype` = the LWS media type;
  `DAV:getlastmodified` = `Last-Modified` (a listing's `modified`, an
  `xsd:dateTime`, is written as an HTTP-date); `DAV:getcontentlength` = the
  listing's `size` (an LWS `HEAD` has no length, so a Depth 0 PROPFIND of a
  file reads the parent's listing too). `DAV:creationdate` is not given: LWS
  has no creation time.
* A listing has no entity tags. RFC 4918 §15.6: getetag "MUST be defined on
  all DAV-compliant resources that return the Etag header", so a Depth 1
  PROPFIND that asks for it (allprop, or by name) reads each member with one
  `HEAD`.
* MKCOL = `PUT <path>/` with `If-None-Match: *` and no content (an LWS
  container).
* LOCK of an unmapped URL (RFC 4918 §9.10.4) = `PUT` of an empty
  `application/octet-stream` resource with `If-None-Match: *`.

Storage answers become WebDAV statuses (`Server.davStatusOf`): 2xx as they
are; 404 and 410 are "absent"; 400, 405, 409, 412, 415 as they are; 401 and
403 become 403 (the file browser has no credential to give this server);
413 and 507 become 507; no answer and 5xx become 502. A lookup that fails
(not 404) is reported, never read as "absent".

## Methods

OPTIONS answers `DAV: 1, 2`, `MS-Author-Via: DAV` (Windows) and `Allow`.

| Method | Statuses |
| --- | --- |
| GET, HEAD | 200; a collection is an HTML page of links; 404 |
| PUT | 201, 204; 405 on a collection; 409 with no parent; 423 |
| DELETE | 204; 404; 400 for a collection with Depth other than infinity; 423 |
| MKCOL | 201; 405 when the name exists; 409 with no parent; 415 with a body |
| COPY, MOVE | 201, 204; 400 (no Destination, bad Depth); 403 (overlap, mount root); 409; 412 (Overwrite F); 423; 502 (another server or mount) |
| PROPFIND | 207; 400; 403 (Depth infinity or none); 404 |
| PROPPATCH | 207 (403 for a live property and 424 for the others); 400; 404; 423 |
| LOCK | 200, 201 (unmapped URL), with `Lock-Token`; 400; 409; 412 (refresh with no matching token); 423 (`no-conflicting-lock`) |
| UNLOCK | 204; 400 (no Lock-Token); 409 (`lock-token-matches-request-uri`) |

A read-only mount answers 403 to every write method. Every request starts
with the `If` header (§10.4): a malformed header is 400, a false one 412. A
write to a locked resource needs the lock's token in the `If` header, else
423 with `DAV:lock-token-submitted`. A lock covers its root, and with Depth
infinity everything under it; a lock on a collection protects its membership,
so a member added or removed needs its token too (§7.4). An exclusive lock
shares nothing; shared locks share with shared locks. Lock tokens are
`urn:uuid:` version 4 UUIDs from 16 of the host's random bytes. Timeouts:
`Second-N` or `Infinite`, at most a week, an hour by default; an expired lock
is gone.

Dead properties (§4) keep the element the client sent and the namespace
bindings in force at it, so a value that uses a prefix declared on an
ancestor reads back the same (litmus `propvalnspace`). The last instruction
of a PROPPATCH for a name decides it.

## Limits

Each limit is a refusal the engine names, measured by `tests/webdav/scaling.mjs`
(each case in its own process, through the wasm module, which has the
smallest stack):

* A request body that nests elements deeper than 256 levels is refused (400)
  before it is parsed (`Xml.maxBodyDepth`, a one-pass scan that never counts
  lower than the real depth). Found by the scaling check: a dead property
  value 25,000 levels deep overflowed the wasm stack in the parse tree.
* Responses are written from a work list (`Xml.serializeFlat`, `#guard`s
  equal to `Node.serialize`): a PROPFIND answer with 20,000 property names
  overflowed the wasm stack through `Node.serialize`, which recurses once per
  child.
* A PROPPATCH applies its instructions in one pass with a set of the names
  seen; the first version was quadratic (5,000 properties 1.1 s, 10,000
  3.5 s).
* An `If` header may name at most 16 resources (`Server.ifTagsMax`); a copy
  or move descends at most 64 levels.
* A mount file is read in one loop: 400,000 lines in 1.7 s.

## Theorems

* `Config.scan_known`: a mount file the reader accepts holds no unknown key.
* `Server.refused_keeps_state`: a request the precheck refuses (bad target,
  unknown method or mount, read-only mount, malformed `If`) names no storage
  operation and keeps the state; `Tests.refused_no_change`: in every model.
* `Login.gate_none`, `Login.finish_unknown`, `Login.finish_refused`: section
  "Login and HTTPS".
* `Theorems.browse_no_write`: OPTIONS, PROPFIND, GET and HEAD name no write
  operation, whatever the storage answers and in every model (the `If`
  evaluation included).
