## Step 1: `idlharness`, named access on the Window, interface objects

### What was wrong

| Loss | Count | Cause |
|---|---|---|
| Every `idlharness` test of WPT (all directories) | 39,327 Chrome subtests, 2 passed | Three defects of BubblePopJS, each hit by WPT's `resources/webidl2.js`. (1) `String.prototype.startsWith`, `endsWith`, `includes` and `lastIndexOf` ignored their position argument; the tokeniser finds punctuation with `str.startsWith(p, i)`, so no IDL parsed ("Unrecognised tokens"). (2) A sticky regular expression that fails took the steps of the whole rest of the subject, though it is tried at one index: two failures a token on `html.idl` (109 KB) used the 5 M steps of a run. (3) The decoded subject of the last match was kept for one string only, and the tokeniser tests one character (`/[\t\n\r ]/.test(c)`) between two matches on the input, so the input was decoded again for every token (quadratic: 2 s for `dom.idl`, 23 KB). |
| `x is not defined` for an element id (`html/` about 1,500; `css/` about 6,000 by the CSS agents' count) | several thousand | Named access on the Window object (HTML §7.3.3) was missing. |
| `idlharness`: "property should be enumerable", class strings | about 260 in `dom/` and `html/dom` alone | The page objects are JavaScript classes: their members are not enumerable and their prototypes had no `Symbol.toStringTag`. |
| `idlharness`: "interface object must pass IsConstructor check" | one for each interface | `new` on a Proxy threw: BubblePopJS had no `[[Construct]]` for a Proxy. |

### Changes

- `JS/Interp.lean`: `clampPos`, `unitsAt`, `lastIndexOfFrom`; the four String methods take their
  position; `startsWith` and `endsWith` on an ASCII receiver read only the units compared
  (`indexesReceiver`). A failed sticky match takes one step. `cachedChars` keeps only strings of
  `cachedCharsMin` (256) bytes or more, so a match on a short string leaves the kept subject.
- `JS/Interp.lean`: `construct` and `isConstructor` for a Proxy (`construct` trap, or the target).
- `DOM/Named.lean` (new): the named objects of a Window and the value of a named property, a
  function of the document tree. `node_query` op 180 (`Hosts/DomOps.lean`; this work uses ops 180
  to 199).
- `JS/Interp.lean` `namedGlobal`: a name with no binding (`lookup`, `typeof`), or a property that
  the global object and its chain lack (`getV`), asks the function in the global's internal slot
  (`namedGetterKey`, a private-name key). The prelude's function asks op 180 for the document of
  the running script. Only the miss path changed: a name that resolves does no new work.
- `prelude.js`: one pass over the interfaces on the global when the prelude runs (once for the
  engine): members enumerable, `Symbol.toStringTag` the interface's name (Web IDL §3.7).

### Proved, tested, open

Proved (Lean theorems, no `sorry`):

- `JS.clampPos_le`: a clamped position is at most the length.
- `JS.unitsAt_bound`: where `unitsAt` is true, the search string lies inside the subject.
- `DOM.Named.namedObjects_empty`, `value_empty`: the empty string names nothing.
- `DOM.Named.namedObjects_sound`: every named object is in the document's tree order and is
  named by one of the three bullets of §7.3.3.

Tested (`#guard`): the four String methods with positions, BMP and surrogate cases; 20,000
failed sticky matches inside 200,000 steps; `new` on a Proxy; the named-properties hook with a
script as the host; `DOM.Named.answer` on a sample tree (element, collection, frame, the
elements whose `name` does not count).

Open:

- `clampPos` equals the integer part of its argument: rests on `Float`, not proved.
- `'x' in window` and `Object.getOwnPropertyDescriptor(window, 'x')` do not see named
  properties. A frame renamed with `window.name` is not followed.
- A named-property miss walks the document once (as `getElementById` does): linear in the
  document for each read of a property the Window lacks.
- A Proxy on the prototype chain of an ordinary object is still not consulted on a miss.

## Step 6: the Sanitizer API (HTML §8.5.2, §8.6)

### What was wrong

`sanitizer-api/` passed 136 of 3,816: there was no `Sanitizer`, no `setHTML`, no
`Document.parseHTML`, and `setHTMLUnsafe` took no options.

### Design

- `HTML/Sanitizer.lean`: a configuration (`Config`), "canonicalize the configuration",
  validity (§8.6.3.1), every modifier method, "remove unsafe", `get()`'s sorting, the built-in
  safe default configuration (a table of 122 elements and 58 attributes), the decisions "get
  the sanitizer action for an element name" and "check if a sanitizer config allows an
  attribute", and the walk over a parsed fragment (`plan`: remove, replace with children, drop
  an attribute; template contents and declarative shadow roots are walked).
- The page's `Sanitizer` object holds its configuration as a text (`configWire`) and asks Lean
  for every method (`answer`, node_query 192). The prelude converts Web IDL dictionaries to that
  text and back; it decides nothing.
- `setHTML`, `appendHTML`, `prependHTML`, `beforeHTML`, `afterHTML`, `replaceWithHTML`, their
  `Unsafe` forms and `Document.parseHTML`/`parseHTMLUnsafe`: the markup is parsed into a fragment
  (or document) that no script holds, sanitized there (node_query 193, `Hosts.DomOps.sanitizeM`:
  the steps run as recorded commands), and only then inserted. A safe method never reads the
  fragment's event handler content attributes.
- **The check after the walk.** Safety does not rest on the walk. After it, `conforms` reads
  the tree again and answers whether every node below the root is one the configuration keeps;
  when it is not, the root is emptied. `conformsGo` answers false when its fuel ends with nodes
  left, so a true answer has read every node, with no assumption that the arena is a tree.
  Cost: one more pass over the sanitized fragment; a page that calls no sanitizing method pays
  nothing.

### Proved

- Decisions: `safe_removes_baseline` (with `safe`, `script`, `iframe`, `frame`, `object`,
  `embed`, `base`, SVG `script` and `use` are removed under any configuration),
  `safe_removes_handlers`, `safe_removes_script_urls`, `no_script_urls`,
  `navigating_javascript_scriptURL`, `unwrap_not_kept`, `setJavascriptURLs_sets`,
  `removeUnsafe_javascriptURLs`.
- The output: `conformsGo_sound`, `conforms_sound` (a true check means every node reachable
  from the root through children, template contents and shadow roots conforms),
  `below_emptied`, `sanitizeChecked_conforms`, and `safe_output`: in what a safe method leaves
  below the root, for every arena, root and configuration, no element is a baseline element,
  none has an event handler content attribute, and none has an attribute whose value is a
  script URL (`javascript:` in a navigating attribute or a MathML `href`, or an SVG animation
  of a link's target).

### Tested only, and open

- Tested: the `#guard`s (the default configuration's size, validity cases, the modifier
  sequences of `sanitizer-config.html`, the wire round trip, sanitized fragments); the
  `Sanitizer` object against Lean's answers in a local harness (sanitizer-config 71 of 72 as
  Chrome, sanitizer-get 9/9, sanitizer-modifiers 21 of 22 as Chrome).
- Open: that the walk's result always passes the check (if it did not, a page would get an
  empty result: fail closed); that the commands `sanitizeM` records build the same arena as
  `sanitize` (the host runs `conforms` on the arena it has); the standard sanitizes while
  parsing, this sanitizes the parsed fragment, which differs where the parser would have moved
  a node the sanitizer removes; `get()` sorts by code points, not UTF-16 code units;
  `runScripts`; the streaming methods; declarative shadow roots in `parseHTML`;
  `javascriptURL` is the URL parser's answer for the scheme.

## Step 7: Trusted Types

### What was wrong

`trusted-types/` passed 54 of 3,754: no `trustedTypes`. 2,695 of the subtests declare their
policy in a `meta` element, 93 in response headers.

### Design

- `HTML/TrustedTypes.lean`: the two CSP directives read from a serialized policy
  (`parsePolicy`), "does sink type require trusted types" (`requires`), the outcome of "get
  Trusted Type compliant string" (`outcome`: the input's string, the default policy's value,
  or a TypeError), "should sink type mismatch violation be blocked" and which policies get a
  report, "should Trusted Type policy creation be blocked", "get Trusted Type data for
  attribute" (`attributeType`), the data of `getPropertyType`, the list of event handler content
  attributes, and the policies of a document's `meta` elements (`metaContents`). node_query 194.
- The prelude holds the objects (`trustedTypes`, policies whose functions are the page's, the
  three value types) and asks Lean at every sink; it never decides that a string may pass.
- Sinks: `setAttribute`, `setAttributeNS`, `setAttributeNode(NS)`, `Attr.value`; `innerHTML`,
  `outerHTML`, `insertAdjacentHTML`, `ShadowRoot.innerHTML`, the `Unsafe` insertion methods,
  `Document.parseHTMLUnsafe`, `document.write/writeln`, `DOMParser.parseFromString`,
  `Range.createContextualFragment`, `iframe.srcdoc`; script `src`, `text`, `innerText`,
  `textContent`; `setTimeout`/`setInterval` with a string.
- **An attribute is compiled as an event handler only when Lean's table names it.** So every
  attribute that can run script is a TrustedScript sink (`handler_is_script_sink`).
- Cost: the sink hooks are null until the page uses `trustedTypes`, creates a `meta` element,
  or one of its documents declares a policy (asked once when the page starts, and once for a
  frame's document when its first script runs). Other pages pay one comparison at a sink.
- A policy once seen stays in the document's list after its `meta` element is removed (CSP:
  a policy is not withdrawn). That list is the prelude's state; the network side's header
  policies join it when they exist.

### Proved

`enforced_refuses_plain`, `enforced_input_is_trusted` (under an enforced policy a string
reaches a sink only as a value of the expected type or through the default policy),
`trusted_passes`, `unrequired_passes`, `requires_mono`, `mismatchBlocked_mono`,
`creationBlocked_mono` (adding policies never removes a restriction), `no_directive_allows`,
`unlisted_blocked`, `duplicate_blocked`, `handler_is_script_sink`,
`sanitizer_handlers_are_handlers`.

### Tested only, and open

- Tested: the `#guard`s (directive parsing, the creation cases of
  should-trusted-type-policy-creation-be-blocked-by-csp-001, the attribute cases of
  support/attributes.js, getPropertyType, the wire, a document with `meta` policies); the
  objects and the sinks against Lean's answers in a local harness.
- Open: policies from response headers and report-only policies (the network side);
  `eval`, `Function`, `javascript:` URLs, the script element's text changed through child
  nodes ("prepare the script element"), workers, `TrustedHTML.fromLiteral`, the
  `createParserOptions` callback, `Node` methods with several arguments on a script element;
  reports are fired as events only (no report endpoint); a `meta` element inserted with markup
  into a page that has not gone live is not seen.

## Step 8: interface objects (Web IDL §3.7.6)

The one pass over the interfaces at prelude time now also names the accessor functions
("get x", "set x"), and puts an interface check (`this instanceof` the interface, else a
TypeError) in front of each getter that answered for a plain object when asked once there.
In the `idlharness` files of `dom/` and `html/dom` these two are 843 of the 3,396 failing
subtests; 2,000 more fail on interfaces and members that do not exist.

On a generated Web IDL binding layer (from `interfaces/*.idl`): not taken. What such a layer
can add correctly without an implementation behind it is shape (names, enumerability,
`length`, interface checks), and that part is closed by this pass without the IDL files. The
larger part of the failures is missing interfaces and members; generating them as members
that do nothing would pass `idlharness` and break pages, which choose code paths by testing
whether a member exists. A table from the IDL files would still be worth having for the
argument-count checks ("Called with 0 arguments" must throw: 110 here) and for `length`.

### Step 9: frames share the realm, not their windows' properties

348de4289 made `frame.contentWindow.x = v` a property of the frame's window object alone, so
that it could not replace the page's global `x`. The frame's own scripts run in the shared
realm and read `window.x` from its global, so they never saw such a value: `dom/ranges`
Range-cloneContents, deleteContents and extractContents (440 subtests) set `testRangeInput`
on the frame's window and its `run()` found nothing. The write now goes to the global unless
the page made a global of that name itself (that one stays the page's and the value stays
on the window). A frame element (`frame`) gets a child navigable as an `iframe` does
(`Hosts.Dom.frameOwner`); `contentDocument` and `contentWindow` are null when there is none;
a frame's XML document has the content type its root gives.

### Step 10: presentational hints (HTML §2.3.4, §15)

`HTML.Dimension` reads the rules for parsing integers, non-negative integers, dimension
values and nonzero dimension values exactly: a decimal mantissa and scale, a length or a
percentage (`200.25%`, `20.25e2` is 20.25, a sign or a leading `.` fails). `Rendering.Style`
maps with it: `width`/`height` of `img`, `video`, `canvas`, `iframe`, `embed`, `object`,
`marquee` and image buttons, `hr` width, `hspace`/`vspace` to margins, `border` of `img`,
`object` and image buttons to solid borders, table and cell sizes ignoring zero, `col`
width, `table`/`tr` height, and the `body` margin attributes. A percentage height is left
out: this layout resolves a percentage height against 0. `ComputedValues` wrote a
percentage (held as a fraction) as the fraction; it writes `50%` now. These hints change
what real pages look like: `<img width=… height=…>`, `<td width=…>`, `<hr width=50%>` and
`<body marginwidth=0>` are common in older markup.
