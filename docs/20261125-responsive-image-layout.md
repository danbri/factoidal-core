# Responsive image dimensions in native layout

The image selector returns a URL and a rational pixel density. The renderer used the URL to fetch and decode a bitmap, then used the decoded dimensions for every element displaying that URL. A 96×48 image selected at 2x occupied 96×48 CSS pixels. Its intended box is 48×24, with the full bitmap drawn inside it.

The native renderer carries the selected density to the individual element. The URL continues to identify its store entry, backing bitmap and paint-table ID. SVG width, height and ratio are recorded when the decoder already has the XML root. Layout divides the intrinsic axes by density in 1/64 CSS pixel units. An explicit CSS width or height can use the independent source ratio even when both natural axes round down to zero. CSS object fitting maps the full bitmap to the fitted rectangle.

Chrome on a Retina display drew the same 101×51 PNG at 50.5×25.5 CSS pixels with a 2x descriptor and returned 50×25 from its natural-size getters. At 1000x the natural-size getters both returned zero, while a CSS width of 101px produced a 101×51 box. Chrome also retained 101×51 at 10000x when the only constraint was a 101px minimum width or a 51px minimum height. The constraint table therefore transfers those limits with the stored source ratio. At 2x a width-only SVG of 30px without an intrinsic ratio measured 15×150. Height-only measured 300×15. An SVG without intrinsic axes retains the renderer's existing fallback geometry. Source selection still uses the existing nominal 1280×800 viewport and DPR of one.

Lean 4.33.1 compiled the image store and its codec dependencies. A source-extracted integration check decoded the original 256×256 WPT PNG, verified its green pixels, and exercised the selector, element-to-picture lookup and CSS dimensions. Two requests for the same URL returned the same bitmap and ID at sizes of 256×256 and 128×128. The resource-preservation theorem covers every selected density. Its audit reported only standard Lean foundations.
