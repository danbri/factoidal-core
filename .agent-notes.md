## Comment draft for issue 750 (not posted)
The audit did see `L4Factoidal.XML.scanRefs`: on core 4b5892b0 it is a row of
`--json` with 2 non-tail self-calls. It is classed `counter`, and `--gate` checks
only `length` and `depth`. Why `counter`: the classifier reads the signature as
text; `scanRefs (ents : EntityTable) (s : Chars) (start stop : Nat) : Nat → ...`
names `Chars`, which is `abbrev Chars := Array Char` (XML/Parser.lean:185), and
LENGTH_TYPES does not resolve an abbrev; the Nat arguments then give `counter`.
The Nat is a fuel set to the range length (`pos' - pos + 1`), so the depth is the
input length. Not `unknown`, not a short-name csimp match. Same shape in other
counter rows (textual search of the signature for the 74 `abbrev`s whose right
side names List/Array/ByteArray/String/Substring; short names like `P`, `M` can
give false hits): 11 of 32 counter rows, e.g. SPARQL.pCollection,
SPARQL.pGroupOrUnion, SPARQL.pAnnotations (TStream), Cottas uvarintDecode and
leUintDecode (Bytes), VC.Multibase.natToBytesBE. Repairs: resolve abbrevs before
the length match; gate `counter` with an allow list that states the bound.
